# 実測モードの試作(runtime PoC)の設計メモ

作成日: 2026-11-01

実測モードの試作(PoC)の設計メモ(B1)である。対象アプリを計測用の DB に載せて、件数を変えながらルートを実際に叩き、クエリの本数を数えて増え方を判定する。静的解析が「分からない」と言ったルートを、実測でどこまで埋められるかを見るための試作であり、**本採用ではない**。

試作のコードは `poc/runtime/` にあり、公式の CLI にも phar にも入っていない(`tests/Unit/PocIsolationTest.php` が、混ざらないことを守る)。本採用が決まったら `src/` に作り直す。試作をそのまま移さない。

節の構成は、目的と読み方(§0)・全体像(§1)・起動のしかた(§2)・データの生成(§3)・N の決め方(§4)・ルートの叩き方(§5)・計測(§6)・判定の規則(§7)・結果の出し方(§8)・安全の条件の実装(§9)・実装の状況(§10)・質問と判断(§11)である。実測の結果は `docs/research/runtime-poc.md` に書く。この文書は設計であり、数字は実装を確かめて得た事実(起動、データ生成)に限る。

## 0. 目的・範囲・読み方

### 0.1 目的

静的解析は「コードが何をしうるか」を読む。実測は「この入力で、実際にどの経路を通り、何本のクエリを流したか」を数える。両方を並べて、次の 3 点を調べる。

1. 静的解析が確定と言ったルートを、実測も同じ判定にするか(食い違いは最優先の発見である)
2. 静的解析が unknown と言ったルートのうち、実測が判定できる割合
3. 実アプリで、自動で叩けるルートの割合と、叩けない理由の内訳

### 0.2 読み方の注意

- **実測の言い切りは「この入力で通った経路」だけである。** 実測の語は静的解析の語と分ける(`measured_O1`・`measured_ON`・`measured_ONM`・`inconclusive`・`no_info`・`not_measured`)。`measured_O1` を「O(1)」と読み替えない。データに届いていない実測は、平坦に見えても「情報なし」とする(§7.3)。
- D21(「分からない」を「安全」にしない)は崩さない。実測が O(1) に見えても、静的解析の確定を実測で上書きしない。食い違いは期待値にも実測にも合わせず、そのまま報告する(§8)。
- 「実装済み」と書いたものは、`poc/runtime/` に実装と試験がある。「設計のみ」「未確認」と書いたものは、まだ実装していない、または実機で確かめていない。見分けられるように、節ごとに明記する。
- **実測が見る経路の範囲。** 「この入力で通った経路」の中身は、次の 3 点で決まる。実測は、ここに書いた入力が通る経路しか見ない。
  - (a) POST などの本文は、**必須の項目だけ**を送る(§5.4)。任意の項目が通ったときにだけ現れる分岐は見ない。
  - (b) GET は**クエリ文字列なし**で叩く(§5.4)。ページ番号・絞り込み・並び順を指定したときの経路は通らない。
    - **例外が 1 つある。** アプリのプロファイルが認めたルート(実アプリの Subsonic 互換 API)では、ルート自身の認証を通すために、資格情報をクエリ文字列に載せる。載せるのは、その走の合成の鍵から導いた値だけで、ページ番号や絞り込みは指定しない。
  - (c) 画面を返すルートは、`Accept` の選び方で経路が変わる(JSON と HTML で別の処理をするルートがある)。どちらで測ったかは試行の記録に残るが、片方しか測らないルートでは、もう片方の経路は見ない。
- 手元の実アプリは Laravel 12 が 1 本、13 が 4 本で、11 は無い(D40)。11 に関する記述は**見込み**である。

## 1. 全体像

```
静的解析の出力(JSON)── ルート一覧と、静的の判定(growth・lower_bound・n_table・m_table)
        │
        ▼
計測用 DB を規模ごとに作る(peak_sim_measure_<run>_<規模>)
   対象アプリの migration を流す → ツールが合成データを入れる(§3)
        │
        ▼
ルート × 規模ごとに 1 プロセスで対象アプリを起動し、3 回叩く(ウォームアップ・コールド・ウォーム)(§5・§6)
   各リクエストはトランザクションで巻き戻す。クエリ本数は DB::listen で数える
        │
        ▼
最大の 2 規模の log-log 傾きで判定する(§7)。静的の判定と並べる(§8)
```

構成は 3 つのコンテナ層に分かれる。対象アプリのコードが動くのは、内部ネットワークだけにつながった PHP コンテナの中だけである(§9)。

| 部品 | 場所(`poc/runtime/`) | 役割 | 状況 |
| --- | --- | --- | --- |
| 封じた環境 | `compose/`・`bin/stack`・`bin/preflight`・`bin/cleanup`・`bin/canary-egress` | 内部ネットワーク、専用 DB ユーザー、起動前の検査 | 実装済み |
| 入力の検査 | `src/Config/`・`src/Guard/` | 環境変数だけを入力にし、ホスト・ユーザー・DB 名を検査 | 実装済み |
| 起動 | `src/Boot/` | 対象アプリをプロセス内で起動し、偽物に差し替える | 実装済み |
| データ生成 | `src/Data/` | スキーマから合成データを入れる | 実装済み |
| ルート・引数・本文 | `src/Route/` | ルートの地図、引数、ログイン利用者、POST の本文 | 実装済み |
| 1 回の計測 | `src/Run/`・`bin/measure-one` | 1 つの(ルート、規模)を 1 プロセスで測る | 実装済み |
| 判定・報告 | `src/Judge/`・`src/Report/` | 傾きの判定、静的との突き合わせ | 実装済み |
| 全体を回す入口 | (`bin/measure`) | 規模ごとの DB 作成 → 生成 → 全ルートの計測 → 後始末を束ねる | **未実装**(§10) |

## 2. 起動のしかた

### 2.1 起動の方式(安全の条件 4)

対象アプリのファイルは 1 つも書き換えず、パッケージも足さない(D7)。ツール側のファイルが、対象アプリの `vendor/autoload.php` と `bootstrap/app.php` を読み込み、**同じ PHP プロセスの中で HTTP カーネルを呼ぶ**。Web サーバーもネットワークも使わない。

1. 対象アプリは**読み取り専用**でマウントする(`/app`)。コンテナのルートも読み取り専用で、書けるのは `/tmp`(tmpfs)と出力先(`/out`)だけである。「書き換えない」を、守る決まりでなく、破れない機構にする。
2. 設定は**実環境変数**で与える。Laravel は実環境変数を `.env` より優先するので、対象アプリの `.env` は値の出どころにならない。与えるものは、`APP_ENV=local`・`APP_DEBUG=false`・`APP_KEY`(起動のたびにツールが生成)・`DB_*`(計測用 DB)・`CACHE_STORE`/`CACHE_DRIVER=array`・`SESSION_DRIVER=array`・`QUEUE_CONNECTION=sync`・`MAIL_MAILER=array`・`BROADCAST_*=null`・`LOG_CHANNEL=stderr` などである。
3. アプリが書く場所(`storage`・コンパイル済みビュー・各種キャッシュ)は、環境変数(`APP_*_CACHE`・`VIEW_COMPILED_PATH`)と `useStoragePath()` で、使い捨ての作業ディレクトリ(`/tmp`)へ逃がす。
4. 起動後に**全ての DB 接続**を調べる。mysql/mariadb の接続は、ホスト・DB 名・ユーザー・パスワードを計測用の値で上書きする。他のドライバ(sqlite・pgsql など)の接続は、計測用の mysql 接続に付け替える。そのうえで、全接続が計測用 DB を指すことを、設定と DB サーバーの両方で確かめる(違えば起動を拒否する)。
5. 偽物の差し替え(§9 の条件 5)を入れてから、リクエストを送る。

## 3. データの生成

### 3.1 方針

データは**ツールが生成した合成データだけ**を入れる。既存の DB やダンプは使わない(安全の条件 3)。ツールが自分で入れたデータを読むことは、D5 の「データの中身は読まない」に反しないと判断している(D44。実測モードが読むのは `peak_sim_measure_` で始まる計測専用 DB の合成データに限り、利用者の既存 DB の中身は読まない)。

層は 3 つある。

1. **スキーマから生成する(既定)。** factory が無い表も、同じ規則で入れられる。実装は `src/Data/` の `Generator`。
2. **アプリの factory を使う(任意)。** `FactoryRunner` が、モデルの `::factory()->count(n)->create()` を呼ぶ。1 行ずつの INSERT で遅く、Faker(dev 依存)が要るので、「ログインする利用者」のような少数行にだけ使う。Faker が無い環境(`--no-dev`)では `faker_missing`、factory が無いモデルは `no_factory` と記録する。
3. **アプリが動くために必要な参照行(ロール、組織、設定)。** 生成器は作らない。アプリ固有の知識なので、プロファイル(§11 の Q2)の領分である。生成器に渡せる引数は、飛ばす表・表ごとの行数・列ごとの定数だけである。

### 3.2 スキーマの読み方

`information_schema` から読むのは**構造だけ**である。表、列(型、長さ、NULL 可、既定値、ENUM/SET の値、生成列、自動採番)、主キー、外部キー、一意索引。データの中身は読まない。

### 3.3 生成の順序と、行数の掛け方

1. 外部キーから、親 → 子の順に並べる(`FkOrder`)。並びは決定的で、同順位は表名順である。
2. **循環**は、サイクル上の外部キーのうち、列が全て NULL 可のものを 1 本だけ切る。切った外部キーは NULL で入れ、全表を入れた後で UPDATE する(整数の主キー同士のときだけ。そうでなければ NULL のまま残し、記録する)。切れる辺が無い循環は、その表を生成せず `fk_cycle` と記録する。循環に依存するだけの表は `parent_not_generated` とする。サイクルに依存するだけの表の辺は切らない(切ると、関係を辿るコードが動かなくなるため)。
3. **自己参照**(NULL 可)は、後からの UPDATE をやめ、同じ INSERT の中で埋める。最初の行は根(NULL)、行 n は行 n DIV 2 の子(木)、一意キーなら行 n-1 の子(鎖)である。親の行が先にあるので、キーの型に依らず埋まる。
4. 規模は `ScalePlan` が決める(§4)。外部キーの値は決定的に割り当てる。行 i は、親の行 `((i-1) mod 親の行数) + 1` を指す。乱数を使わないので、同じ入力から同じ行ができる。子を M 倍にした表は、親 1 行あたりちょうど M 行になる。
5. 一意制約のある外部キー(1 対 1)と、外部キーだけでできた複合の一意キー(pivot)では、親の行数を子の行数以上に引き上げ、親の行を数字の桁のように順に回して、組が重ならないようにする。
6. 表ごとに 1 つのトランザクションで入れ、1,000 行ずつの多行 INSERT にする。入れた後に `COUNT(*)` が計画どおりかを確かめ、ずれたら巻き戻して `count_mismatch` と記録する。自動採番の主キーは INSERT から省き(DB に任せる)、入れた後に最小値と最大値が 1..行数であることを確かめる(外部キーの値がこの前提に立つため)。ずれたら `autoinc_gap` とする。

migration が最初から入れている行(Koel のロールや権限など)は、触らず、基準として数える(`existing`)。計画の行数は「ツールが生成する行」であり、自動採番の親を指す外部キーは、その既存の行の後ろの id を指す。

### 3.4 列ごとの値

値は(表、列、行番号)だけで決まる。

| 列の型・性質 | 値 |
| --- | --- |
| 自動採番の主キー | 省略(DB に任せる) |
| 外部キー | §3.3 の割り当て。NULL 可の列でも、原則は親を指す(関係を辿るコードを動かすため) |
| `varchar`/`char`/`text` | `{表}_{列}_{行番号}` を長さで切る。**一意の列では行番号を必ず残す**(前を切る)。36 文字の列は UUID の形。名前に `mail` を含む列は `example.test` のアドレス |
| 整数・小数・浮動小数 | 行番号(範囲を超えたら巻き戻す)。小数は桁数を守り、`.5` を付ける。一意の列は行番号そのまま |
| 日付・日時 | 基準日(2026-01-01)+日数。TIMESTAMP の範囲(2038 年)を超えないよう周回する。一意の日時は 1 秒刻み |
| `created_at`・`updated_at`・`deleted_at` | 基準日・基準日・NULL(NULL 不可なら基準日) |
| 真偽(`tinyint(1)`) | 0 と 1 を交互に。権限や非表示を表す名前(`admin`・`super*`・`deleted`・`archived`・`banned`・`disabled`・`inactive`・`blocked`・`suspended`)の列は常に 0 |
| `enum`/`set` | 値を順に回す。ただし、行を隠してしまう名前の値(`deleted`・`banned`・`archived`・`disabled`・`inactive`)は除く。全てがそうなら全値を使う |
| `json` | `{}` |
| `blob`/`binary` | 短い固定の ASCII 列(長さを守る) |
| NOT NULL で既定値あり、NULL 可で非 NULL の既定値あり | 省略(DB の既定値が意図した値)。ただし一意の列と外部キーは必ず入れる |
| 生成列 | 省略(DB が計算する) |
| 空間型・`bit`・未知の型 | NULL 可または既定値ありなら省略。必須なら**表ごと失敗**(`unsupported_type`)として、入れない |

CHECK 制約は解析しない。挿入が拒否されたら、その表を `check_constraint` とし、エラー文の先頭 200 字を記録する。

### 3.5 失敗の記録

失敗は黙らせず、理由コードで全表に残す。語彙は固定で、`fk_cycle`・`unsupported_type`・`check_constraint`・`unique_violation`・`fk_violation`・`not_null_violation`・`no_default`・`data_too_long`・`out_of_range`・`insert_error`・`parent_not_generated`・`count_mismatch`・`autoinc_gap`・`faker_missing`・`no_factory`・`factory_error` である。意図して飛ばした表は失敗に数えず、`framework_table`(`migrations`・`jobs` など)と `profile_skip` で記録する。

### 3.6 確かめたこと

- 検証用アプリ(5 表)で、計画どおりの行数になる(`COUNT(*)` を実 MySQL で確認)。M 軸で各親ちょうど M 件、1 対 1 の一意キー、N=0、同じ入力から同じ行(チェックサム一致)も確かめた。
- 実 MySQL で、全ての型、CHECK 制約、FK サイクル、自己参照、複合キーの pivot を確かめた。`check_constraint`・`unsupported_type`・`unique_violation`・`fk_cycle`・`parent_not_generated` は実際に出る。
- **Koel の生成成功率(表単位): 41/41 表**(失敗 0)。Koel の migration 131 本を計測用 DB で流すと 45 表になり、`migrations`・`jobs`・`failed_jobs`・`password_resets` の 4 表は意図して飛ばした。N=100 と N=1000 のどちらでも同じである。migration は約 20〜30 秒、生成は 0.3 秒(N=100)・2.6 秒(N=1000)かかった。
  - 成功率は「表を生成できた」割合であり、「ルートが叩ける」割合ではない。
  - Koel の migration は `organizations`・`roles`・`permissions`・`role_has_permissions` に参照行を入れる(1・4・5・9 行)。これは触らず基準として数えた。
  - 外部キーが NULL のまま残ったのは `organizations.owner_id` だけである(`users` との相互サイクルで、キーが整数でないため、後からの UPDATE で埋められない)。
  - 生成が通っても、参照行の中身に頼るルートは叩けない(§11 の Q2)。

## 4. N の決め方

増やす表は、静的解析の出力の `n_table` を候補にし、親 1 行あたりの子の数を振る表(`m_table`、どの表の 1 行あたりかを `m_per` が示す)を第 2 の軸にする。

| 場合 | 計画(`ScalePlan`) | 結果の `scope` |
| --- | --- | --- |
| `n_table` がある | `n_table` の行数を N にし、他の表は小さな基底の行数 B(既定 5)に固定する。同点の候補(`n_table_alternatives`)があれば、それぞれを別々に N として測り、最大の傾きを採る(D17 の最悪ケース採用と同じ向き) | `targeted:<表>` |
| `n_table` と `m_table` がある | 上に加え、N を固定して M を振る第 2 の掃引を行う。`m_table` の行数は、`m_per` の行数の M 倍 | `targeted:<表>` |
| `n_table` が無い(候補なし) | 全ての表を N 行にそろえる(**global スケール**)。参照専用の小さな表は B に固定できる | `global` |
| N=0 | `n_table` を 0 行にする。それに NOT NULL の外部キーで依存する表(連鎖を含む)も 0 行、NULL 可の外部キーで指す表は行を保って NULL にする。空のシステムの応答として、`suspect_empty` の判定に使う(§7.3) | `targeted:<表>` |

候補なしのルートが多数を占める。静的解析の出力で数えると、`n_table` が付くルートは Koel で 66/260(25%)、Laravel.io で 1/97、Snipe-IT で 610/752 である。静的解析が unknown と言ったルートを実測で埋める主力は、global スケールになる。global スケールの結果は「全体のデータ量に対する伸び」であり、N と M を分けないので、O(N×M) とは言わない(§11 の Q4)。

規模の列は、少なくとも 3 点を使う。検証用アプリは期待値を決めたときの 100・1,000・10,000 に合わせ、Koel は 10・100・1,000 とする(時間次第で足す。§11 の Q5)。M 軸は、N を固定して `[3, 30, 300]` のように振る。規模ごとに DB を 1 つ作る(`peak_sim_measure_<run>_<規模>`)。migration の時間(Koel で数十秒)を規模の数だけ払う。

## 5. ルートの叩き方

### 5.1 ルートの地図

静的解析の出力の `routes[]` を地図にし、実行時のルート表(`Route::getRoutes()` から読んだ URI、メソッド、ミドルウェア、引数、`where`、束縛)と突き合わせる。キーは(URI、メソッド)である。叩くのは `kind=controller` のルートだけで、フレームワークやクロージャのルートは数えるだけで叩かない(静的解析と同じ)。

### 5.2 引数(ID)の埋め方

ルートの引数は、計測用 DB に実在する値で埋める。URI の順に、最初に値の出たものを採る(親を先に、子を後に)。

1. 暗黙のモデル束縛: モデルの表の先頭行のルートキー(`slug` など、束縛のフィールドを含む)。親子のスコープ束縛は、親の行を外部キーで指す先頭の子の行。
2. 名前が `id` で終わる(`orderId`・`category_id`): 接頭辞が指す表の先頭行の主キー。
3. `where` 制約: 値の候補があれば最初の候補、なければ制約に合う最初のサンプル。制約に合わない値は使わない。
4. `int` の型宣言: 1。

**選ぶ行は、規模に依らず先頭行**である。先頭行の子の数は M で決まり、N では動かないので、N の掃引では子の数が一定になり、M の掃引でだけ動く。埋まらなかった必須の引数は、引数名と理由を付けて `unfilled_param` と記録する。

### 5.3 ログインする利用者と認可(2 段階)

- 認証が要るかは、ルートのミドルウェア(`auth`・`auth:<guard>`・`verified`・`can:` など)から読む。
- 利用者は、`config('auth.providers.<provider>.model')` のモデルで作る。guard は `auth:<guard>` の名前、無ければ既定とする。ログインは `Auth::guard()->setUser()` で行い、`laravel/sanctum` がアプリ自身の vendor にある場合だけ `actingAs` も使う。**パッケージは足さない。**
- **認可は 2 段階で測る。** 第 1 段は通常の一般利用者(プロファイルが管理者を指定できればそれ)。403 が返ったら、もう 1 回だけ全ての Gate を通す状態で叩き直し、結果に `gate_bypass=true` を付ける。ポリシーのクエリは数えられなくなるので、**別の値**として扱い、静的解析との突き合わせでは参考扱いにする(§11 の Q1)。それでも 403 なら `forbidden_even_bypass`。

### 5.4 リクエストの本文

- GET: クエリ文字列なし(プロファイルが認めたルートだけ、資格情報をクエリに載せる。§0.2)。`Accept: application/json` で叩く。画面を返すルートは `Accept: text/html` でも叩く方針である(Blade の経路を通すため。静的解析は Blade も読むため)。`bin/measure-one` はどちらの `Accept` も送れる。どのルートで両方を叩くかは、全体の入口が決める(§10)。
- 書き込み(POST・PUT・PATCH・DELETE)の本文は、3 回まで試す。
  1. FormRequest があれば、`rules()` から必須の欄だけ値を作る(`required`・`present`・`accepted`)。任意の欄は、検証に落ちる機会が増えるだけで、ルートが流すクエリは増えないと見込んで送らない(**未検証**。任意の項目が通ると増える分岐は在りうる。例: 絞り込み、`exists` の検査、任意の関連の保存)。値の作り方は `string` → `x_{i}`、`integer` → 1、`email` → 合成アドレス、`in:a,b` → 最初の値、`exists:表,列` → その表の先頭行、`unique` → 新しい値、`array` → `[]`、`confirmed` → `_confirmation` も同じ値、`file`/`image` → 偽のアップロードである。
  2. 無ければ空の本文で 1 度叩き、422 が返ったら応答の `errors` のキーから本文を作って再試行する。型は分からないので、文字列 → 整数 → 配列の順に 1 回ずつ試す。
  3. 3 回目も 422 なら `validation_422` と記録する(最後のエラーの先頭 200 字)。
- CSRF は、セッションを開始し、トークンを `X-CSRF-TOKEN` に載せる。419 は `csrf_419`、スロットルの 429 は `rate_limited`。1 計測 1 プロセスなので、キャッシュは毎回空から始まり、通常は起きない。
- リダイレクト(3xx)は追わず、その 1 回の本数を採る。ログイン画面へのリダイレクトは `unauthenticated` と分類する。

### 5.5 1 回の試行の分類

ステータスと例外から、次の語彙のどれかに分類する。叩けなかった理由の内訳は、この語彙の件数表になる。

| 分類 | 意味 |
| --- | --- |
| `ok` | 測れた(2xx・3xx) |
| `unfilled_param` | 引数が埋まらない(どの引数かを記録) |
| `unauthenticated` / `forbidden` / `forbidden_even_bypass` | 401 または認証リダイレクト / 403 / 全 Gate を通しても 403 |
| `not_found` / `method_not_allowed` | 404(引数の行が無い疑い)/ 405 |
| `csrf_419` / `validation_422` / `rate_limited` / `signature_required` | CSRF / 検証 / スロットル / 署名付き URL |
| `exception` | 5xx または例外(例外クラスとメッセージの先頭を記録) |
| `external_call_blocked` | 外部通信を試みた(§9 の条件 1・5) |
| `not_rollbackable` / `app_write_attempt` | 巻き戻せない(§9 の条件 6)/ 対象アプリが `storage` の外へ書こうとした |
| `timeout` | 1 リクエストが上限(20 秒。`pcntl` 拡張が要る)を超えた |
| `client_error` / `unexpected_status` | 上のどれにも当たらない 4xx / 想定外のステータス |

データ側の理由(`data_generation_failed`: 関係する表が生成できなかった、`vendor_missing`: vendor が無い、`file_dependency`: 曲ファイルの実体のような、ファイルに依存するルート)も、同じ表に載せる想定である(集計は全体の入口の仕事。§10)。

## 6. 計測

- **回数:** 1 つの(ルート、規模)につき、新しい PHP プロセスで対象アプリを起動し、3 回叩く。1 回目はウォームアップ(フレームワークの初回コストを払う。判定には使わない)、2 回目はコールド(キャッシュが空で、ログインし直す。**主値**)、3 回目はウォーム(同じプロセスでキャッシュが埋まった状態。副値)である。1 計測 1 プロセスにするのは、静的なキャッシュやシングルトンが計測をまたいで残るのを断つためである(実アプリの調査では、`Setting::$_cache` のような static が N+1 の見落としを生んだ前例がある)。
- **クエリ本数:** `DB::listen` で、その試行の間に流れた `QueryExecuted` を**全接続**で数える(接続名ごとの内訳も残す)。PDO のトランザクション呼び出し(BEGIN・COMMIT・SAVEPOINT)はイベントに出ないので数えない。ツール自身の検査用クエリは別の接続で流し、混ざらないようにする。
- **メモリ:** `memory_reset_peak_usage()` を直前に呼び、直後に `memory_get_peak_usage()` との差を取る。**参考値**であり、静的解析との突き合わせには使わない。
- **データに届いたかの確認(誤判定の防止):** 試行で流れた SQL から `FROM`/`JOIN` の表名を取り、増やした表に 1 つも触れていなければ `untouched_data` とする。応答が空のままに見えるものは `suspect_empty` とする(§7.3)。
- **記録:** 試行ごとに JSON 1 行(ルート、メソッド、規模、軸、試行番号、ステータス、クエリ本数、接続別の本数、触れた表、応答のバイト数、ピークメモリ、`gate_bypass`、分類、詳細)。詳細は先頭 200 字までで、コードの長い引用はしない。

## 7. 判定の規則

### 7.1 傾き(D26 の移植)

系列(規模、本数)の傾きを、**最大の 2 規模の間**の log-log 傾きで取る。

```
傾き = log(max(1, 最大規模の本数) / max(1, 1 つ手前の本数)) / log(最大規模 / 1 つ手前の規模)
```

| 傾き | 判定 |
| --- | --- |
| 0.2 以下 | `measured_O1` |
| 0.5 以上 | `measured_ON`(さらに、各区間の傾きが第 1 区間の傾きの ±10% 以内であること。外れたら `inconclusive`) |
| 0.2 と 0.5 の間 | `inconclusive`(**どちらにも丸めない**) |
| 3 点未満 | 判定しない(`insufficient_points`) |

O(N×M) は、N の掃引と M の掃引の**両方**が `measured_ON` のときだけ言う。片方だけなら `measured_ON`、どちらも平坦なら `measured_O1` とする。

判定の規則は、検証用アプリの期待値を決めたときの `GrowthRules`(`fixtures/laravel-app/tests/Support/GrowthRules.php`)を移植したものである。同じ判定ベクトル(`poc/runtime/tests/vectors/growth.json`)を両方の試験に読ませ、2 つの実装が同じ答えを返すことを縛っている。

### 7.2 どの試行が判定に使われるか

各規模の**コールド**の試行で、分類が `ok` のものだけが判定に使われる。N の軸(または global)の試行が主の掃引、M の軸の試行が第 2 の掃引になる。ウォームアップとウォームは試行の記録に残すが、判定には使わない。主値をコールドにするのは、毎回空のキャッシュから測る(安全の条件 5)ことと、キャッシュの効いた軽い側を採らない(最悪側を採る)ことによる。

### 7.3 実測の O(1) を信用しない場合

実測の O(1) は、偽の安心になりうる。データが 0 件のまま走った、条件分岐が届かなかった、ウォームアップで隠れた、のどれでも、本数は平坦に見える。そのため次の場合は、平坦でも判定を出さず `no_info`(情報なし)とする。

- **`untouched_data`:** 増やした表に、クエリが 1 つも触れなかった。
- **`suspect_empty`:** 本数が平坦で、**最大規模の応答が、N=0(増やした表が空)の応答と同一**だった。データが応答に届いていない。N=0 の応答と**同一のときだけ**とするのは、毎回同じ大きさの画面を返す正当な O(1)(ページネーションなど)を、「判定不能」にしないためである。N=0 を測れなかったときは、本文の大きさが一度も変わらず、空の本文の標準的な大きさに一致するときに限る。

## 8. 結果の出し方

### 8.1 並べ方

ルートごとに、静的解析の判定(`growth`・`lower_bound`・`confidence`)と、実測の判定を並べた表を出す(JSON と Markdown)。実測側の全ての欄に、`scope`(`targeted:<表>` または `global`)・`gate_bypass`・規模の列・測った本数・傾きを載せる。**実測は「この入力で通った経路での実測」と明示する。**

### 8.2 突き合わせ

| 突き合わせ | 意味 |
| --- | --- |
| `agree` | 静的が確定で、実測が同じ |
| `runtime_only` | 静的は unknown で、実測が判定できた |
| `static_stronger` | 静的に下限があり、実測がそれを下回った(下限の過大の疑い) |
| `conflict` | 静的が確定で、実測が食い違う。**最優先で報告する。期待値にも実測にも合わせない** |
| `not_comparable` | 実測が何も決めなかった(`inconclusive`・`no_info`・`not_measured`)。または `gate_bypass` で測ったもので、`conflict` や `static_stronger` になるはずだったもの(別の値なので参考扱い) |

検証用アプリでは、さらに期待値(`fixtures/expected.json`)と並べ、`match`・`mismatch`・`inconclusive`・`no_info`・`not_measured` と、期待値自体が unknown だったルートの `unknown_filled`・`unknown_open` で分ける。

### 8.3 アプリ全体の集計

実アプリ 1 本あたり、次を出す。

1. 叩けたルートの数と割合(分母は controller ルート数)
2. 叩けなかった理由の内訳(§5.5 の語彙の件数表)
3. データ生成が成功した表の割合と、失敗の理由別の件数
4. 叩けたルートの実測の判定の分布(`measured_O1`・`measured_ON`・`measured_ONM`・`inconclusive`・`no_info`)
5. 静的との突き合わせ(静的が確定のルートが実測と合うか、静的が unknown で実測が判定できた数、`static_stronger` の数と代表例)
6. 所要時間と DB の大きさ

生の出力は、リポジトリの外に置く。リポジトリに入れるのは集計(`runtime-poc.md`)だけで、絶対パス・ユーザー名・対象アプリのコードの長い引用は載せない。

## 9. 安全の条件 1〜6 の実装

根拠(実行ログ)は、リポジトリの外の証拠ディレクトリに保存してある。ここには要旨だけを書く。

### 条件 1: 対象アプリのコードはコンテナの中だけ。外部通信は失敗として検知する

- 対象アプリのコードが動くのは、`internal: true` の compose ネットワークにつながった PHP コンテナだけである。DB のコンテナとだけ通信でき、ポートは公開しない。PHP コンテナは `cap_drop: ALL`・`no-new-privileges`・読み取り専用のルート・非 root で動く。
- 起動前の検査(`bin/preflight`)が、ネットワークが `internal` であることをホスト側で確かめ、コンテナの中から、公開名の DNS 解決・公開 IP への TCP 接続(2 か所)・HTTP・既定ゲートウェイが**全て失敗**し、DB サービスへは**接続できる**ことを確かめる。外へ出られるなら**起動を拒否**する(終了コード 11)。
- **拒否の実例:** 外へ出られる通常のネットワークに差し替えた試験専用の compose では、検査が「ネットワークが internal でない」と拒否した(終了コード 11)。
- **失敗の実例:** 封じた環境では、名前解決、公開 IP への TCP、HTTP、curl の 4 つの外部通信が、全て失敗した(外に漏れた試行 0)。アプリ層の `Http` クライアントは、呼ばれたホストを台帳に記録し、接続例外を返す。Guzzle 直・curl・`file_get_contents` は、ネットワーク層で失敗し、例外のメッセージから `external_call_blocked` と分類する。

### 条件 2: 計測用 DB の専用名と、接続先の検査

- DB 名は `peak_sim_measure_` で始まり、ツールが `peak_sim_measure_<run>_<規模>` の形で自分で作る。**外から名前を渡す口は無い。** 作成と削除は `MeasureDb` の 2 つの関数だけが行い、どちらも入口で名前を正規表現で再検査する(DB 名・ホスト・ユーザーの拒否と許可を、表にして試験している)。ツールは、これ以外の DDL を発行しない(DDL は対象アプリの migration が、計測用 DB の中でだけ行う)。
- **機構が先、コードが後。** PHP コンテナに渡す MySQL ユーザーは、`peak_sim_measure_%` の DB にしか権限が無い。ほかの DB の削除・作成、ユーザーの作成は、サーバーが拒否する(実例: `DROP DATABASE app` と `CREATE DATABASE other_db` が 1044、ほかの DB の `SELECT` が 1142、ユーザー作成が 1227)。root の資格情報は PHP コンテナに渡さない。
- コードの検査(2 枚目の関門)は、ホスト名が DB サービスの名前と完全一致すること、ユーザーが `measure` であること、DB 名が正規表現に合うことである。違えば起動を拒否する(終了コード 10)。入力は環境変数だけで、対象アプリの `.env` は値の出どころにならない(実例: `.env` 相当の `DB_HOST=127.0.0.1`・`DB_DATABASE=app` を与えても無視され、接続先は DB サービスの計測用 DB のまま)。
- 起動後に全ての DB 接続を調べ、計測用 DB を指すことを確かめる(§2.1)。
- 終了時に計測用 DB を全て消す。異常終了した場合に備え、同じ検査を通る `bin/cleanup` がある(実例: SIGKILL で落とした後に 2 つ残った DB が `cleanup` で消え、`app` DB は残った)。データ生成器は、書き始める前に `SELECT DATABASE()` が計測用 DB の名前であることを確かめ、違えば何も書かずに拒否する。

### 条件 3: 合成データだけ

§3.1 のとおり。生成器が読むのは `information_schema` の構造だけで、既存の DB・ダンプ・アプリのシーダーは使わない。検証用アプリ(B2)のシーダーだけは、この試作の方針として使ってよいことにしている。D44 に、合成データを読むことが D5 に反しないという判断を記録した。

### 条件 4: 対象アプリのファイルを書き換えない・パッケージを足さない

- 対象アプリは `:ro` でマウントし、コンテナのルートも読み取り専用にする(実例: 書き込みの試みは `/app`・`/peak-sim`・ルートで失敗し、`/tmp` と `/out` だけが成功した)。書き込み先は環境変数と `useStoragePath()` で `/tmp` に逃がす(§2.1)。
- 起動は、ツール側のファイルが `vendor/autoload.php` と `bootstrap/app.php` を読む形(§2.1)で、パッケージは足さない。
- 対象アプリが `storage` の外へ書こうとすると、`:ro` のため例外になり、`app_write_attempt` と分類する(そのルートは測れないと正直に記録する)。

### 条件 5: 副作用は偽物

- `Mail::fake()`・`Notification::fake()`・`Queue::fake()`。キューに積まれたリスナーとジョブは**走らない**ので、その分のクエリは数えない(報告に明記する)。
- `Event` は**差し替えない**(オブザーバとリスナーのクエリも数えるため)。
- `Http::preventStrayRequests()` と、既定で全て失敗する `Http::fake`。呼ばれたホスト名を記録し、接続例外を返す。
- ストレージは、ローカルのディスクを Laravel の fake(作業ディレクトリの下)にし、s3・ftp などの外部ドライバのディスクは、先にローカルに置き換える。
- キャッシュとセッションは `array` ドライバで、1 計測 1 プロセスなので、毎回空のキャッシュから始まる。ブート後に、`array` 以外のストアに解決されていれば起動を拒否する(アプリが config で固定している場合のため)。放送、メール、検索のドライバも `null` や `array` に置き換える。
- 設定で塞げないドライバは、実行時にネットワーク層で失敗し、`external_call_blocked` と分類する。

### 条件 6: 書き込みは 1 回ごとに巻き戻す

- リクエスト 1 回ごと(ウォームアップ・コールド・ウォームのそれぞれ)に、トランザクションを開始して終わりに巻き戻し、回の間にデータを持ち越さない。対象アプリが内部でトランザクションを張る場合は入れ子(SAVEPOINT)になり、外側の巻き戻しで戻る。
- **巻き戻せないものは測らず、記録する(`not_rollbackable`)。** 検知は 3 本ある。(1) 暗黙のコミットを起こす SQL(`ddl`・`lock`・`transaction_control`・`privilege`・`maintenance`・`load_data`・`call`。一時表は除く)。(2) 既定以外の接続への書き込み(`other_connection`)。(3) 試行の前後で全表の行数を比べ、ずれたら汚染とみなす(`row_count_changed`)。
- 汚染を検知したら、その規模の DB を捨てて作り直す。DB は規模ごとに使い捨てなので、被害は 1 規模に限られる。
- 自動採番の進みは巻き戻らない(InnoDB)。主キーの値の連続性は、計測に影響しない前提とする。

### 11.4 実装で増えた判断(採った扱いを書く)

- **ルート読み込み中に `request()` を読むアプリ**(Koel・Snipe-IT)のため、`bootstrap()` の前にリクエストを束縛した。起動の方式に関わるので、本採用でも引き継ぐ(§2.2)。
- **自己参照の外部キー**は、後からの UPDATE でなく、INSERT の中で埋めた(§3.3)。最初の設計(NULL で入れて後から UPDATE)は、文字列のキーを持つ表で埋められず、Koel の初回の実走で、外部キーが NULL のまま残る表が 1 割ほど出たため、実装を正とした。
- **migration が入れた既存の行**は、触らず、数えもせず、基準として記録する(§3.3)。
- **N=0**(増やす表を空にして測る)を計画に加えた。`suspect_empty` を、毎回同じ大きさの正当な O(1) と取り違えないための基準である(§7.3)。
