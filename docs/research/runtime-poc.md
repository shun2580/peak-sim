# 実測モードの試作(runtime PoC)の結果

作成日: 2026-11-02

実測モードの試作(PoC)の結果である。設計は `docs/research/runtime-poc-design.md` に書いた。この文書は、試作を動かして得たものだけを書く。対象アプリを計測用の DB に載せ、件数を変えながらルートを実際に叩き、クエリの本数を数えて増え方を判定した結果である。

**これは試作の結果であり、実測モードの本採用ではない。** 試作のコードは `poc/runtime/` にあり、公式の CLI にも phar にも入っていない。

節の構成は、目的と読み方(§1)・検証用アプリの 24 ルート、シーダー方式(§2)・生成器方式(§3)・実アプリ(§4)・本採用の判断材料(§5)・安全の条件の根拠(§6)である。**この版に書いてあるのは §1〜§6 である。** 実アプリ(§4)は 4 構成で測り、4 つ目は利用者に寄せたプロファイルでの再測定である(§4.1・§5.1.1)。

## 1. 目的と読み方

### 1.1 目的

静的解析は「コードが何をしうるか」を読む。実測は「この入力で、実際にどの経路を通り、何本のクエリを流したか」を数える。両方を並べて、次の 3 点を調べる(設計メモ §0.1)。

1. 静的解析が確定と言ったルートを、実測も同じ判定にするか(食い違いは最優先の発見である)
2. 静的解析が unknown と言ったルートのうち、実測が判定できる割合
3. 実アプリで、自動で叩けるルートの割合と、叩けない理由の内訳

この版の §2 は、1 と 2 を検証用アプリ(`fixtures/laravel-app`)の 24 ルートで調べた結果である。3 は実アプリで調べるもので、§4 に書く。

### 1.2 読み方の注意

- **試作であって、本採用ではない。** ここに書く数字は、試作が動いたこと、そして試作の範囲で何が言えるかを示す。ツールの機能として約束するものではない。
- **実測の言い切りは「この入力で通った経路での実測」だけである。** 実測の判定は静的解析の判定と語を分け(`measured_O1`・`measured_ON`・`measured_ONM`・`inconclusive`・`no_info`・`not_measured`)、どの表をどう増やして測ったか(scope)を付けて出す。`measured_O1` を「O(1)」と読み替えない。
- **実測の `unknown` の扱い。** 静的解析が unknown と言ったルートを実測が判定した場合、それは「この入力で通った経路は O(1) だった(または O(N) だった)」であって、「そのルートの全ての経路が」ではない。静的解析の unknown を実測が `measured_*` で埋めたものは、分類で `runtime_only` と呼び、確定した判定とは別の枠で扱う(§2.4)。
- **実測は静的の確定を上書きしない。** D21(「分からない」を「安全」にしない)は崩さない。静的が確定と言い、実測が食い違った場合は、期待値にも実測にも合わせず、そのまま `conflict` として報告する。この試作では 0 件だった(§2.3)。
- **データに届いていない実測は、平坦に見えても「情報なし」とする**(`no_info`)。応答が空の系と同じ大きさのままなら、本数が変わらなくても O(1) とは言わない(設計メモ §7.3)。
- **「24 ルートで一致した」は、ツール全体の実証ではない。** 24 本の性質は §2.5 に書いた。

## 2. B2a: 検証用アプリの 24 ルート(シーダー方式)

### 2.1 方法

検証用アプリ(Laravel 13.39.0)の 24 ルートを、**アプリ自身のシーダー**で入れたデータで実測し、静的解析の出力と、`fixtures/expected.json` の期待値に並べた。

### 2.4 別枠: 静的が分からないと言ったルートを、実測がどこまで埋めたか

次の 2 ルートは、静的解析が「分からない」または「最悪のケースを採った」ルートである。実測が埋めたのは**既定の経路だけ**で、そこから先は言えない。

#### `/unknown/dynamic`(静的: unknown)

- 実測は **measured_O1**(`scope: global`、本数 1/1/1。空の系でも 1)だった。静的が unknown としたものを、実測が判定した(`runtime_only`)。
- **言えるのは「既定の経路」だけである。** ツールはクエリ文字列を付けずに 1 回叩く。このルートは `?method=` で呼ぶメソッドを選び、既定は `summary`(`Order::count()` の 1 本)である。もう一方の `latest`(`limit(10)`)は叩いていない。コードを読むと `latest` も 1 本だが、それはツールの実測ではなく、読んだ結果である。したがって「動的呼び出しの全分岐が O(1)」とは言わない。
- 偽の O(1) の防止は働いた。触れた表は orders で、応答本体のバイト数は規模で変わる(`{"orders":N}`)ため、`untouched_data` にも `suspect_empty` にもならなかった。

#### `/hidden/conditional-binding`(静的: O(N)、最悪ケース採用)

- 実測は **measured_ON**(101/1001/10001、傾き 0.9996)で、静的の最悪ケース採用の O(N) と一致した。
- **これは「production でない側」を測っただけである。** この束縛は、`environment('production')` のときは先読み(eager loading)の実装、それ以外では N+1 の実装に切り替わる。ツールは `APP_ENV=local` で動かすので、N+1 の側が走った。production 側(先読み。O(1) の見込み)は測っていない。
- 実測が確かめたのは「最悪ケースの採用が、実在する経路だ」ということまでである。「このアプリの本番での挙動」は言えない。ツールが環境を変えて 2 回測る案は未実装で、本採用の判断材料になる(§5)。

#### 参考: `/hidden/cache`(期待の `query` は null)

- コールド(キャッシュ空)の本数は 101/1001/10001 で O(N)。期待の `query_on_miss: O(N)` と一致した。
- ウォーム(2 回目)は 0/0/0 で、`query_on_hit: O(1)` と整合する(ヒットでは DB に行かない)。判定の主はコールドである。

### 2.5 限界

次の限界は、この結果を読むときに必ず付ける。

1. **実測の範囲は「この入力・この経路」である。** ツールは `APP_ENV=local`・クエリ文字列なし・必須項目だけの本体・`Accept: application/json` で叩く。**クエリ文字列なしには 1 つだけ例外がある:** アプリのプロファイルが認めたルート(実アプリの Subsonic 互換 API。§4)では、ルート自身の認証を通すため、GET のクエリ文字列に資格情報を載せる。載せるのは、その走の合成の鍵から導いた値だけで、ページ番号や絞り込みは指定しない。検証用アプリの 24 本には、この例外は無い。環境・クエリ文字列・任意項目・HTML の画面で分岐する経路は測っていない。§2.4 の 2 ルートが、その実例である。
2. **既定の経路だけが埋まった。** `/unknown/dynamic` は既定の分岐(`summary`)だけ、`/hidden/conditional-binding` は `APP_ENV=local` の側だけである。静的が分からないと言ったルートを、実測が全経路について埋めたわけではない。
3. **検証用アプリの 24 本は、GET のみ・認証なし・パラメーターなしである。** したがって、引数の埋め(ArgumentResolver)・ログイン利用者の用意(UserProvider)・POST などの本体の生成(BodyBuilder)・巻き戻しの汚染からの再構築は、**24 ルートの実測では通っていない**。これらは、単体試験と、封じたコンテナの中の試験(プローブ用に複製したアプリで、DDL・commit・403・401・404・500 を返すルートを使う)でだけ確かめた。実アプリで初めて、実測の経路として通る(§4 で扱う)。パラメーター付きルートの検出と、scoped binding の外部キーの推定も、実アプリのルートに当てた試験がまだ無い。**「24 本とも一致」を、ツール全体が正しいことの証拠として読まないこと。**
4. **書き込みを持つルートは 3 本ある**(`/ok/bulk`・`/ng/save-in-loop`・`/ng/first-or-create-in-loop`)。巻き戻しは働き、汚染(行数のずれ)は 0 だった。ただし DDL や別接続を使うルートは、この 24 本には無い(巻き戻せないものは測らず記録する規則は、プローブ用の複製アプリの試験でだけ確かめた)。
5. **ピークメモリは参考値である。** 100 → 10,000 の倍率は、`/ok/paginate`・`/ok/chunk`・`/ok/lazy`・`/unknown/dynamic` が 1.0、`/hidden/cursor` が 10.5、その他は 70〜95 倍(N の 100 倍に対してほぼ線形)だった。判定には使っていない。
6. **`ShouldQueue` のリスナーは、キューに積まれるだけで走らない**(Queue は偽物)。この 24 本には該当するルートが無い。

### 2.6 20 秒の上限で `/ng/nested` が一度測れなかった経緯

最初の最終走(commit `3464a34`、リクエストの上限は既定の 20 秒)で、`/ng/nested` の N=10,000 が約 4 万本のクエリを要して 20 秒を超えた。ウォームアップが `exception(the request ran longer than 20 seconds)` となり、残った点が 100 と 1,000 の 2 つだけになって、このルートは `not_measured(insufficient_points)` になった。

- **原因は、実装の欠陥でも判定規則でもなく、時間の上限である。** 同じ上限で通った開発中の通し走があり、時間の余裕が薄い境界だったと考えている。当時は他の処理が同じ機械で動いていた可能性があるが、負荷は測っていない。
- 対応は 2 つ。(a) 上限を `--request-timeout`(1〜60 秒)で変えられるようにした。最終走は 60 秒で行い、使った値は走ごとに `summary.json` の `request_time_limit_seconds` に書かれる。(b) 点が足りずに判定できないとき、その行の分類を `ok` のままにせず、落ちた規模と理由(`scale 10000 (axis N): … ran longer than 20 seconds`)を出すようにした(`d68a88b`)。
- 最初の走の記録は、教訓として手元に残してある。上の表は 60 秒で再走した結果である。

この経緯が示すとおり、**クエリを数万本流すルートは、既定の上限に近づく。** 上限に当たったルートは `not_measured` として理由つきで残り、O(N) とも O(1) とも言わない。

### 2.7 食い違いの切り分け

シーダー方式の本番走で、`conflict`・`mismatch`・`static_stronger` は 0 件だったので、切り分けるものは無い。

## 3. B2b: 検証用アプリの 24 ルート(生成器方式)

シーダー方式(§2)は、アプリ自身が用意したシーダーに頼る。アプリのシーダーは、アプリごとに行数も中身も違い、規模を変えられるとは限らない。そこで、アプリのシーダーを使わず、ツールが表の定義から合成データを作る**生成器方式**(`--data=generator`)でも、同じ 24 ルートを測った。この節は、生成器がシーダーと同じ判定を出すか、違うなら原因は何かを調べた結果である(設計メモ §0.1 の目的 1・2 に当たる)。

### 3.1 方法

§2.1 と同じ条件(同じ検証用アプリ・封じたコンテナ・規模の列・M 軸・測り方・リクエストの上限 60 秒)で、データの作り方だけを変えた。生成器は、規模ごとに新しい DB を作り、増やす表の行数を計画どおりにして、そのほかの表には基底の行を入れる(基底行は `--base` で変える。既定は 5)。

**次の 2 通りを、別々に走らせた。**

| 走 | 指定 | 測った commit | 所要 | 終了 |
| --- | --- | --- | --- | --- |
| (a) プロファイル無し | `--data=generator` | `d68a88b` | 326 秒 | 0 |
| (b) プロファイル有り | `--data=generator --profile=fixtures` | `1af9767` | 339 秒 | 0 |

- **プロファイル**は、アプリ固有の知識を人が足すための小さなファイルである。生成器は文字列の列に `orders_status_<i>` のような値を入れるので、`status = 'paid'` で絞るコードには一致する行が届かない。プロファイルはそうした列の値を与える。使ったもの(`profiles/fixtures.php`)は **`values` の 1 項目だけ、`orders.status = 'paid'`** である。**`skip`(表を作らない指定)も `rows`(行数の指定)も与えていない。** データを期待に寄せるための調整はしていない。
- (a) と (b) は commit が違う。`1af9767` が足したのは `--profile` の配線(と `profiles/fixtures.php`)だけで、`--profile` を付けない経路は変えていない。使ったプロファイルの名前は、`summary.json` の `meta.profile` に残る((b) は `fixtures`、(a) は `profile` のキー自体が無い)。読む人が `summary.json` を開かなくても分かるように、`report.md`・`comparison.md` の見出し行にも `profile: fixtures` または `profile: none` が出て、`routes.jsonl` の各 `statement` の末尾には、プロファイルがあるときだけ `(with profile: fixtures)` が付く(プロファイルが判定に関わらないルートにも付く。安全側の表示である)。

- 2 つの走とも、起動前の検査(preflight)を通り、終了後に残った計測用 DB 0・コンテナ 0 だった。生成に失敗した表は、どちらの走でも 0 件だった。

### 3.4 差が出た 2 ルートの切り分け

差の原因は、データ・N の選び方・判定規則・実装のどれか、という順で切り分けた。2 ルートとも、N の選び方(同じ 100 / 1,000 / 10,000)・判定規則・実装(`--profile` の配線を除く)は 3 系統で同一であり、変わったのは**データ**だけである。

#### `/ng/collection-filter`: 生成器・無しは `no_info`、有りは `measured_O1`

- コードは `Order::get()->where('status', 'paid')`(クエリ 1 本で全件を取り、PHP 側で絞る)。
- **(a) 無し:** 生成器が入れる `status` の値は `paid` に一致しないので、応答は全規模で `[]`、**2 バイト**のままだった。これは空の系(N=0)の応答と同じ大きさである。本数は 1/1/1 で平らだが、ツールは「データが応答に届いていない」と見て、**`no_info`(理由 `suspect_empty`)**とし、O(1) とは言わなかった。静的は O(1) なので、静的 vs 実測は `not_comparable` になった。**これは偽の O(1) を止めた実例である。** 平らな本数だけで O(1) と言っていれば、データが一度も届いていない系を「O(1) だ」と言い切るところだった(D21 を守る側に働いた)。
- **(b) 有り:** プロファイルで `orders.status = 'paid'` を与えると、応答は **14,383 / 144,794 / 1,457,895 バイト**と規模に応じて増え(空の系は 2 バイトのまま)、本数 1/1/1 の `measured_O1` になり、静的と `agree` した。シーダーの応答(4,982 / 49,248 / 494,899 バイト。`paid` を含む)と同じく、「データが届いた上での O(1)」である。
- **言えることと言えないこと。**
  - (a) の `no_info` は正しい挙動である。ツールは `paid` という値を知らない。それは欠陥ではなく、アプリ固有の知識の不足である。
  - **(b) の O(1) は、「人が `paid` を与えた条件つき」の O(1) である。** `status` が `paid` の行が全件にある入力で、というものであって、ツールが `paid` を推定したのではない。プロファイルを足したから判定が出たのであり、足さなくても出る、という意味ではない。
  - **`no_info` の件数は、アプリ固有の知識の不足量の目安になる。** (a) の `no_info` は 1 件だった。実アプリでは、値に依存する絞り込みが多いほど、プロファイル無しで `no_info` が増えると見込まれる。これは見込みであり、実アプリでの件数は §4 で測る。

#### `/ng/first-or-create-in-loop`: 本数が一律 5 ずれるだけで、判定は同じ

- 本数は、(a)(b) とも **196 / 1,996 / 19,996** で、シーダーの 201 / 2,001 / 20,001 より、どの規模でも **5 だけ少ない**。判定は 3 系統とも `measured_ON` である(傾きは、シーダー 0.9998・生成器 1.0008 で、どちらもほぼ 1)。
- 原因は**基底行**である。コードは全商品を回して `firstOrCreate` を呼ぶ(行が無ければ SELECT と INSERT の 2 本、有れば SELECT の 1 本)。生成器は `product_stats` に基底の 5 行を先に入れるので、最初の 5 商品は「既にあった」(1 本)になり、2 本の場合より 1 本ずつ少ない。シーダーは意図して `product_stats` を空にする。
- **切り分けの確認として、`--base=1`(基底行を 1)にして、このルートだけを測り直した。** 本数は **200 / 2,000 / 20,000** になり、判定は `measured_ON`(傾き 1)のままだった。基底行を 5 から 1 に減らすと、差が 5 から 1 に減った(201 − 1 = 200)。**差が基底行の数に比例する**ので、原因はデータの基底行で確定する。N の選び方・判定規則・実装ではない。
- この差は (a)(b) で同じで、プロファイルとは関係が無い(プロファイルは `product_stats` に触れていない)。期待値(O(N))とは、判定が一致している。

### 3.5 この節が言えることと限界

- **言えること:** 検証用アプリの 24 ルートについて、生成器方式の判定は、(プロファイル有りで)シーダー方式と 24 本すべて一致した。プロファイル無しでは、アプリ固有の値に依存する 1 本が `no_info` になり、偽の O(1) は出なかった。生成器が O(1) を偽って言った例は無い。`conflict`・`mismatch`・`static_stronger` は 3 系統とも 0 件で、見逃しも過検知も無かった。
- **言えないこと:** 生成器が、実アプリのデータの形(値の分布・外部キーの偏り・NULL の割合)を再現するとは言えない。24 本は、生成器に有利な単純な表の形である。
- **§2.5 の限界はそのまま当てはまる。** 24 本は GET のみ・認証なし・パラメーターなしで、引数の埋め・ログイン利用者の用意・本体の生成・巻き戻しの汚染からの再構築は、この 3 系統の実測でも通っていない。実アプリで初めて通る(§4)。
- **`--profile` の試験:** 配線は、(b) と `--base=1` の 2 回の実走で確かめた。加えて、Docker の中の試験(`poc/runtime/tests/Docker/MeasureDriverDockerTest.php` の `testAProfileMakesTheFilterRouteSeeItsDataAndIsNamedInTheRecord`)が、`/ng/collection-filter` をプロファイル無しと有りで走らせ、無しは `no_info`・有りは `measured_O1` になること、`report.md` の `profile:` の行と `statement` の末尾の表示、`summary.json` の `meta.profile`、終了後に計測用 DB とコンテナが残らないことを確かめる。

## 4. B3: 実アプリ(Koel)

実アプリ 1 本(Koel。Laravel 製の音楽サーバー)を、シーダー方式でなく**生成器方式**で測った。検証用アプリの 24 本と違い、認証・パラメーター・本文・外部サービス・アプリ固有の参照行があり、§2.5 で「実アプリで初めて通る」と書いた部品(引数の埋め・ログイン利用者の用意・本体の生成・巻き戻しの汚染からの再構築)がここで通った。

**この節の数字は、1 つのアプリ(Koel)を、規模 10・100・1,000 で測ったものである。** 10,000 は足していない(時間。§4.7)。一般化はしない。

### 4.1 方法

| 項目 | 内容 |
| --- | --- |
| 対象 | Koel(commit `da0e70f`。Laravel 13.37・PHP 8.3.36)。読み取り専用でマウント。実行の前後で、Koel の `git status` は空 |
| 静的解析の入力 | 同じ対象に対する `peak-sim analyze` の出力(スキーマ 0.2)。**260 ルート**(ルート × HTTP メソッドの行) |
| データ | 生成器方式(`--data=generator`)。Koel のシーダーは走らせない。規模 0(空の系)・10・100・1,000 と、増やす表を変えた組み合わせで、DB を 22 通り作る(規模 0 は応答の同一判定にだけ使う) |
| 規模の列 | N 軸 10・100・1,000(B2 と違い 10,000 は無い)。M 軸 3・30・300 |
| リクエストの上限 | 60 秒。上限に達した要求は無かった |
| 測り方 | §2.1 と同じ(1 計測 = 1 プロセス、コールドが主値、リクエストごとにトランザクションで巻き戻す) |

**母数の 260 と、262・270 について。** Koel が実行時に登録するルートは 270 本で、うち 10 本はコントローラーでない(クロージャやフレームワークのルート)。静的解析も実測も対象にしない。コントローラーのルートが 260 本で、この節の分母はすべて 260 である。途中で 262 と書いた測定仕様があったが、それは除外の定義の違いで、今回の記録は 260 行で統一した。

**構成。** 次の 4 構成を、同じ 260 ルートに当てた。

| 構成 | プロファイル | 403 のときの扱い |
| --- | --- | --- |
| ① | 無し | そのまま(素通しなし) |
| ② | Koel 用のプロファイルあり(§5.3) | そのまま(素通しなし) |
| ③ | ②と同じ | 403 のとき、全ての Gate を通す第 2 段で 1 回だけ再試行する(`gate_bypass`。設計メモ Q1) |
| ④ | 利用者に寄せたプロファイル(`koel_userbound`。③のプロファイルに、生成した行をログインした利用者に寄せる手当てを足したもの。§5.1.1) | ③と同じ(素通しあり) |

②には、あとから 3 つの**後追い**を足した。後追いは、②で叩けなかったルートだけを、直したコードで測り直したものである。

| 後追い | 内容 | 再測定したもの |
| --- | --- | --- |
| a | Subsonic 互換 API の 51 本に、クエリ文字列で資格情報を運べるようにして叩く | Subsonic 51 本 |
| b | 26 文字の鍵の列に正しい ULID を生成する(`HasUlids` のモデルは不正な鍵の形を、行を探す前に 404 にする)。重複アップロードの `storage` の値を、アプリが読める形にする | 404 または例外だった 40 URI(65 ルート) |
| c | 第 1 段のログインを管理者にして(プロファイルの変種。`login_as: admin`)、403 だった 9 URI を測り直す | 403 だった 9 URI(38 ルート) |

「② + 後追い」は、②の基本の走に a〜c の結果を重ねたものである。

**①・②・③は同じコミット(`95bf12a`)のコードで測った。後追いと④だけが別のコードである**(a は `15b5428`、b と c は `9720031`、④は `90fe961`。`90fe961` は `95bf12a` の子孫で、a・b の修正と、④のプロファイルを含む)。①②の基本の走と③の使用コミットは、それぞれの実行記録で確かめた。比較は「構成の違い」を主に読み、後追いの分は別の行にした(後追いは、そのあとに足した修正を含むコードで測っている)。④は③と同じ範囲(260 ルート・規模 10・100・1,000・素通しあり)だが、**コードとプロファイルの両方が違う**ので、③との差は「プロファイルの差」だけとは言えない(§5.1.1)。①〜③は同じ機械で 2〜4 本を同時に走らせたので、時間の比較は目安である。④を走らせたときの同時の本数は確かめていない。

### 4.2 叩けた数と割合

「叩けた」とは、**応答が 2xx または 3xx で、外部通信の遮断が起きず、巻き戻しの問題が無かった試行**(class `ok`)をいう。**応答が意味を持つかどうかは別の問い**である(§4.5・§5.1)。推測で作った引数への 404 は、叩けた扱いにしていない(今回の走で該当は 1 件)。

| 構成 | 走 | 2xx が返った / 260 | 割合 |
| --- | --- | ---: | ---: |
| ① プロファイル無し・素通しなし | 基本 | 93 | 35.8% |
| ② プロファイルあり・素通しなし | 基本 | 53 | 20.4% |
| ② + 後追い a〜c | 基本に重ねた | **120** | **46.2%** |
| ③ プロファイルあり・素通しあり | 基本 | 55 | 21.2% |
| ④ 利用者に寄せたプロファイル・素通しあり | 基本 | 119 | 45.8% |

「② + 後追い」と④については、**2xx が返っただけの数と、アプリの処理に届いた数を並べて読む**。

| | ② + 後追い a〜c | | ④ | |
| --- | ---: | ---: | ---: | ---: |
| | 本数 / 260 | 割合 | 本数 / 260 | 割合 |
| (1) 2xx が返った | 120 | 46.2% | 119 | 45.8% |
| (2) 処理に届いた可能性がある(上限。処理に届かないと確定した分だけを引く) | 92 | 35.4% | 91 | 35.0% |
| (3) 認証以外の表を読んだ(処理がデータの表に届いた証拠がある) | 68 | 26.2% | 67 | 25.8% |

**この割合は「2xx が返った」割合であり、「規模のデータが応答に届いた」割合ではない。単独の 46.2%(④では 45.8%)を、自動で測れた割合として読まないこと。**

④の (1)〜(3) は、②+後追いと同じ基準で数えた。④で 2xx が返った 119 本は、Subsonic 51 本と非 Subsonic 68 本である。Subsonic の 51 本は、②+後追いと同じ内訳になる(必須入力が足りず処理に届かないとコードから確定した 28 本・処理には届くが認証の表だけを読む 8 本・認証以外の表を読む 15 本)ので、(2) は 119 − 28 = 91 である。非 Subsonic の 68 本は、最初の試行で認証・基盤以外の表を読んだものが 52 本、認証・基盤の表だけのものが 16 本で、(3) は Subsonic の 15 本と合わせて 67 本である。②+後追いより (1) が 1 本、(2) が 1 本、(3) が 1 本少ないのは、非 Subsonic の 69 本が 68 本になった差による。この差の原因は調べていない。**④の 2xx は、③(55 本)から約 2 倍に増えたが、その大半は範囲の差である**(③で叩かなかった Subsonic 51 本を、④は叩いた。非 Subsonic は 55 → 68 本)。

- **(2) の 92 は上限であって、下限ではない。** 120 本のうち、アプリの処理に届いていないとコードから確定したのは **Subsonic の 28 本**で、これだけを引いた(120 − 28)。Subsonic の操作の多くは必須の入力(`id`・`type`・`name` など)を持つが、ツールは認証の 2 項目(`u` と `apiKey`)しか送らないため、検証の例外が HTTP 200 のエラーの封筒になる(§5.1)。非 Subsonic の 69 本は、処理に届いたかをコードで点検していないので、引いていない。
- **(3) の 68 は、処理がデータの表を読んだ証拠がある数**である。1 回目の試行(キャッシュが効く前)の SQL が、認証・基盤以外の表を読んだルートを数えた。内訳は、Subsonic の 15 本と非 Subsonic の 53 本。(2) の 92 との差 24 本は、Subsonic で処理には届くが認証の表しか読まない 8 本(`ping`・`getLicense` など)と、非 Subsonic で認証・基盤の表しか読まない 16 本である。
- **表を読んだことは、増やした行が応答に届いたことでもない。** 応答が規模で増えたと確かめられたのは 9 本である(§5.1)。

**①が②の基本より多い理由。** ②は Subsonic の 51 本を、プロファイルの宣言で「叩かない」とした(その時点では資格情報をクエリで運べなかった)。①はプロファイルが無いので叩き、**認証が通らない HTTP 200(Subsonic のエラーの封筒)を、51 本とも「叩けた」と数えた**。51 本とも `no_info`(`untouched_data`)になり、偽の O(1) にはならなかった(§4.5)。①の 93 本のうち、意味のある実測(`measured_O1`)は 17 本だけである。

**叩けた率と、データ生成の成功率は別の指標である。** 生成は表単位で 100%(§4.4)だが、叩けた率は 46.2% にとどまる。データを作れても、必須項目の検証(422)・404・外部通信・ファイル依存で叩けない。

### 4.6 実害が出た 3 件(生成したデータが、アプリの意味に合っていなかった)

どれも「アプリは動くが、応答にデータが届かない」型で、プロファイルが直した。直さなければ、偽の O(1) になっていた。

1. **曲の一覧が空になった。** 生成器が `songs.podcast_id` に値を入れるので、全曲がポッドキャストの回として扱われ、`GET /api/songs` が空の一覧を返した。プロファイルの後処理で `podcast_id` を NULL に戻した。
2. **`GET /api/data` が 500 になった。** 生成器は `queue_states.song_ids` に文字列を入れるが、アプリはこの列を曲 ID の JSON の配列として読む。プロファイルで `'[]'` を指定した。
3. **自分のプレイリストが空になった。** アプリは利用者のプレイリストを `playlist_user.role = 'owner'` で引くが、生成器は列に別の文字列を入れた。プロファイルで `'owner'` を指定した。

**アルバム: 仕組みの限界と、案 (a) の結果。**

### 5.2 管理者ログインと素通しの扱い

403 のときの扱いは 2 通りある。

- **素通し(`gate_bypass`)。** 403 になったら、全ての Gate を通して 1 回だけ再試行する。通れば測れるが、**ポリシーのクエリを数えない**ので、測った本数が実際より少なくなり、偽の O(1) を隠す側に働く。
- **管理者ログイン(`login_as: admin`)。** 最初から管理者でログインする。ポリシーのクエリも数えるので、測定の意味が保たれる。

管理者ログインを素通しより優先するのがよい。ただし、**既定にはしない**。管理者の視点で叩くと、一般利用者の視点の経路(自分のものだけを引く経路など)が見えなくなる。**一般利用者の走と管理者の走を重ねる**のが、この試作で採った手順である。

1. 一般利用者の走で、全ルートを測る(素通しなし)。
2. 403 だったルートだけを、管理者の走で測り直す(プロファイルの変種で `login_as: admin`)。
3. ルートごとに、一般利用者の結果を主とし、403 だった分だけ管理者の結果で埋める。素通しで通った分は、`gate_bypass` を付けた別の値として残す。

実績: 手順 2 で、403 だった 9 URI のうち 4 本が通った(§4.5)。この変種(管理者でログインするプロファイル)は `poc/runtime/profiles/koel_admin.php` にある(後追い c は、同じ内容の作業用の変種で測った)。

### 5.4 判定器の弱点と、改善案(提案。実装していない)

**弱点。** 判定器が `no_info` に落とすのは、次の 2 つである。

- `untouched_data`: 増やした表を一度も読まない。
- `suspect_empty`: 応答が、増やす表を空にした系(規模 0)の応答と同じ大きさのまま。

したがって、次には効かない。

- **読んだが、規模と無関係な少数の行しか返らない**(§5.1 の「一覧なのに一定」)。表を読み、規模 0 の応答より大きいので、どちらにも当たらない。
- **エラーの封筒**(§5.1 の Subsonic の 24 本)。200 で、規模 0 の系が無い(`global` の走)か、あっても大きさが違う。
- **ページネーションの封筒だけの空**。①の `GET /api/songs` は、曲 0 件の空のページ(284 バイト)が全規模で同じで、`measured_O1` になった。`global` の走には規模 0 の系が無く、`suspect_empty` が拾えなかった。同じルートを②(プロファイルあり)で測ると、データが届いた。

**改善案(3 本。すべて提案で、実装していない)。** いずれも、判定を `no_info` または `not_measured` に**倒す向き**であり、D21 を緩めない。24 ルートの期待値(24/0/0)は変えない。

1. **応答の要素数の記録(`response_flat`)。** 試行の記録は、いまバイト数しか持たない。応答の要素数(一覧なら `data` 配列の長さ)を記録し、増やした表を読んだのに要素数が全規模で同一で、かつ基準の規模より大きく空でもない場合は、`measured_O1` でなく `no_info`(理由 `response_flat`)とする。バイトだけでは、単一のレコードの API が誤って降格する。要素数を持たない形(オブジェクト 1 件)の応答は対象外にする。副作用として、定数の LIMIT やページの上限で正当に有界の一覧(`/api/overview` など)も `no_info` に落ちる。D21 の側に倒れるので許容できるが、「分からない」が増えて見える。実装の前に、「一覧なのに一定」の 22 本を全数追跡して標本調査する。
2. **封筒印の宣言(`app_error_envelope`)。** アプリのプロファイルに、「2xx でも失敗を表す封筒」の見分け方(例: Subsonic のエラー封筒の印)を宣言できるようにし、それに当たる応答は `not_measured` にする。Subsonic の 28 本(`measured_O1` の 24 本と `no_info` の 4 本)のように、処理に届いていない 2xx を `not_measured` にできる。
3. **`global` の走にも規模 0 の系を持たせる。** いまの規模 0 は、増やす表を名指しできる走にだけある。`global` の走にも置けば、空のページの封筒を `suspect_empty` が拾える。

**関連する提案(これも未実装)。**

- `request_query` の値に、生成した行から必須の `id` を埋める書き方を足す。Subsonic の 28 本が、必須の入力(`id` など)を送らずに検証例外の封筒になる(§5.1)ことへの対応。
- プロファイルで、プレイリスト・ラジオ局・購読・組織の行を、ログインした利用者に寄せる(構成④。結果は §5.1.1)。「一覧なのに一定」の 25 本のうち 12 本は、これで応答が増えた。判定器の変更より先にやるほうが安いが、**増えなかった 12 本は、この手当てでは足りなかった**ので、判定器の改善案は不要にならない。

## 6. 安全の条件の根拠

条件 1〜6(設計メモ §9)について、**どう実装したか**と、**効いた実例**を書く。根拠の実行ログは、リポジトリの外の証拠ディレクトリに保存してある。ここでは要旨を書く。Koel の走(7 本。①・②・③と後追い a・b・c、④)は、すべて起動前の検査(`PREFLIGHT OK`)を通った。④の終了後も、残ったコンテナは 0 で、Koel の作業木は読み取り専用のマウントのまま差分が無かった。終了後の確認(計測用 DB の全破棄・コンテナ 0)は、③の走(DB 97 個を作って全て破棄)で行った。

### 6.1 条件 1: 対象アプリのコードはコンテナの中だけ。外部通信は失敗として検知する

- **実装。** 対象アプリのコードは、`internal: true` の compose ネットワークにつながった PHP コンテナだけで動く。DB のコンテナとだけ通信でき、ポートは公開しない。コンテナは `cap_drop: ALL`・`no-new-privileges`・読み取り専用のルート・非 root。起動前の検査(`bin/preflight`)が、ネットワークが `internal` であることを確かめ、コンテナの中から、公開名の DNS 解決・公開 IP への TCP(2 か所)・HTTP・既定ゲートウェイが全て失敗し、DB へは接続できることを確かめる。外へ出られるなら起動を拒否する(終了コード 11)。
- **拒否した実例。** 外へ出られる通常のネットワークに差し替えた試験用の compose では、検査が「ネットワークが internal でない」と拒否した。コンテナの中の検査も、同じ構成で 5 項目(DNS・TCP 2 つ・HTTP・既定ゲートウェイ)が失敗して拒否した。
- **外部通信が失敗した実例。** (a) 封じた環境では、名前解決・公開 IP への TCP・`file_get_contents`・curl の 4 通りの外部通信が全て失敗した(外に漏れた試行 0)。外へ出られる構成を対照として同じ試験を走らせると、4 通りとも漏れた(漏れた試行 4)。(b) **Koel で、実際のアプリが外部サービスを呼んだ。** `GET /api/albums/{album}/information` と `GET /api/artists/{artist}/information` が、それぞれ `coverartarchive.org` と `musicbrainz.org` を呼び、`Could not resolve host` で失敗した。HTTP クライアントのライブラリが `Http` ファサードを通らずに curl で出たが、ネットワーク層で失敗し、`external_call_blocked` と分類した。6 本の走の試行の記録に、`external_call_blocked` が合計 12 件残る。黙って成功させたものは無い。

### 6.2 条件 2: 計測用 DB の専用名と、接続先の検査

- **実装。** DB 名は `peak_sim_measure_` で始まり、ツールが自分で `peak_sim_measure_<run>_<規模>` の形に作る。外から名前を渡す口は無い。作成と削除は 2 つの関数だけが行い、どちらも正規表現で名前を再検査する。**機構が先**で、PHP コンテナに渡す MySQL ユーザーは、`peak_sim_measure_%` の DB にしか権限が無い。root の資格情報は渡さない。コードの検査は、ホスト名が DB サービスの名前と完全一致すること、ユーザーが `measure` であること、DB 名が正規表現に合うことで、違えば起動を拒否する(終了コード 10)。入力は環境変数だけで、対象アプリの `.env` は値の出どころにならない。
- **拒否した実例。** DB 名の拒否: `app`・`peak_sim_measure_`(接頭辞だけ)・`peak_sim_measure_x'; DROP DATABASE app; --` の 3 つの削除を、名前の検査が拒否した。権限の拒否: 計測用ユーザーによる `DROP DATABASE app` と `CREATE DATABASE other_db` が 1044、ほかの DB の `SELECT` が 1142、ユーザー作成が 1227 でサーバーに拒否され、`app` の DB の行は無傷だった。接続先の拒否: ホストが `db.example.com` なら起動を拒否し、ホストが未設定でも拒否した。`.env` 相当の `DB_HOST=127.0.0.1`・`DB_DATABASE=app` を与えても無視され、接続先は DB サービスの計測用 DB のままだった。
- **後始末の実例。** SIGKILL で落とした走が残した 2 つの DB を、`bin/cleanup` が消し、`app` の DB は残った。③の走は、作った 97 個の計測用 DB を全て破棄して終わった。

### 6.3 条件 3: 合成データだけ

- **実装。** データ生成器が読むのは `information_schema` の構造だけで、既存の DB・ダンプ・アプリのシーダーは使わない(Koel のシーダーは走らせていない)。値は規則から決定的に作る。プロファイルが足す行は、**計測用 DB にだけ**書き、DB 名が計測用であることを確かめてから書く。利用者のメールは、実在しない形(`.invalid`)にしている。migration が入れる行(組織 1・役割 4・権限 5 など)は、アプリのコードがスキーマの一部として入れるものであり、基準として数えた。
- **ログイン情報(鍵)の扱い。** Subsonic のために利用者ごとに保存する API キーは、**秘匿値ではなく、合成した値**である。走ごとに違い、その走のアプリのキー(`APP_KEY`)が無ければ推測できない。走の識別子から導出できるが、封じたコンテナの中だけで意味を持つ合成の鍵であり、本物の資格情報とは関係が無い。キーそのものは、プロファイルにも、報告にも、ログにも書かない。

### 6.4 条件 4: 対象アプリのファイルを書き換えない・パッケージを足さない

- **実装。** 対象アプリは `:ro` でマウントし、コンテナのルートも読み取り専用にする。書き込み先は `/tmp` と出力先だけ。ツール側のファイルが対象の `vendor/autoload.php` と `bootstrap/app.php` を読み、プロセスの中で HTTP カーネルを呼ぶ。パッケージは足さない。対象アプリが `storage` の外へ書こうとすると、`:ro` のため例外になり、`app_write_attempt` と分類する。
- **効いた実例。** 書き込みの試みは、`/app`・`/peak-sim`・ルートで失敗し、`/tmp` と出力先だけが成功した。Koel の走では、実行の前後で `git status` が空で、`app_write_attempt` は 1 件も出なかった。
- **画像づくりの `apt`。** 既定の PHP イメージに無い拡張(Koel は `gd`・`xsl`)のため、利用者が自分の名前のイメージを作る手順がある。この手順の中の `apt-get` は、**公式イメージが既定で使う取得元(Debian のミラー)から、ビルド用のコンテナの中でだけ**パッケージを取る。実測の走そのもの(封じたネットワーク)の中では、取得しない。このイメージづくりは、利用者が自分の環境で行う手順であり、取得元は公式の PHP イメージが同じ目的で使うものと同じ Debian のミラーである。

### 6.5 条件 5: 副作用は偽物

- **実装。** `Mail`・`Notification`・`Queue` は fake にする(キューに積まれたリスナーとジョブは走らないので、その分のクエリは数えない)。`Event` は差し替えない(オブザーバとリスナーのクエリも数える)。`Http::preventStrayRequests()` と、既定で全て失敗する `Http::fake()`(呼ばれたホスト名を記録して接続例外を返す)。ストレージは、ローカルのディスクを作業ディレクトリの下の fake にし、外部ドライバのディスクは先にローカルに置き換える。キャッシュとセッションは `array` で、1 計測 1 プロセスなので毎回空から始まる。
- **効いた実例。** §6.1 の (b) が、fake を通らない外部通信を、ネットワーク層が受け止めた例である。fake だけでは足りず、封じたネットワークが最後の防壁になる。**ライセンス確認(`POST /api/licenses/activate`)と Dropbox の認可は、外部サービスを呼ぶので、プロファイルで「埋められない」と宣言し、叩かなかった**(外へ出る試みそのものを避けた)。
- **この条件で測れないもの。** キューに積まれたジョブのクエリは数えていない。

### 6.6 条件 6: 書き込みは 1 回ごとに巻き戻す

- **実装。** リクエスト 1 回ごと(ウォームアップ・コールド・ウォーム)に、トランザクションを開始して終わりに巻き戻す。アプリが内部でトランザクションを張る場合は入れ子(SAVEPOINT)になる。**巻き戻せないものは、測らず記録する**(`not_rollbackable`)。検知は 3 本ある。(1) 暗黙のコミットを起こす SQL(DDL など)、(2) 既定以外の接続への書き込み、(3) 試行の前後で全表の行数を比べ、ずれたら汚染とみなす。汚染を検知したら、その規模の DB を捨てて作り直す。
- **効いた実例。** Koel の走で、書き込みのメソッド(DELETE・POST・PATCH)のルート 19 本が叩けた。行数のずれ(汚染)は 0 件だった。アプリ内で外部キー制約違反(`DELETE /api/users/{user}`)の例外になった場合も、巻き戻して次の試行に影響しなかった。DDL や別接続を使うルートは Koel の走では現れず、`not_rollbackable` は 0 件だった。検知そのものは、DDL・commit・別接続を使うルートを持つ、プローブ用の複製アプリの試験で確かめた(§2.5)。
- **残る限界。** 自動採番の進みは巻き戻らない(InnoDB)。主キーの連続性は、計測に影響しない前提とした。

### 6.7 そのほか

- **PHP 自身の Fatal の行が、案内より前に残る。** メモリ不足で落ちたとき、ツールの案内(原因と再実行の案内)が標準エラーに出るが、PHP 自身の `Fatal error: Allowed memory size …` の行も、案内の前に標準エラーに残る(`docs/output-schema.md` 章 13。静的解析の側の話で、実測モードの子プロセスの落ち方は別に確かめていない)。
