# Prior art: tools and research near a code-based peak-season simulator

Survey date: 2026-11-04. Every source below was opened or queried on that date unless a row says otherwise.

This document records what the survey found about tools and research that come close to the purpose of peak-sim: predicting, from an application's own code, which part of the application reaches its limit first in a busy season. It covers six categories (static performance checkers; tools that find N+1 and slow queries while the application runs; APM and profilers; load testing; capacity planning and forecasting; research). It records what was found, what was not found, and how far the search went. It does not decide what peak-sim should be.

## 0. Summary and how to read this document

1. **63 tools and works were recorded** (category 1: 10, category 2: 13, category 3: 6, category 4: 6, category 5: 11, category 6: 17). Nothing was installed or run. The statements are what documentation, repositories, registries and papers say.
2. **No entry has `yes` on axis D (predicts the busy-season limit) or on axis E (shows accuracy against past real outcomes).** Within this survey's scope, no entry combines axis A (based on the code) with axis B (handles data-volume growth) and axis D. See §4.
3. **Axis B is the place where the surveyed work gets closest.** Six entries have `yes` on B. Five of them also read code, or tie results to code, at least in part, and all five come from research: Yang et al. (ICSE 2018), PIQL, trend-prof, WISE and aprof [S]. The sixth, a patent, works on a single query. None of the five predicts a busy-season limit from code. Panorama (ICSE 2019) is the closest static estimate (`partial` on B). See §5.
4. **Everything here carries one of three evidence grades.** A primary source is an official documentation page, the official repository, a package-registry record, or the paper itself. A secondary source is a blog, a package-listing site, a mirror, or a search-result summary. Rows whose only basis is secondary are marked `[S]` in the name column and carry lower confidence. Where a statement rests on a secondary source, the row says so.
5. **Read §6 (limits) before relying on a `no`.** In this document `no` is a statement about the pages that were read, not about the tool (§1.2).

## 1. The five axes and the rules for filling the tables

The five axes were given only as labels. The survey notes written separately for each category read them in slightly different ways. This section fixes one definition for all categories. Every cell in §3 was set against these definitions. Where setting a cell against them changed a value from the original category notes, the cell carries a dagger in §3 and is listed in §1.3.

### 1.1 Axis definitions

The same letters are used in every table of this document.

| Axis | Name | `yes` | `partial` | `no` |
| --- | --- | --- | --- | --- |
| A | Based on the code | The result is derived by analysing the application's source without running it (static analysis, symbolic execution). | The result comes from running the application, from instrumented runs, or from configuration or mappings, and is attached to a code location (route, function, line, model and relation). | The result is not tied to the application's code (black-box HTTP load, a metric series, database objects, an architecture model). |
| B | Handles data-volume growth | A documented feature models, varies or measures how the cost of a request or program (queries, rows read, time, operations) changes as the stored data or input grows. | The tool handles data size in some other way: it projects the growth of a stored quantity (for example database size) without relating it to request cost; it labels results as bounded or unbounded; or it reports speed-ups at larger sizes without a model. | Data size is outside what the tool takes in and gives out. |
| C | Handles traffic | Traffic (request rate, arrival pattern, concurrency, recorded counts) is an input the tool uses to compute or generate its result. | The tool observes or aggregates real traffic, or uses throughput as a weight, but does not take traffic as an input to a projection. | Per request or per run only. |
| D | Predicts the busy-season limit | The tool predicts where or when the system reaches its limit under a future or peak load and data state. | The tool finds or forecasts a threshold crossing, but only for the current state (an empirical break point at today's data), or only as a time-trend extrapolation of a metric, or as a design-time model whose limit analysis could not be checked. | The tool makes no such claim. |
| E | Shows accuracy against past real outcomes | Figures compare the tool's prediction with what actually happened in a past case (for example a past peak). | A paper reports a correctness figure for what the tool outputs on real code (false positives among detections, behaviour preserved, accuracy on known cases). Axes A to E were called C, D, T, P, B in the research notes and A1 to A5 in the capacity-planning notes. Only A to E are used here.

### 1.2 Rule for `no` and `unconfirmed`

One rule is used for every axis and every category.

- `no` is used only when the pages read are a complete description of what the tool takes in and gives out and the axis is outside it. A complete description is, for example, a short package's README, the documentation page of a single feature, a paper's full text, or a patent's text. For a paper, an abstract alone does not make a complete description; an abstract can support `no` only when it positively describes an output that has nothing to do with the axis. `no` is a statement about the pages read. It does not say the tool cannot do the thing.
- `unconfirmed` is used when the part of the source that would answer was not read, was unreadable, or when only some pages of a large product were read and they are silent. It is also used when the answer rests only on a search-result summary or a listing site and the row cannot be given a primary basis.
- `yes` and `partial` need a statement in a primary source. The only exceptions are the three `[S]` rows, whose values are read from a secondary source and are marked as such.
- A claim made by a vendor without data (for example a stated false-positive rate with no method or data set) counts as `no` on axis E, and the row says that a claim exists.

## 5. Closest items, how they differ, and methods that could be taken

### 5.1 Closest to the gap

| Item | How it is close | How it differs |
| --- | --- | --- |
| Panorama, ICSE 2019 (6.5) | Closest on A and B: a static, workload-independent complexity score per page element, derived from code | A relative score (the highest O(D^k) among an element's queries), not a measured cost; it ignores traffic; it names unequal table sizes as an unaddressed inaccuracy; no test of the score against measured results was found; it predicts no limit |
| Yang et al., ICSE 2018 (6.3) and Yan et al., CIKM 2017 (6.2) | Closest on B with real applications: measured scaling across three data sizes (6.3) and static bounded or unbounded labels (6.2) | Measurement of existing apps or a binary label; no prediction, no traffic, no limit |
| PIQL, PVLDB 2012 (6.10) | Closest on B and D: a bound independent of data size plus an SLO-compliance prediction model | Requires queries written in PIQL; it does not read existing ORM code |
| trend-prof, 2007 and 2009 (6.11) | Closest on the measuring idea: fit cost against workload size | General programs, instrumented runs, no database or traffic model |
| laravel-nplusone-scanner (1.4) | The closest Laravel tool on A: route-level patterns with an explicit confidence level | Finds where a loop multiplies queries; its page says it cannot measure collection sizes or SQL counts; no growth, no traffic, no limit |
| Verriet et al., ICPE 2018 (6.17) | The only item in category 5's scope that builds a performance model from static code analysis plus regression | Targets families of image-processing systems and predicts new family members, not behaviour at larger data volume or traffic (per the abstract); no tool; the full text was not read |
| Query Controller (1.10) | Interprocedural dataflow tying a query argument to the loop iteration: closest to "how many times is this query issued" | No size parameter; unvetted project, closed proposal |
| Patent US 9,117,030 (5.9) | Predicts a query's elapsed time on a larger database from statistics collected on a small one, with projected table size as an input | One query, no application code, no concurrency, linear extrapolation of CPU time; it is a patent (listed as active), so using the method needs a legal check outside this survey |

### 5.2 Methods documented in the sources that peak-sim could take

Each item below is a documented behaviour of the named source. It is not a recommendation, and nothing is said about how peak-sim should be built.

| Method | Source | What it addresses |
| --- | --- | --- |
| Data-size sweep: three sizes (200, 2,000 and 20,000 rows in the main table), other tables scaled by collected statistics, scalability judged by comparing sizes | Yang et al. 2018, Section 3.2 (6.3) | Measuring cost growth on an existing app |
| Evaluate at several database sizes and compare the gain | reformulator (6.7): the speed-up grew with database size | Showing size dependence |
| Fit cost (counts) against workload size with linear and power-law models | trend-prof (6.11) | Turning size sweeps into a growth law |
| Fix load, vary the data: fixed concurrency (400 users) while varying database content; the result was no measurable penalty in that case | A Drupal study seen through a search result [S], not opened | An experiment design |
| Emulate a larger database by scaling statistics, instead of loading the data | Patent US 9,117,030 (5.9); an ICPE 2017 tool paper seen in a search summary, whose reported error of about 10 % on TPC-H and industrial applications is unconfirmed against the paper text [S] | Estimating cost at a data size that does not exist yet |
| Bounded against unbounded result rules: a single value, a single record by unique identifier, or LIMIT is bounded; everything else grows with the table | Yan et al. 2017 (6.2) | Telling which queries scale with the table |
| Complexity rules and their known gaps: JOIN as O(D^2), indexed lookup as constant, an enclosing unbounded loop adds a factor; the paper's own list of inaccuracies (unequal table sizes, optimiser effects) | Panorama (6.5) | A ready list of what a cost formula must handle |
| Prioritise by measured impact and skip cases where the touched table is tiny | Chen et al. 2014 (6.1) | Ranking findings |
| Extract a profile statically and calibrate its cost by regression on measurements | Verriet et al. (6.17); whether it transfers cannot be said until the full text is read | Combining a static structure with measured coefficients |
| Report severity or confidence per finding and state that zero findings are not proof; deterministic JSON and exit codes for CI thresholds; recognise eager loading and aggregate attributes | laravel-nplusone-scanner (1.4) | Output conventions |
| Follow query arguments across function boundaries instead of only inside one loop body | Query Controller (1.10); djch notes the need for type hints on QuerySet parameters (1.7) | Reach of a static pass |
| Baseline files that suppress known findings and fail only on new ones | Larastan (1.1); `bigenergy/laravel-nplusone-baseline` for lazy-loading violations (a search summary only) [S] | CI use |
| Group by SQL fingerprint and call stack, with scan boundaries around a request and fix suggestions in the event | Prosopite (2.9) | The measuring step |
| Normalise SQL into signatures (literals stripped, `IN (?,?,?)` collapsed) and store counts in a committed baseline | QueryGuard README (§2.2 note) | Comparing counts across runs |
| Mark scaled or sampled numbers as approximate | Pulse, `~` for sampled values (2.3) | Output honesty |
| Per-route assertions on metrics such as SQL query count, scoped by a path pattern | Blackfire tests (3.1) | A per-route budget as an output form |
| Weight each route's cost by its traffic share (impact = latency times throughput) | Scout APM (3.5) | Finding what matters first |
| Open workload model (control the arrival rate, not concurrency) | k6 executors (4.1), Gatling injection (4.4), Artillery phases (4.5); Gatling's docs distinguish open and closed models explicitly | The traffic input |
| Build the workload from the busiest hour of past peaks | A retail engineering post seen in a search result [S]; practice, not a tool, with no accuracy report | Past peaks as the basis of a backtest |
| Report a range (forecast bounds) rather than one number; require enough history for seasonality (two seasons minimum in the docs) | Datadog forecast monitor (5.2) | Presenting uncertainty |
| A forecast-only stage that lets a user compare forecast with actual load before acting | EC2 predictive scaling (5.3), Azure predictive autoscale (5.4); neither publishes figures | The shape of a backtest stage |
| Output a fitted curve with an explicit limit and peak | USL (5.8) | The output form for the traffic dimension |
| Per-point quality flags that separate measured, interpolated and projected values | Oracle DBMS_SPACE (5.5) | Marking projected data sizes |

## 6. Limits of the survey

1. **Page summaries, not raw text.** The fetch tool used to read most web pages returns a model-written summary of the page, not the raw text. Facts (names, licences, versions, dates) were cross-checked against a second source where one existed (GitHub API fields, registry JSON). Statements in this document are paraphrases of those readings. Quotation marks are used in five places only: Larastan's rule description (1.1), the laravel-nplusone-scanner warning about zero findings (1.4), Prosopite's accuracy claim (2.9), the Datadog disk-fill example (5.2) and the New Relic availability statement (3.3). Each was compared with the raw page text on 2026-11-04. Other quotation marks name product features or page labels.
2. **Not read, or not fully read.** `www.laravel-enlightn.com` and `docs.laravel-enlightn.com` (host not resolvable); `hypersistence.io/hypersistence-optimizer` (HTTP 404) and the linked Runtime Scanner article; `web.archive.org` (blocked); `github.com/shieldci/shieldci` (HTTP 404; the real repository was named by Packagist and not opened); `docs.rubocop.org/rubocop-performance/` (redirect only); the PyPI page of django-fox-query (first fetch an error page); `docs.blackfire.io/php/index` (navigation only); a Tideways support page (HTTP 404); a first Datadog forecast URL (HTTP 404; the `forecasts` URL worked); `github.com/scoutapp/scout_apm_php` (a guessed path, Not Found); the k6 executors page (learned from a search result and the docs landing page); the ICPE 2017 paper PDF (fetched, no text extractor); the Debugbar collectors page; the part of the Rails guide after section 16.6 (output cut at 100,000 characters, so `n_plus_one_only` was not seen); Laravel 13.x versions of the docs (12.x pages were read); the last ~9,700 characters of the Clockwork page; the Prophet paper (HTTP 403); the ACM page of the ICPE 2018 paper (HTTP 403); the Palladio introduction chapter PDF, the ICPE 2018 paper PDF and the USL vignette PDF (no PDF text tool); the Palladio about page (HTTP 404); a Springer chapter page (login flow, not followed); the ACM page of Yang et al. 2018 (HTTP 403); a DBLP record (access-check page); the aprof publisher pages (HTTP 403 and 429); the original FSE 2007 trend-prof PDF host (certificate error); the original CIKM abstract page (HTTP 404; the paper was read from a course copy). GitHub release pages for EagerEye, RuboCop Performance and Enlightn showed empty "Releases" sections; versions and dates come from the registries or are marked as not obtained. For these, a `no` was not given and the value is `unconfirmed` or follows the abstract (§1.2).

9. **Tools were not installed or run.** Every behaviour recorded is what documentation says, not what was observed. Vendor claims (ShieldCI, Prosopite, Hypersistence Optimizer) are first-party and appear as claims.
