## The stop and the second run of s-3

s-3 was begun at 2026-11-19 21:30:16 and stopped at 23:07:42 with `docker compose stop` (no `-v`; the data volume `peak-lab-dbdata` was kept) for the maintainer's convenience (the machine was to be shut down); this is not a failure of the measurement. Its steps 1 to 6 had ended valid, step 7 was cut 4 s in, and the first run of s-3 is **invalid as a whole** for the verdict (kept in `s-3-170000-INVALID-20261119/`, not used for pass or fail). The stopped scenario ended with exit 19 (the memory guard could not read the stopped container; not a real OOM). The database did not shut down cleanly (the container's stop timeout is 1 s, so the server got SIGTERM and the container's SIGKILL one second later); the volume was not touched.

The lab was started again on 2026-11-20 about 00:30. **The first attempt to start failed** (the nginx.conf bind mount; the failure path of the start script is `docker compose down --remove-orphans`, without `-v`), the database container was removed and made again, and **the mysqld log of the container that had run since the first launch is lost**. What happened to the database between the stop and the second start is therefore not known from a log. What is known: the second start's log (13 lines, `pause-20261119/db-log-after-resume.txt`) has no crash recovery line and no `[ERROR]`; the count and CHECKSUM of the three tables (`entities`, `images`, `references`) are those of before s-1; the statistics of the 41 tables differ in 0 from the readings before s-1, before s-2 and before s-3.

The write counters of the server (`performance_schema.table_io_waits_summary_by_table`) start at the server's start, so the restart set them to 0 and they could no longer be compared with the ones read before s-1. They were read again at **2026-11-20 00:39:23** (`pause-20261119/new-baseline-before-s-3.tsv`) and that reading is the baseline of the second s-3 (the tool, the judging rule and the prediction were not changed; the tool wrote the same values into `s-3-170000/tables-before.tsv`). A check of the CHECKSUM of all tables was **not** taken: there is no baseline of the CHECKSUM of all tables from before the stop, so it would not show that the tables are as they were before it. s-1 and s-2 (one run) and s-3 to s-5 (after the stop and the restart of the lab, s-3 to s-5 one scenario per call of the chain) were therefore measured with a stop and a restart of the lab between them (as the fourth round's s-5 was).

The db log was read before and after every scenario of the second run; each time 0 new lines (`dblog-watch/`); it was also followed live and nothing matched `[ERROR]`, recovery, a server start or a shutdown. The db container was started at 2026-11-20 00:31:33 and ran to the end without a restart.

## Restoring the settings

After s-5 (2026-11-20 06:38:13) the logs were copied, the diff was saved, and `compose-B.diff` was reversed with `bin/lab-config-b restore` at 06:38:41; the two compose files then had the sha256 of before B (`zz-lab.ini` f495eab5…261b, `lab.conf` 604aedff…5ec5) and `git status` showed no change in `poc/lab/compose`. The app and web containers were recreated with `use-db 170000` (06:38:49) and the values read from the php-fpm and nginx side were the defaults (`limits-after-restore/`: `max_execution_time` 30, `memory_limit` 512M, `request_terminate_timeout` 0s, nginx 120s). The lab was left up at that point, with the data volume kept; it was then stopped with `docker compose stop` at 06:45:41-06:45:45 (containers and the volume kept; see `after-chain-20261120/stop/` and the last section of `pause-20261119/RESUME-20261120.md`).
