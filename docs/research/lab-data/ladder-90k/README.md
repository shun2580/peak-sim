## The stop between s-4 and s-5

At the maintainer's request the chain was held before s-5 (the wait in `stats.sh` before the label `before-s-5`: it waits for a mark file, `RESUME-s-5`). s-4 ended at 2026-11-17 20:14:25; the app and web containers were recreated and checked (20:14:42); the chain waited at the guard; the stack was stopped with `docker compose stop` at 2026-11-17 20:15:46 (the data volume `peak-lab-dbdata` was kept). `shutdown-20261117.txt` holds what was read after the stop: the volume list, the container states, the sha256 of the compose diff (`08e29d47…6375`, the same as before the stop and as at B's start), `git status` (the two compose files only), the last lines of `chain.log`, that `RESUME-s-5` did not exist, and the sha256 of `stats.sh` (`a808f07f…aab1d5`).

The wait was put in at 2026-11-17 18:38:41 (the file was replaced in place; the copy of the version before is `scripts/stats.sh.orig`; both sha256 are in `guard-sha256.txt`) and tried on a copy placed elsewhere, with the scale at 0 so that no database row was touched and no real record was written; the three points held: the label `before-s-5` waits when the mark file is absent, it passes when the mark file is made (the line for the end of the wait is also written), and the label `after-s-4` does not wait. `RESUME-s-5` did not exist at 18:39:25 (the last line of `guard-sha256.txt`).

On 2026-11-19, on the maintainer's word at 00:37, the work resumed. `resume-20261119.txt` holds the checks made before anything was started (all as at the stop: the volume present, the compose diff sha256 the same, `stats.sh` sha256 the same, no `RESUME-s-5`, no chain process because the machine's WSL had stopped; `git log e5f406f..HEAD` lists four commits, none of which changes the prediction, the estimate, the calibration, the formula, the rule of the mark or the rule of pass and fail; the Windows event 1074 shows a power-off by the user on 2026-11-17 23:46 and on 2026-11-19 00:14, not an update restart). The stack was started again with `bin/up` (00:40:47; `resume-up.output.txt`), the app and web containers were recreated with `use-db 90000` and the php-fpm side values were read (`resume-before-s-5.txt`, `limits-resume-before-s-5/`: `0`, `4G`, `0s`, `600s`, `600s`; container memory limit 6442450944). The chain had gone with the machine's stop, so it was started again with `SCENARIOS=s-5` at 00:41:46, after `RESUME-s-5` was made at 00:41:46 (the order and times are in `chain.log` and `resume-20261119.txt`). Consequences for reading s-5: it was measured after the database was brought up again (a cold start of the database server and of the app container; the data volume was the same), on a different day than s-1 to s-4, and the stop was for the maintainer's convenience, not because of anything in the measurement.
