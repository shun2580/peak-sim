## How to resume (from the start of s-1, then s-2 to s-5)

Before anything: the maintainer pauses Windows Update (or sets active hours over the night); one scenario takes 2.5-4 hours.

0. `docker info` works; `docker volume ls | grep peak-b180k-dbdata` shows the volume; `docker ps -a --filter name=peak-b180k` shows five `Exited` containers.
1. `source ~/.cache/peak-b180k/scripts/env.sh`. In `~/.cache/peak-b180k/repo`, `git status` shows only the two B compose files (sha256 above); `poc/lab/bin/lab-config-b status` must say `STATE B` - **do not run `apply` again**.
2. Move the old s-1 aside so that `measure-ladder` does not reuse its rungs 1 and 2 (it skips a step that already has `record.json`): `mv out/ladder/s-1-180000 out/ladder/s-1-180000-INVALID-20261121`; `mv out/chain out/chain-INVALID-20261121` and `mv out/chain-ends.txt out/chain-ends-INVALID-20261121.txt`, `mv out/chain-s-1.stdout out/chain-s-1-INVALID-20261121.stdout`, `mv out/dblog-watch out/dblog-watch-INVALID-20261121` (the chain then writes into a fresh `out/chain` and `out/ladder`; a new `--out-dir` is thereby used without losing the inputs in `out/`). Keep `chain/STOP` out of the new directory - that is why `chain` is moved whole.
3. `poc/lab/bin/up` (it runs the sealed-network check). **Right after it, before anything is measured (read only; any miss = do not measure, report to the maintainer):**
   1. `docker logs peak-b180k-db`: the previous shutdown was clean, so expect a normal start and `ready for connections` with no InnoDB crash-recovery lines and no `[ERROR]`; note anything else. Wait for `healthy`.
   2. `poc/lab/bin/use-db 180000` (recreates app and web; exit 2 if the database is missing).
   3. `poc/lab/bin/check-limits --require=unlimited --request-timeout=1800s` (with B on it must read `max_execution_time 0`, `memory_limit 4G`, `request_terminate_timeout 0s`, `fastcgi_read_timeout 1800s`; exit 13 otherwise).
   4. Counts and checksums against the state before the old s-1: `poc/lab/bin/check-tables after --scale=180000 --baseline=out/ladder/s-1-180000-INVALID-20261121/tables-before.tsv ...` (the same call as in the 170,000-row record, with this run's paths), and `poc/lab/bin/read-table-stats 180000 ... after-resume-before-s-1-remeasure`.
4. Start the chain with the same prediction, the same request timeout and `--require-allocation` as the first start (2026-11-21T20:27:29): `setsid nohup bash ~/.cache/peak-b180k/scripts/run-chain-watched.sh s-1 s-2 s-3 s-4 s-5 >/dev/null 2>&1 &`. `run-chain-watched.sh` reads `pause3b/db-log-before-chain.txt` to know how many db-log lines were already seen; with the db restarted the log has grown, so set that count again (or save a fresh `docker logs peak-b180k-db` to that file) before the start, otherwise the first check will flag the shutdown and start lines. Start `scripts/watchdog.sh` again too.
5. A new STOP mark is again only looked at between scenarios; a scenario that has begun is never cut. To stop in the middle, use the same stop as here (copy the logs, `docker stop -t 180` the db last) and write an `INVALID.txt`.
