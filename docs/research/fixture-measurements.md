## (c) 判定規則の一覧(群ごとに異なる点)

メモリ・クエリ数の「O(1) か O(N) か」を決める規則は、群の担当者が**測る前に**決めたもので、仕様の値ではない(仕様は「メモリは誤差が大きく参考値」とする)。試験コードで確かめた実際の規則は次のとおりで、**群ごとに揃っていない**。

### クエリ数

| 群 | 件数 | O(1) の規則 | O(N) の規則 |
| --- | --- | --- | --- |
| ok | 100 / 1,000 / 10,000 | `assertQueriesScaleConstantly`(件数を変えても同じ本数) | chunk・lazy: `atMostSlope(1/100)` と、実測の傾きが 1/100 の±10%以内(`0.1 / CHUNK_SIZE`)。伸びない経路を通さないための下限 |
| ng-basic | N = 5 / 10 / 20 | `QueryGrowth::constant()` | 自作の `BasicGrowsLinearly`: 各区間で本数が増え、区間ごとの傾きの開きが10%以内。O(N×M) も同じ規則 + M の軸で増分比 2.0±0.1 |
| ng-deep | N = 2 / 5 / 10 / 20 | (O(1) を期待するルートなし) | `atMostSlope(1行あたりの本数, 0)` に加え、各区間で傾き > 0、区間ごとの傾きが 1e-9 以内で等しい。`first-or-create` は1行あたり 2 本ちょうどを検証(他は上限のみ) |
| hidden | 10 / 100 / 1,000(判定試験) | 全件数で本数が同じ(`phpunit-query-scaling` の `atMostSlope(1, 0)` / `assertQueriesScaleConstantly` も併用) | 最小と最大の件数の間で、1行増えるごとに 0.5 本以上増える(それ以外は「判定不能」で赤) |

### メモリ(ピークバイト)

| 群 | 比べる2点 | O(1) | O(N) | 中間 |
| --- | --- | --- | --- | --- |
| ok | 10,000 件 / 100 件(100倍の件数) | 比 ≤ 2 | 比 ≥ 10 | 赤 |
| ng-basic | 10,000 件 / 1,000 件の log-log 傾き | 傾き ≤ 0.2 | 傾き ≥ 0.5 | 判定不能で赤 |
| ng-deep | 各段で増加 + 10,000 件 / 1,000 件 | (O(1) を期待するルートなし) | 毎段上がり、最後の段で3倍以上 | — |
| hidden | 10,000 件 / 1,000 件(10倍の件数) | 比 < 2 | 比 ≥ 5 | 判定不能で赤 |

件数の倍率が違う(ok は100倍、他は10倍)ので、比の閾値をそのまま並べると違いが見えにくい。log-log 傾きに直すと(計算による換算)、O(N) 側の下限は ok が 0.50、ng-basic が 0.50、ng-deep が約 0.48(3倍)、hidden が約 0.70(5倍)。O(1) 側の上限は ok が約 0.15、ng-basic が 0.20、hidden が約 0.30。

**揃っていない点が結果に効くか**を、23本のメモリ測定値(群の表の値)に4つの規則を当てて確かめた(計算のみ。試験は動かしていない)。

- 23本中22本は、どの規則でも同じ分類(O(1) か O(N))になる。
- **`/hidden/cursor` だけ**、ok の規則(100 → 10,000 の比 ≥ 10)を当てると 9.76 で「中間」になり、通らない。hidden の規則(10,000 / 1,000 = 5.44 ≥ 5)・ng-basic の規則(傾き 0.735 ≥ 0.5)・ng-deep の規則(3倍以上)では通る。固定のオーバーヘッド(約78KB)が増加分(約0.7MB)に比べて小さくないため。
- `/ok/paginate`・`/ok/chunk`・`/ok/lazy`(O(1) 期待)は ng-deep の規則(3倍以上)には該当しない(その規則は O(N) 専用)。

**提案(メンテナーの判断を仰ぐ。ここでは変えていない)**: T3 以降で一本化するなら、(1) 「10倍の件数の間の比」でなく「log-log 傾き」を共通の尺度にし、O(N) ≥ 0.5、O(1) ≤ 0.2 の2つの値だけにする(ng-basic の規則と同じ)、(2) 1点しかない固定オーバーヘッドの影響を下げるため、`/hidden/cursor` のように増加分が小さいルートは係数(バイト/行)も併記する、(3) クエリ数の傾きの許容は ±10% で統一する。どれも「参考値」の扱いは変えない。

## (d) `/hidden/cache` のドライバと、ミス・ヒットの測り方

- **ドライバ**: `CACHE_STORE=array`(`phpunit.xml` の既定。キャッシュのクエリが混ざらない)。実装は `Cache::remember('hidden.orders', 300, ...)` で、中身は N+1 で組んだ素の配列。
- **ミスの測り方**: 各件数の測定の前に `Cache::flush()` を呼び、その直後の1リクエストを測る。
- **ヒットの測り方**: ミスのリクエストの直後に、同じ件数・同じ試験の中でもう1回リクエストする。ミスとヒットは同じ試験の中で順に測る。ヒットはクエリ0本なので、`phpunit-query-scaling` の検査では `allowNoQueries: true` を指定している(クエリのない場面を正しい契約として扱う)。
- **メモリ(ヒット)**: `array` ストアの既定(`serialize = false`)では配列がそのまま返り、復元は起きない。「全件を復元する」ことを確かめるため、別の試験で `cache.stores.array.serialize = true`(file・redis・database ストアが実質していること)に切り替え、`Cache::get()` だけを測っている(応答本文を除く)。結果は(b)の注のとおり。
- **件数**: クエリは 10 / 100 / 1,000(判定試験)と 100 / 1,000 / 10,000(メモリ試験)。

## (e) 残る疑問・観察(メンテナーの判断材料)

いずれも期待値との食い違いではない。期待値は変えていない。

1. **`/ok/bulk` が書き込みなのに GET** である。仕様の表はパスしか定めておらず、他のルートと同じ GET にした。静的解析が HTTP メソッドを見るなら、POST にする1行の修正で済む。仕様の判断が要る。
2. **`/ok/bulk` の O(1) には上限がある**。1回の INSERT は MySQL のプレースホルダ上限(65,535)に収まる間だけ成り立つ。このルートは1行5列を束縛するので、13,107 顧客までは動き、13,108 顧客で `SQLSTATE[HY000]: General error: 1390 Prepared statement contains too many placeholders` になる(捨て試験で確認、コミットなし)。それ以上では分割が要り、本数は O(N / バッチ) になる。ツールがこの上限を扱うかは設計の論点。fixtures の規模(最大 10,000)では O(1) が成り立つ。
3. **`/ng/first-or-create-in-loop` の「1件あたり2本」は条件つき**。`firstOrCreate` は行がないとき(SELECT + INSERT)、`updateOrCreate` は値が変わるとき(SELECT + UPDATE)にだけ2本。既存の行への `firstOrCreate` は1本、同じ値の `updateOrCreate` は1本(UPDATE が出ない)、同じ商品に両方を続けると4本。fixtures はこの条件(S-31(c))を仕込んでいる。仕様の表が「データの状態を問わず2本」の意味なら、表の書き方が強すぎる。これは作業担当の指摘で、レビュー担当の QC(T2base、T2ngdeep)とも一致する。その確認は本作業では再測定していない(ng-deep.md の読み取りの補助)。
4. **`/ng/first-or-create-in-loop` に表にない動作 `?via=update` を足している**。表は `firstOrCreate` / `updateOrCreate` を1つのルートに挙げているが、同じ商品に両方を当てると4本になるため、既定(`firstOrCreate`)と `?via=update`(`updateOrCreate`)に分けた。パスは表のとおりだが、静的解析が1つのルートの中の分岐をどう扱うかは別の論点。
5. **`/hidden/model-with` の「毎回1本追加」の読み**。実測は 2 / 2 / 2 本で、素の `Order::get()`(1本)より常に1本多い。`query_extra_per_request = 1` を「`$with` の先読みが1本足す」と読むのは実測と合う。試験は 10 / 100 / 1,000 件で2本ちょうどを検証している。別の読み(例: 先読みの対象が複数あれば本数が増える)は測っていない。
6. **メモリは参考値**。1リクエスト・1プロセスの1回きりの測定で、応答本文とテストクライアントの分を含む。同じ要求を別の試験で測ると最大2%ほどずれる(`/hidden/appends` の100件で 548,008 と 558,648)。全体通しでもわずかにずれた(上の(a))。判定の閾値を群が個別に決めており、揃っていない(上の(c))。
7. 各群の「Points to keep in mind」:
   - ok: `chunk` / `lazy` のメモリは10,000件で約14KB増える(比 1.09。線形ではない)。
   - ng-basic: `/ng/get-then-count` のメモリが O(N) なのは全行を読み込むから。表のメモリが「応答の大きさ」の意味なら O(1) になるが、表自身の理由(全行を読み込む)とは合わない。メモリの測定は応答本文を含むため、全件を返すルートでは本文の分が上乗せされるが、傾き 1.0 に対し閾値 0.5 の余裕があり判定には影響しない。
   - ng-deep: 「O(N)」は4つの件数での線形性で、漸近の証明ではない(パッケージ自身も同旨)。メモリは応答本文を含むので、1行あたりの返す量が多いルートほど重く見える。customers にはタイムスタンプがないので `save-in-loop` は1行あたり1列の UPDATE。
