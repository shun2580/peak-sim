# Laravel 繁忙期シミュレーター 判断記録

Oct 29, 2026 · @shun

Doc の各決定について、なぜそう決めたかと、退けた案を記録する。仕様を変えるときは、まずここの理由がまだ成り立つかを確認する。

## 何を作るか

### D1. ルートごとの「増え方」を静的に判定し、繁忙期の限界点まで推定するツールにする

- 理由:既存パッケージと競合しないこと。実行時のN+1検出(laravel-query-detector など)やルールベースの監査(Enlightn 系)は既に多い。一方、Laravel向けに「テストを書かず静的に増え方を出し、繁忙期の限界まで推定する」組み合わせは見当たらなかった(2026-10調査)
- 理由:スペックアップや改修の優先順位を、数字の根拠つきで判断できるようにしたい
- 退けた案:「全部を見てメモリと速度を総合評価する」汎用ツール。コードだけでは実測値は原理的に出せず、既存ツールとの差もつかない

### D2. 「データ量を知っているレビュー用MCPサーバー」は単体で作らず、本ツールのMCPモードとして後から足す

- 理由:DBの事実(スキーマ、行数、インデックス、スロークエリ)を返すMCPは Laravel Boost、laravel-agent-mcp、Postgres MCP Pro など既に揃っている。単体で作ると競合する
- 理由:それらにないのは「コードの側の判定」と「本番規模での危険度」。これは本ツールのJSON出力をMCPで公開すれば小さいコストで補える
- 退けた案:DB接続型のMCPサーバーを独立プロジェクトとして作る

### D3. OSSとして公開する

- 理由:GitHub / Packagist で公開し、Zenn記事にもする。勤務先で使えればなお良い程度の位置づけ
- 制約:公開リポジトリのテストやサンプルに、業務のコードやテーブル名を使わない

## セキュリティと入力

### D4. 対象リポジトリのローカルクローンに対して実行し、本番には接続しない

- 理由:本番のDBやログへのアクセスを必要としなければ、認証情報も不要で、社内で使う許可も取りやすい。気軽に使えることを優先した
- 理由:CIにそのまま組み込める
- 退けた案:CloudWatchやスロークエリログなど本番の実測を直接取り込む構成。精度は上がるが、導入の重さとセキュリティ上の気軽さを失う。実測値は人が集計値として手入力する形でのみ受け付ける

### D5. ローカルDBへの接続は許可するが、取得するのはスキーマとインデックスだけ

- 理由:ローカルDBならセキュリティ上の問題はない。カラムやインデックスは正確に自動取得できる
- 理由:データの中身は判定に不要。読まなければ個人情報の心配も生じない

### D6. テーブル規模とトラフィックはYAMLで手入力する

- 理由:ローカルDBは開発用データなので、件数が本番とまったく違う。自動取得した件数では危険度を誤る
- 理由:large / medium / small 程度の大まかなタグで十分。正確な件数を書かせなければ、本番の情報を持ち出す心配も小さい
- 理由:既存のDB系MCPとの差別化にもなる(D2)

## 構成と配布

### D7. 対象アプリの外で動く単体CLIとし、Laravelの情報はartisanのJSON出力から集める

- 理由:保守できなくなってセキュリティの穴になるのを避けたい。Composerパッケージとして対象アプリに入ると、`illuminate/*` やPHPのバージョン制約が衝突しうる。Laravelの内部APIに密結合すると、メジャーアップデートのたびに壊れる。本家のメンテナンスが止まったEnlightnのようになりやすい
- 理由:`route:list` / `model:show` / `db:table` は `--json` で構造を出せる。Laravelのバージョン差を公開コマンドの出力形式に閉じ込められる
- 退けた案:① Composerパッケージ(使い勝手は良いが上記の保守負担) ② ルートやモデルを自前で解釈する完全単体CLI(Laravelの仕様変更を結局追うことになる)

### D8. 配布はpharを主とし、artisanの呼び方を設定可能にする。DockerはMVPでは提供しない

- 理由:pharは依存が中に閉じるので、他ツールと衝突しない(PHPStanなども採用する定番の形)
- 理由:対象アプリがDocker内で動く構成でも、artisanの呼び方を設定できれば対応できる。事前書き出しモードを逃げ道にする
- 退けた案:① Composerグローバル(他のグローバルツールと依存が衝突しうる。pharを包む形なら後から追加可) ② Docker(対象アプリのコンテナ内のartisanを呼ぶのが煩雑で、WSL上では遅くなりがち)

### D9. 対象はLaravel 11以降(2026-10-31 変更、当初は10以降)

- 理由:Laravel 10では `model:show` と `db:table` にdoctrine/dbalが必要で、素のプロジェクトでは動かない(将軍の指摘。T1で実地確認する)。対象に含めるとD7(対象アプリにパッケージを追加しない)とぶつかり、回避策の分だけ仕様が複雑になる
- 理由:Laravel 10は2025-02-04でセキュリティ修正も終了している
- 補足:Laravel 11も2026-03-12でセキュリティ修正が終了しているが、対象に残す。ツールは対象アプリを読むだけなのでツールの安全性には影響せず、11→12→13は破壊的変更が少なく対応コストが小さいため
- 今後の線引き:サポート終了で即外すのではなく、artisanの出力の差分を吸収するコストが見合わなくなったら外す
- ツールの動作要件はPHP 8.2以上(Laravel 11の最低バージョンに合わせる)
- 退けた案:Laravel 10を残し、リレーションをモデルのASTから取る・インデックス情報を縮退させる

## スコープと検証

### D10. MVPはシミュレーターまで含めるが、内部で3フェーズに分ける

- 理由:スペックアップの根拠に使うという目的は、シミュレーターがあって初めて達成できる
- 理由:シミュレーターの精度はフェーズ1・2の精度に依存する。各フェーズの区切りで将軍の出力を人が確認できるようにする

### D11. 判定の正しさは、答えを仕込んだ自作の検証用アプリで確かめる。仕込むのは一般的な書き方

- 理由:正解データがないと、将軍はそれらしい出力を作るだけで終わってしまう。期待する判定を先に決め、テストを先に書かせる
- 理由:業務特有の書き方ではなく一般的な書き方にする。OSSとして説明しやすく、業務のコードも持ち込まずに済む
- 退けた案:既存のOSSのLaravelアプリを検証に使う(どこが問題なのかの正解がない)

### D12. Blade、JsonResource、`$appends`、モデルの `$with`、キャッシュも解析対象に含める

- 理由:N+1はコントローラーよりもビューやリソースの中で起きやすい。ここを見ないと判定の信頼性が落ちる
- キャッシュは既定でミス時(最悪ケース)で計算する。理由:繁忙期の頭にキャッシュが一斉に切れるケースがあるため。ヒット率はYAMLで指定できる

### D13. ジョブとコマンドは起動頻度をもとに試算する

- 理由:リクエストの外でもDB負荷は生じる。繁忙期にはリクエストから `dispatch` されるジョブも一緒に増える
- 理由:ジョブには「キューの滞留」というリクエストとは別の壊れ方があるため、別に報告する
- 退けた案:ジョブとコマンドを対象外にする

## 実装方針

Claudeの提案をもとに、2026-10-29に合意した実装方針。

### D14. LLMを解析の中核に使わない(2026-10-29 合意)

- 理由:同じ入力には常に同じ結果を返す必要がある。LLMは実行ごとに結果が変わり、CIで「前回より悪化したら落とす」使い方ができない
- 理由:大きなリポジトリでは全ファイルを読み切れず、見落としやコストの問題もある
- 補足:修正案の説明など、判定の後段で任意機能として使う余地は残す(仕様書の未決事項)

### D15. 実装言語はPHP + `nikic/php-parser`

- 理由:phar配布(D8)と対象がLaravelであることから自然に決まる。PHPStanなども同じパーサーを使っている

* 理由:artisanを呼ぶ設計(D7)なので、どの言語で書いても実行環境にPHPは必要。他言語の利点(PHP不要の単一バイナリ)が活きない
* 理由:Laravelユーザーが読んで直せるので、OSSとして貢献を受けやすい。新しい構文への追従も早い
* 退けた案:Rust(Magoのパーサー)やGo / TypeScript(tree-sitterのPHP文法など)で書く

### D16. 変数の型は自前の簡易推論で解決する(2026-10-29 合意)

- 内容:`model:show --json` で取れるリレーション名の一覧を使い、`Order::where()->get()` の戻り値をループする、といった典型的な流れだけを追う。追えないものは「不明」にする
- 理由:PHPStan + Larastan に乗ると検出精度は上がるが、対象アプリのオートロードや起動が必要になり重くなる。対象アプリから独立させる方針(D7)ともぶつかる
- 退けた案:PHPStan + Larastan の型解決を使う
- 見直す条件:検証用アプリの `/ng/service` などで精度が足りないと分かった場合

### D17. 呼び出しの深さは実質無制限とし、インターフェースはServiceProviderの束縛から解決する(2026-10-29 合意)

- 理由:DDDや三層構造では、Controller → UseCase → DomainService → Repository → Eloquent実装で5〜6段になり、N+1の実体はたいてい最奥にある。浅い上限では調査にならない
- 理由:深さよりも、インターフェースで追跡が途切れることの方が大きな問題。ServiceProviderの `bind` / `singleton` / `$bindings` を静的に読めば、対象アプリを起動せずに解決できる
- 理由:メソッドごとの解析結果を使い回すので、深くしても計算量は爆発しない。異常に深いコードに備えて安全上限(既定20段)だけ置き、到達したら明示する
- 退けた案:既定3段の上限(Claudeの当初案)
- 実装が複数ある場合は全候補を解析し、最悪ケースを採用して明示する

### D18. 検証用アプリの期待値は人が決め、実測は突き合わせに使う(2026-10-31 合意)

- 内容:全ルートにクエリとメモリの期待値、Nのテーブルを仕様書で決める。実測と食い違ったら合わせずに報告し、人が判断する
- 理由:期待値は正解データそのものなので、実装側に推測させると検証の意味がなくなる(将軍の指摘:メモリ欄やNのテーブルが空だと推測で埋めることになる)
- 理由:期待値の側が間違うこともある。実際、chunkの係数の書き誤りや、cursor()のメモリがPDOのバッファリングでO(N)になる点は、レビューで見つかった
- 補足:メモリの実測は誤差が大きいので参考値とする。phpunit-query-scalingが使えなければ `DB::listen` でもよい

### D19. 開発・検証環境のPHPはDockerで用意する(2026-10-31 合意)

- 理由:Laravel 3バージョン × PHP複数の組み合わせを、ホストを汚さずに切り替えられる。普段の開発環境(WSL + Docker Desktop)とも合う
- 退けた案:WSLに複数バージョンのPHPとcomposerを入れる
- 補足:「外部通信なし」はツールが解析中に守る要件。開発環境の準備でPackagistやDocker Hubから取得するのは問題ない

### D20. 検証用アプリとartisanの互換性調査のDBはMySQL 8とする(2026-10-31 合意)

- 理由:Laravel 11以降の新規プロジェクトの既定DBはSQLite。そのままだと `/hidden/cursor` の期待値(PDOが全件をバッファするのでメモリO(N))が成り立たない。SQLiteのドライバは1行ずつ読むため
- 理由:フェーズ2のインデックス判定も、実際の本番で使われるDBと挙動を合わせる必要がある
- 補足:T1ではSQLiteでの出力差分も記録する。PostgreSQLへの対応は未決
- 退けた案:Laravelの既定どおりSQLiteを使う

## 指示書 #02 での裁定

2026-11-01 に、殿が外への仕様に関わる三点(D21〜D23)を裁き、将軍が六点(D25・D26)を裁いた。正本の置き場所(D24)は指示書 #02 で改めた。

### D21. 確度は high / medium の2段とし、「分からない」を「安全」にしない(2026-11-01 殿裁定)

- 原則:**「分からない」を「安全」にしない。** 追えない呼び出しが経路に1つでもあれば、その軸を O(1) とは出さない
- 理由:危ないルートを安全と出す見逃しは、「不明」と出すより害が大きい。プロトタイプでは、追えなかったのに確度 high で O(1) と出した例があった(`prototype-findings.md` §4.3)。「何も見つからなかった」と「見つけようとして追えなかった」を数え分けていなかったのが原因
- 内容:
  - high:経路上の呼び出しが、すべて解決できた
  - medium:すべて解決できたが、推定を含む(実装が複数ある束縛で最悪ケースを採った、リレーション名を推論で当てた、など)
  - low は使わない。追えない部分があれば、その軸は `unknown` とする
  - `unknown` のときも、追えた範囲で分かった下限(「少なくとも O(N)」など)があれば、別の項目として添える。確度と「下限であること」は別の情報として出す
  - 「何も見つからなかった」と「見つけようとして追えなかった」を必ず区別する。追えなかった箇所は gap(ファイル・行・理由)として出力に含める
- 退けた案:プロトタイプの「gap なし = high、gap あり = medium、イベントなし = low」。gap があっても medium では判定が実際より軽くなりうる(`prototype-findings.md` §4.2)ことと、確度と下限であることが混ざるため

### D22. Laravel 11 はベストエフォート対応とする(2026-11-01 殿裁定)

- 内容:D9 の補足(Laravel 11 を対象に残す)を独立させ、「ベストエフォート」と位置づける。解析の対象には含める
- 理由:Laravel 11 を外す理由は保守の重さだけで、今はそれが小さい。T1(互換性調査)で動作も確かめられた
- 理由:Composer が弾くのは「Laravel 11 を新しく作ること」だけで、既存の Laravel 11 アプリを解析することには関わらない
- README の書き分け(README は別途作る):「Laravel 11:動作確認済み。フレームワーク自体のサポートが終わっているため、ベストエフォート」
- artisan の出力が JSON として読めなかったときは、「PHP のバージョンが対象の Laravel の対応範囲外の可能性」を案内するエラーにする
- 退けた案:サポート終了(2026-03-12)をもって Laravel 11 を対象から外す(D9 の「今後の線引き」は、差分を吸収するコストが見合わなくなったときに適用する)

### D23. `/hidden/cache` の期待値は O(N) のまま、文言を直す(2026-11-01 殿裁定)

- 新しい文言:「シリアライズするキャッシュドライバ(Redis、Memcached、database、file など本番で一般的なもの)では、ヒット時も全件を復元するためメモリ O(N)。シリアライズしない array ドライバは対象外」
- 理由:期待値(メモリ O(N))は変えない。成り立つ条件を、ドライバで明示するだけ
- 実測でシリアライズを有効にして測ったやり方は正しい
- 退けた案:ヒット時のメモリを O(1) に改める(array ドライバの挙動に合わせることになり、本番で一般的なドライバの挙動とずれる)

### D24. 仕様と判断の正本をリポジトリに移す(2026-11-01 指示書 #02)

- 内容:仕様と判断の正本は、リポジトリの `docs/spec.md` と `docs/decisions.md`。claude.ai 上の版は更新を止める
- 運用:仕様を変えるときは、`docs/spec.md` を直し、理由を `docs/decisions.md` に記帳する。両方を同じコミットに入れる
- 理由:仕様と実装の食い違いを、コミットで追えるようにするため

### D25. 検証用テストアプリの表の解釈(2026-11-01 将軍裁定 S-32 の(1)〜(4)・(6)・(7))

殿が将軍に委ね、将軍が裁いた。期待値は変えない。いずれも `docs/spec.md` の「検証用テストアプリ」の表と注記に反映した。誤っていても文書か試験の1か所で戻せる。

- (1) `/ok/bulk` は POST に改める。検証用アプリのメソッドと試験を直す(期待値は不変)
- (2) `/ok/bulk` の O(1) は、MySQL のプレースホルダ上限(このルートで 13,107 顧客)の内に限ると表に注記する。ツールはこの上限を判定に使わない
- (3) `/ng/first-or-create-in-loop` の「1件あたり2本」は、`firstOrCreate` は行が無いとき、`updateOrCreate` は値が変わるときの条件つき。`?via=update` を認める
- (4) `/hidden/model-with` の「毎回1本追加」は、`$with` の先読み1つにつき1本と読む(実測 2 / 2 / 2 本と合う)
- (6) メモリは参考値のまま。増加分が小さいルート(`/hidden/cursor`)はバイト / 行も併記する
- (7) 期待値との一致は、クエリ・メモリ・N(M)のテーブルの3軸で判定する。キャッシュのミス時 / ヒット時とキャッシュ付きの明示、最悪ケース採用の明示は出力に必須。係数の補足(chunk の 1/チャンクサイズ、1件あたり2本、毎回1本追加)は出せれば出し、一致の判定には入れない
- 退けた案:係数の補足まで一致の判定に入れる(静的解析で出せない係数があると、見逃しではない差で不一致になる)

### D26. 増え方の判定規則は log-log 傾きに一本化し、閾値を残す(2026-11-01 将軍裁定 S-32 の(5))

- 内容:件数を動かして測った結果を、log-log グラフの傾きに一本化して判定する
  - O(1):傾き ≤ 0.2
  - O(N):傾き ≥ 0.5
  - 0.2 と 0.5 の間:判定不能。どちらかに合わせず、そのまま報告する
  - O(N×M):N を動かした傾きと M を動かした傾きが、両方 ≥ 0.5
  - クエリ数の区間ごとの傾きのばらつきは ±10% 以内
- 取り方(実装 `fixtures/laravel-app/tests/Support/GrowthRules.php` のとおり):
  - 傾きは、検証した規模のうち**最大の2規模の間**で取る。測った値(件数)が 1 未満のときは 1 とみなす(log の 0 を避けるため。0 だけの系列は平坦と読む)
  - ばらつき ±10% は、**第1区間の傾き**(増えた行数あたりの増えたクエリ数)を基準に、各区間の傾きがその ±10% 以内であること
- 理由:判定の基準が測る人ごとにずれると、期待値との突き合わせ(D18)が意味を失う。閾値を文書に残せば、同じ入力に同じ判定を返せる(再現性)
- 理由:間の領域を無理にどちらかへ丸めると、期待値の側が間違っているかもしれない場合に気づけない(D18「合わせずに報告」と同じ考え方)
- 閾値は `docs/spec.md` の「検証用テストアプリ」の実測の節に書いた
- 退けた案:閾値を決めず、人が目で見て判定する

### D44. ツールが生成した合成データを読むことは、D5 に反しないと判断する(2026-11-01 殿裁定)

- 内容:実測モード(指示書#04 の B。試作)では、ツールが自分で生成した合成データだけを計測用のデータベースに入れる。既存のデータベースやダンプは使わない
- 内容:ツールが自分で作ったデータを読むことは、D5 の「データの中身は読まない」に反しないと判断する
- 理由:D5 が中身を読まない理由は、データの中身が判定に不要であり、読まなければ個人情報の心配も生じないから。ツールが生成した合成データには、利用者の実データも個人情報も含まれない。D5 が避けたかった心配が、この読みには成り立たない
- 付記:D5 の取得対象(スキーマとインデックスだけ)は、利用者のローカルDBに対する規則として変えない。実測モードが読むのは、`peak_sim_measure_` で始まる計測専用のデータベースの合成データに限る。利用者の既存のデータベースの中身を読むことは、引き続きしない
- (補足)D5 の本文は「ローカルDBへの接続」と「取得するのはスキーマとインデックスだけ」を定めており、ツールが自分で作って入れたデータの読みを想定していない。この判断は、D5 の理由(実データの個人情報)に照らして、規則の文面ではなく趣旨に反しないと読んだもの
