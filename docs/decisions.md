# Laravel 繁忙期シミュレーター 判断記録

Oct 29, 2026 · @shun

Doc の各決定について、なぜそう決めたかと、退けた案を記録する。仕様を変えるときは、まずここの理由がまだ成り立つかを確認する。

## 何を作るか

### D1. ルートごとの「増え方」を静的に判定し、繁忙期の限界点まで推定するツールにする

- 理由:既存パッケージと競合しないこと。実行時のN+1検出(laravel-query-detector など)やルールベースの監査(Enlightn 系)は既に多い。一方、Laravel向けに「テストを書かず静的に増え方を出し、繁忙期の限界まで推定する」組み合わせは見当たらなかった(2026-10調査)
- 理由:スペックアップや改修の優先順位を、数字の根拠つきで判断できるようにしたい
- 退けた案:「全部を見てメモリと速度を総合評価する」汎用ツール。コードだけでは実測値は原理的に出せず、既存ツールとの差もつかない

### D2. 「データ量を知っているレビュー用MCPサーバー」は単体で作らず、本ツールのMCPモードとして後から足す

- 理由:DBの事実(スキーマ、行数、インデックス、スロークエリ)を返すMCPは Laravel Boost、laravel-agent-mcp、Postgres MCP Pro など既に揃っている。単体で作ると競合する
- 理由:それらにないのは「コードの側の判定」と「本番規模での危険度」。これは本ツールのJSON出力をMCPで公開すれば小さいコストで補える
- 退けた案:DB接続型のMCPサーバーを独立プロジェクトとして作る

### D3. OSSとして公開する

- 理由:GitHub / Packagist で公開し、Zenn記事にもする。勤務先で使えればなお良い程度の位置づけ
- 制約:公開リポジトリのテストやサンプルに、業務のコードやテーブル名を使わない

## セキュリティと入力

### D4. 対象リポジトリのローカルクローンに対して実行し、本番には接続しない

- 理由:本番のDBやログへのアクセスを必要としなければ、認証情報も不要で、社内で使う許可も取りやすい。気軽に使えることを優先した
- 理由:CIにそのまま組み込める
- 退けた案:CloudWatchやスロークエリログなど本番の実測を直接取り込む構成。精度は上がるが、導入の重さとセキュリティ上の気軽さを失う。実測値は人が集計値として手入力する形でのみ受け付ける

### D5. ローカルDBへの接続は許可するが、取得するのはスキーマとインデックスだけ

- 理由:ローカルDBならセキュリティ上の問題はない。カラムやインデックスは正確に自動取得できる
- 理由:データの中身は判定に不要。読まなければ個人情報の心配も生じない

### D6. テーブル規模とトラフィックはYAMLで手入力する

- 理由:ローカルDBは開発用データなので、件数が本番とまったく違う。自動取得した件数では危険度を誤る
- 理由:large / medium / small 程度の大まかなタグで十分。正確な件数を書かせなければ、本番の情報を持ち出す心配も小さい
- 理由:既存のDB系MCPとの差別化にもなる(D2)

## 構成と配布

### D7. 対象アプリの外で動く単体CLIとし、Laravelの情報はartisanのJSON出力から集める

- 理由:保守できなくなってセキュリティの穴になるのを避けたい。Composerパッケージとして対象アプリに入ると、`illuminate/*` やPHPのバージョン制約が衝突しうる。Laravelの内部APIに密結合すると、メジャーアップデートのたびに壊れる。本家のメンテナンスが止まったEnlightnのようになりやすい
- 理由:`route:list` / `model:show` / `db:table` は `--json` で構造を出せる。Laravelのバージョン差を公開コマンドの出力形式に閉じ込められる
- 退けた案:① Composerパッケージ(使い勝手は良いが上記の保守負担) ② ルートやモデルを自前で解釈する完全単体CLI(Laravelの仕様変更を結局追うことになる)

### D8. 配布はpharを主とし、artisanの呼び方を設定可能にする。DockerはMVPでは提供しない

- 理由:pharは依存が中に閉じるので、他ツールと衝突しない(PHPStanなども採用する定番の形)
- 理由:対象アプリがDocker内で動く構成でも、artisanの呼び方を設定できれば対応できる。事前書き出しモードを逃げ道にする
- 退けた案:① Composerグローバル(他のグローバルツールと依存が衝突しうる。pharを包む形なら後から追加可) ② Docker(対象アプリのコンテナ内のartisanを呼ぶのが煩雑で、WSL上では遅くなりがち)

### D9. 対象はLaravel 11以降(2026-10-31 変更、当初は10以降)

- 理由:Laravel 10では `model:show` と `db:table` にdoctrine/dbalが必要で、素のプロジェクトでは動かない(将軍の指摘。T1で実地確認する)。対象に含めるとD7(対象アプリにパッケージを追加しない)とぶつかり、回避策の分だけ仕様が複雑になる
- 理由:Laravel 10は2025-02-04でセキュリティ修正も終了している
- 補足:Laravel 11も2026-03-12でセキュリティ修正が終了しているが、対象に残す。ツールは対象アプリを読むだけなのでツールの安全性には影響せず、11→12→13は破壊的変更が少なく対応コストが小さいため
- 今後の線引き:サポート終了で即外すのではなく、artisanの出力の差分を吸収するコストが見合わなくなったら外す
- ツールの動作要件はPHP 8.2以上(Laravel 11の最低バージョンに合わせる)
- 退けた案:Laravel 10を残し、リレーションをモデルのASTから取る・インデックス情報を縮退させる

## スコープと検証

### D10. MVPはシミュレーターまで含めるが、内部で3フェーズに分ける

- 理由:スペックアップの根拠に使うという目的は、シミュレーターがあって初めて達成できる
- 理由:シミュレーターの精度はフェーズ1・2の精度に依存する。各フェーズの区切りで将軍の出力を人が確認できるようにする

### D11. 判定の正しさは、答えを仕込んだ自作の検証用アプリで確かめる。仕込むのは一般的な書き方

- 理由:正解データがないと、将軍はそれらしい出力を作るだけで終わってしまう。期待する判定を先に決め、テストを先に書かせる
- 理由:業務特有の書き方ではなく一般的な書き方にする。OSSとして説明しやすく、業務のコードも持ち込まずに済む
- 退けた案:既存のOSSのLaravelアプリを検証に使う(どこが問題なのかの正解がない)

### D12. Blade、JsonResource、`$appends`、モデルの `$with`、キャッシュも解析対象に含める

- 理由:N+1はコントローラーよりもビューやリソースの中で起きやすい。ここを見ないと判定の信頼性が落ちる
- キャッシュは既定でミス時(最悪ケース)で計算する。理由:繁忙期の頭にキャッシュが一斉に切れるケースがあるため。ヒット率はYAMLで指定できる

### D13. ジョブとコマンドは起動頻度をもとに試算する

- 理由:リクエストの外でもDB負荷は生じる。繁忙期にはリクエストから `dispatch` されるジョブも一緒に増える
- 理由:ジョブには「キューの滞留」というリクエストとは別の壊れ方があるため、別に報告する
- 退けた案:ジョブとコマンドを対象外にする

## 実装方針

Claudeの提案をもとに、2026-10-29に合意した実装方針。

### D14. LLMを解析の中核に使わない(2026-10-29 合意)

- 理由:同じ入力には常に同じ結果を返す必要がある。LLMは実行ごとに結果が変わり、CIで「前回より悪化したら落とす」使い方ができない
- 理由:大きなリポジトリでは全ファイルを読み切れず、見落としやコストの問題もある
- 補足:修正案の説明など、判定の後段で任意機能として使う余地は残す(仕様書の未決事項)

### D15. 実装言語はPHP + `nikic/php-parser`

- 理由:phar配布(D8)と対象がLaravelであることから自然に決まる。PHPStanなども同じパーサーを使っている

* 理由:artisanを呼ぶ設計(D7)なので、どの言語で書いても実行環境にPHPは必要。他言語の利点(PHP不要の単一バイナリ)が活きない
* 理由:Laravelユーザーが読んで直せるので、OSSとして貢献を受けやすい。新しい構文への追従も早い
* 退けた案:Rust(Magoのパーサー)やGo / TypeScript(tree-sitterのPHP文法など)で書く

### D16. 変数の型は自前の簡易推論で解決する(2026-10-29 合意)

- 内容:`model:show --json` で取れるリレーション名の一覧を使い、`Order::where()->get()` の戻り値をループする、といった典型的な流れだけを追う。追えないものは「不明」にする
- 理由:PHPStan + Larastan に乗ると検出精度は上がるが、対象アプリのオートロードや起動が必要になり重くなる。対象アプリから独立させる方針(D7)ともぶつかる
- 退けた案:PHPStan + Larastan の型解決を使う
- 見直す条件:検証用アプリの `/ng/service` などで精度が足りないと分かった場合

### D17. 呼び出しの深さは実質無制限とし、インターフェースはServiceProviderの束縛から解決する(2026-10-29 合意)

- 理由:DDDや三層構造では、Controller → UseCase → DomainService → Repository → Eloquent実装で5〜6段になり、N+1の実体はたいてい最奥にある。浅い上限では調査にならない
- 理由:深さよりも、インターフェースで追跡が途切れることの方が大きな問題。ServiceProviderの `bind` / `singleton` / `$bindings` を静的に読めば、対象アプリを起動せずに解決できる
- 理由:メソッドごとの解析結果を使い回すので、深くしても計算量は爆発しない。異常に深いコードに備えて安全上限(既定20段)だけ置き、到達したら明示する
- 退けた案:既定3段の上限(Claudeの当初案)
- 実装が複数ある場合は全候補を解析し、最悪ケースを採用して明示する

### D18. 検証用アプリの期待値は人が決め、実測は突き合わせに使う(2026-10-31 合意)

- 内容:全ルートにクエリとメモリの期待値、Nのテーブルを仕様書で決める。実測と食い違ったら合わせずに報告し、人が判断する
- 理由:期待値は正解データそのものなので、実装側に推測させると検証の意味がなくなる(将軍の指摘:メモリ欄やNのテーブルが空だと推測で埋めることになる)
- 理由:期待値の側が間違うこともある。実際、chunkの係数の書き誤りや、cursor()のメモリがPDOのバッファリングでO(N)になる点は、レビューで見つかった
- 補足:メモリの実測は誤差が大きいので参考値とする。phpunit-query-scalingが使えなければ `DB::listen` でもよい

### D19. 開発・検証環境のPHPはDockerで用意する(2026-10-31 合意)

- 理由:Laravel 3バージョン × PHP複数の組み合わせを、ホストを汚さずに切り替えられる。普段の開発環境(WSL + Docker Desktop)とも合う
- 退けた案:WSLに複数バージョンのPHPとcomposerを入れる
- 補足:「外部通信なし」はツールが解析中に守る要件。開発環境の準備でPackagistやDocker Hubから取得するのは問題ない

### D20. 検証用アプリとartisanの互換性調査のDBはMySQL 8とする(2026-10-31 合意)

- 理由:Laravel 11以降の新規プロジェクトの既定DBはSQLite。そのままだと `/hidden/cursor` の期待値(PDOが全件をバッファするのでメモリO(N))が成り立たない。SQLiteのドライバは1行ずつ読むため
- 理由:フェーズ2のインデックス判定も、実際の本番で使われるDBと挙動を合わせる必要がある
- 補足:T1ではSQLiteでの出力差分も記録する。PostgreSQLへの対応は未決
- 退けた案:Laravelの既定どおりSQLiteを使う

## 指示書 #02 での裁定

2026-11-01 に、殿が外への仕様に関わる三点(D21〜D23)を裁き、将軍が六点(D25・D26)を裁いた。正本の置き場所(D24)は指示書 #02 で改めた。

### D21. 確度は high / medium の2段とし、「分からない」を「安全」にしない(2026-11-01 殿裁定)

- 原則:**「分からない」を「安全」にしない。** 追えない呼び出しが経路に1つでもあれば、その軸を O(1) とは出さない
- 理由:危ないルートを安全と出す見逃しは、「不明」と出すより害が大きい。プロトタイプでは、追えなかったのに確度 high で O(1) と出した例があった(`prototype-findings.md` §4.3)。「何も見つからなかった」と「見つけようとして追えなかった」を数え分けていなかったのが原因
- 内容:
  - high:経路上の呼び出しが、すべて解決できた
  - medium:すべて解決できたが、推定を含む(実装が複数ある束縛で最悪ケースを採った、リレーション名を推論で当てた、など)
  - low は使わない。追えない部分があれば、その軸は `unknown` とする
  - `unknown` のときも、追えた範囲で分かった下限(「少なくとも O(N)」など)があれば、別の項目として添える。確度と「下限であること」は別の情報として出す
  - 「何も見つからなかった」と「見つけようとして追えなかった」を必ず区別する。追えなかった箇所は gap(ファイル・行・理由)として出力に含める
- 退けた案:プロトタイプの「gap なし = high、gap あり = medium、イベントなし = low」。gap があっても medium では判定が実際より軽くなりうる(`prototype-findings.md` §4.2)ことと、確度と下限であることが混ざるため

### D22. Laravel 11 はベストエフォート対応とする(2026-11-01 殿裁定)

- 内容:D9 の補足(Laravel 11 を対象に残す)を独立させ、「ベストエフォート」と位置づける。解析の対象には含める
- 理由:Laravel 11 を外す理由は保守の重さだけで、今はそれが小さい。T1(互換性調査)で動作も確かめられた
- 理由:Composer が弾くのは「Laravel 11 を新しく作ること」だけで、既存の Laravel 11 アプリを解析することには関わらない
- README の書き分け(README は別途作る):「Laravel 11:動作確認済み。フレームワーク自体のサポートが終わっているため、ベストエフォート」
- artisan の出力が JSON として読めなかったときは、「PHP のバージョンが対象の Laravel の対応範囲外の可能性」を案内するエラーにする
- 退けた案:サポート終了(2026-03-12)をもって Laravel 11 を対象から外す(D9 の「今後の線引き」は、差分を吸収するコストが見合わなくなったときに適用する)

### D23. `/hidden/cache` の期待値は O(N) のまま、文言を直す(2026-11-01 殿裁定)

- 新しい文言:「シリアライズするキャッシュドライバ(Redis、Memcached、database、file など本番で一般的なもの)では、ヒット時も全件を復元するためメモリ O(N)。シリアライズしない array ドライバは対象外」
- 理由:期待値(メモリ O(N))は変えない。成り立つ条件を、ドライバで明示するだけ
- 実測でシリアライズを有効にして測ったやり方は正しい
- 退けた案:ヒット時のメモリを O(1) に改める(array ドライバの挙動に合わせることになり、本番で一般的なドライバの挙動とずれる)

### D24. 仕様と判断の正本をリポジトリに移す(2026-11-01 指示書 #02)

- 内容:仕様と判断の正本は、リポジトリの `docs/spec.md` と `docs/decisions.md`。claude.ai 上の版は更新を止める
- 運用:仕様を変えるときは、`docs/spec.md` を直し、理由を `docs/decisions.md` に記帳する。両方を同じコミットに入れる

### D25. 検証用テストアプリの表の解釈(2026-11-01 将軍裁定 S-32 の(1)〜(4)・(6)・(7))

殿が将軍に委ね、将軍が裁いた。期待値は変えない。いずれも `docs/spec.md` の「検証用テストアプリ」の表と注記に反映した。誤っていても文書か試験の1か所で戻せる。

- (1) `/ok/bulk` は POST に改める。検証用アプリのメソッドと試験を直す(期待値は不変)
- (2) `/ok/bulk` の O(1) は、MySQL のプレースホルダ上限(このルートで 13,107 顧客)の内に限ると表に注記する。ツールはこの上限を判定に使わない
- (3) `/ng/first-or-create-in-loop` の「1件あたり2本」は、`firstOrCreate` は行が無いとき、`updateOrCreate` は値が変わるときの条件つき。`?via=update` を認める
- (4) `/hidden/model-with` の「毎回1本追加」は、`$with` の先読み1つにつき1本と読む(実測 2 / 2 / 2 本と合う)
- (6) メモリは参考値のまま。増加分が小さいルート(`/hidden/cursor`)はバイト / 行も併記する
- (7) 期待値との一致は、クエリ・メモリ・N(M)のテーブルの3軸で判定する。キャッシュのミス時 / ヒット時とキャッシュ付きの明示、最悪ケース採用の明示は出力に必須。係数の補足(chunk の 1/チャンクサイズ、1件あたり2本、毎回1本追加)は出せれば出し、一致の判定には入れない
- 退けた案:係数の補足まで一致の判定に入れる(静的解析で出せない係数があると、見逃しではない差で不一致になる)

### D26. 増え方の判定規則は log-log 傾きに一本化し、閾値を残す(2026-11-01 将軍裁定 S-32 の(5))

- 内容:件数を動かして測った結果を、log-log グラフの傾きに一本化して判定する
  - O(1):傾き ≤ 0.2
  - O(N):傾き ≥ 0.5
  - 0.2 と 0.5 の間:判定不能。どちらかに合わせず、そのまま報告する
  - O(N×M):N を動かした傾きと M を動かした傾きが、両方 ≥ 0.5
  - クエリ数の区間ごとの傾きのばらつきは ±10% 以内
- 取り方(実装 `fixtures/laravel-app/tests/Support/GrowthRules.php` のとおり):
  - 傾きは、検証した規模のうち**最大の2規模の間**で取る。測った値(件数)が 1 未満のときは 1 とみなす(log の 0 を避けるため。0 だけの系列は平坦と読む)
  - ばらつき ±10% は、**第1区間の傾き**(増えた行数あたりの増えたクエリ数)を基準に、各区間の傾きがその ±10% 以内であること
- 理由:判定の基準が測る人ごとにずれると、期待値との突き合わせ(D18)が意味を失う。閾値を文書に残せば、同じ入力に同じ判定を返せる(再現性)
- 理由:間の領域を無理にどちらかへ丸めると、期待値の側が間違っているかもしれない場合に気づけない(D18「合わせずに報告」と同じ考え方)
- 閾値は `docs/spec.md` の「検証用テストアプリ」の実測の節に書いた
- 退けた案:閾値を決めず、人が目で見て判定する

### D45. enum の `->value`・`->name` の読みは、受け手が enum と静的に分かるときだけ、`gap` にしない例外とする(2026-11-01 指示書#04 の A3。D39 の実施)

- 内容:プロパティ読みの受け手が、次のどちらかで enum と静的に分かるとき、`->name`(backed enum・pure enum とも)と `->value`(backed enum のみ)の読みを値(PlainT)として通し、`gap` にしない
  - `Foo::BAR->value`・`self::BAR->name` の形。`Foo`(`self`・`static` を含む)がアプリの enum で、`BAR` がその enum の `case` として宣言されている

- 内容:次は従来どおり `gap` のまま
  - 受け手の型が分からない読み(型宣言の無い変数・プロパティ、`mixed`、型の取れない呼び出しの結果)

  - 同「Enumerations overview」(https://www.php.net/manual/en/language.enumerations.overview.php):「Enum cases are objects」。ケースは enum クラスの単一インスタンスのオブジェクトである
  - 読みの結果は、定義に書かれた名前または定数で、実行の度に変わらない。DB に触れず、`name`・`value` はマニュアルが read-only の組み込みのプロパティと述べるもので、アプリのコードが書くものではないので、アプリのコードを呼び返さない
  - (補足)「ケースの `name`・`value` の読みはゲッターを呼ばない」という点は、マニュアルが「read-only の property」と述べていることから読んだ。マニュアルに「ゲッターを呼ばない」という文言はない
- 理由:D39 のとおり、FIX3 の防壁(型の取れない値へのプロパティ読みは `gap`)が、DB に触れない enum の読みまで `gap` にしていた(real-app-trial.md の §3.6・§6.1。`->value` 612 件・`->name` 71 件、確実な形で 568 件・271 箇所)。受け手が enum と分かるものに限れば、D21 を崩さずにこの過検知を外せる
- 理由:個別処理にして、例外表(`resources/known-calls.php`)には載せない。例外表は「関数名・クラスとメソッド名」の引き当てで、載せる条件は呼び出しの名前だけで決まる。この例外は「受け手の型が enum と静的に分かること」を要するので、型を見る場所(`CallResolver` のプロパティ読み)に置くのが自然である。D35(`$loop` の 1 段目)が `ViewHandler` の個別処理で、例外表に載せなかった前例に合わせた
- 付記:実装は `CallResolver` の `propertyFetch`(定数の形)と `propertyOf`(宣言された型)。試験は `tests/Unit/Engine/EnumReadTest.php`
- (補足)外した場合は、enum の読みが `gap` に戻るだけで、判定は重くなる側に動く。見逃しは増えない(推測)。この段の再測定で D33 の抜き取りを行う
- 退けた案:例外表に `->value`・`->name` を載せる(型が enum かどうかを見ず、enum でない値の `->name`(モデルの列など)まで通してしまう)

## 読んだ行数の測定の細部(2026-11-04)

指示書#09 の T1(読んだ行数の測定)で決めた細部。いずれも D72 の委任による戻せる判断である。

### D73. 読んだ行数は、セッションの `Handler_read_*` 7 本の差分から空の差分を引いて数える(D72 の委任による戻せる判断)

- 内容:リクエストの直前と直後に `SHOW SESSION STATUS LIKE 'Handler_read%'` を、アプリの既定の接続の PDO へ直接送り、`Handler_read_first`・`_key`・`_last`・`_next`・`_prev`・`_rnd`・`_rnd_next` の差の合計を「読んだ行数」とする。Laravel の接続を通さないので、クエリの本数には数えない。`RowsRead`(返った行数)は消さずに残し、出力の見出しは「returned rows」と「examined rows」に分ける
- 内容:空の差分(SHOW を続けて 2 回取ったときの差分)を、起動ごとに 1 回測って毎回の差分から引く。その前に読みを 1 回捨てる(接続して最初の SHOW は status の表の準備で多く読む恐れがあるため)。基準は「捨て読み → 読み → 読み」の後ろ 2 回の差
- 内容:差し引いた結果が基準を下回ったら 0 に切る(雑音であり、負の行数にしない)。7 本のどれか 1 本でも減っていたら、セッションが替わったとみて null にする
- 内容:永続接続は取得不可として null にする(他のセッションと共有されうるため)。取れないときは 0 にせず null にする(D21)
- 内容:JSON のキーは `rows_examined`・`rows_examined_baseline`(既存の `peak_mem`・`rows_read` と揃えた snake_case)。PHP のプロパティ名は指示書どおり `rowsExamined`・`rowsExaminedBaseline`
- 内容:`routes.jsonl` の行数は、規模 0 を含む平行配列(`rows: {scales, returned, examined, examined_baseline}`)とする。既存の `scales`/`values` は規模 0 を含まないままなので、取り違えないよう別のキーにした
- 理由:返った行数は、全件走査して 1 行だけ返す読みを見逃す。コストの式(T2)に要るのは DB が実際に読んだ量である

### D74. 照合のために、測定 DB の利用者 `measure` へ 2 つの SELECT 権限と、文の履歴の設定を与える(D72 の委任による戻せる判断)

- 内容:与えた権限は 2 つだけ:`performance_schema.events_statements_history_long` と `performance_schema.threads` の SELECT(`compose/mysql-init/20-statement-history-grants.sql`)。これより広い権限(他の performance_schema・sys の表、PROCESS、SUPER)は与えない。試験(`SHOW GRANTS` を見る)が、この 2 つ以外の performance_schema の権限と、測定 DB 以外への権限が無いことを確かめる
- 内容:設定は測定用スタックの MySQL に置く(`compose/mysql-conf/20-statement-history.cnf`、`/etc/mysql/conf.d` へ読み取り専用で載せる):consumer `events_statements_history_long` を有効にし、履歴の長さを 100,000 行にする。履歴は輪(古い行から消える)であり、試験は、照合する窓の始まり(START TRANSACTION)が履歴に残っていることを確かめる(残っていなければ失敗)
- 内容:この権限は PHP 側の同じ利用者にも及ぶ(利用者は 1 つのため)。すなわちアプリのコードも、理屈の上では他の接続の文の履歴を読める。測定スタックは閉じたネットワークで、中の DB は使い捨てかつ合成データのみなので、安全の条件 2(測定 DB 以外に触れない)は保たれる。アプリの接続から照合しない、という規則は試験の側で守る(照合は試験の別の接続から行う)
- 理由:ツール側の別の接続から、サーバ自身が文ごとに数えた ROWS_EXAMINED を読むには、この 2 つが要る。履歴を有効にする設定は起動時にしか入れられない

### D75. 照合の方法:窓は START TRANSACTION と ROLLBACK の間の最初と最後の実行で決め、差は「サーバの数」を分母にして 10% で見る(D72 の委任による戻せる判断)

- 内容:アプリは prepared statement で文を送るため、サーバは文の本文を履歴に残さない(`SQL_TEXT` が空)。そこで、実行ごとに `bin/measure-one` の cold の試行を 1 回動かし、その接続の履歴から、START TRANSACTION と ROLLBACK の間にある最初の実行と最後の実行(どちらも 7 行を返す=SHOW のスナップショット)を窓の端とし、端の間の文の ROWS_EXAMINED を合計する。窓の端が見つからないときは、見つからなかったこととして失敗にする(合格にしない)
- 内容:差は `|読んだ行数 − サーバの数| ÷ サーバの数` とし、10% を超えるルートが 1 本でもあれば失敗にする(指示書のとおり。閾値は動かさない)。サーバの数が 0 で読んだ行数が 1 以上のときは、無限大(失敗)とする
- 理由:サーバの数を基準とするのは、これが文ごとの正式な数え方であり、どちらが正かを決める前の、照合の向きを 1 つに固めるため。向きを替えると 10% に入るルートが変わりうるので、決めて記録しておく

### D76. ピークメモリは、`memory_get_peak_usage(false)` の増分で測る。仕様 §4 の文言(`true`)とは別の道を採る(D72 の委任による戻せる判断)

- 内容:ピークメモリは、リクエストの直前(`gc_collect_cycles()` の後)の `memory_get_usage()` を、リクエスト後の `memory_get_peak_usage()`(引数なし=`false`、emalloc の実使用バイト)から引いた差で測る。試行(warmup・cold・warm)ごとに、リクエストの直前に `memory_reset_peak_usage()` を呼ぶので、前の試行のピークは持ち越さない(確かめたところ、既にそうなっていたので直していない)
- 内容:仕様 §4 の文言は `true`(確保したチャンクの大きさ)だが、これは採らない
- 理由:`true` は 2 MiB のチャンク単位でしか動かず、小さな規模では値が段になり、規模ごとの当てはめ(T2)が粗くなる。`false` は実使用バイトで滑らかに動く。一方、§6.2 で `memory_limit` と比べるときは、増分ではなく起動分を足した総量が要る。これは手順 4 以降で扱う(今回の範囲ではない)

## 当てはめ(コストの式)の細部(2026-11-04)

指示書#09 の T2(当てはめ)で決めた細部。いずれも D72 の委任による戻せる判断である。

### D77. `k = 0` のときは、定数を `a` に置き、`b = 0` として出す(D72 の委任による戻せる判断)

- 内容:`k = 0` では `a + b·N^0 = a + b` となり、`a` と `b` は区別できない。定数を `a` に、`b` を 0 にして出す
- 理由:同じ誤差なら小さい `k` を採る規則(指示書 T2-1)と整合する

### D78. 「同じ誤差」は、その系列の二乗和の 1e-12 倍未満の差とする(D72 の委任による戻せる判断)

- 内容:二乗誤差の差が、観測値の二乗和の 1e-12 倍未満なら同じ誤差とみなし、小さい `k` を採る
- 理由:浮動小数の揺れで、大きい `k` を採ってしまうのを避ける

### D79. 規模 0 での `N^k` は、`k > 0` なら 0、`k = 0` なら 1 とする(D72 の委任による戻せる判断)

- 内容:式のとおりに計算する。したがって規模 0 の値は、`k > 0` の式では `a` を直接押さえる
- 理由:規模 0(空のシステム)の値が、固定費 `a` を決める役を持つ

### D80. `contradicts_static` の判定は、静的解析の `lower_bound`(O(N) または O(N·M))だけを見る(D72 の委任による戻せる判断)

- 内容:`growth` が O(N) と確定していても `lower_bound` が null のルートは、この判定の対象にしない(指示書の文言どおり)
- 理由:指示書は「O(N) 以上の下限を付けたルート」としている。下限の無いルートまで矛盾と呼ぶと、静的解析の確信の弱いところを根拠にしてしまう

### D81. 2 規模ずつの式は、規模 0 を除いた規模から選ぶ(D72 の委任による戻せる判断)

- 内容:規模 0 は、全規模の当てはめで `a` を決めるために使う。2 規模ずつの式(`a` は全規模の当てはめの値に固定)の組には入れない
- 理由:指示書 T2-1 は、`a` を固定して `b`・`k` だけを求めるとしている。規模 0 を組に入れると `a` の固定と二重になる

### D82. 「測れなかった規模」の定義(D72 の委任による戻せる判断)

- 内容:そのルートの cold の試行が `class=ok` で、その量の値が null でない規模を「測れた」とする。それ以外(試行はあるが `ok` でない・値が null)は「測れなかった」。試行そのものが無い規模は `not measured` とする。量ごとに判定するので、`rows_examined` が null の規模があれば、`rows_examined` だけが `insufficient_scales` になる
- 理由:null を 0 にしない(D21)。量ごとに分けるのは、ある量が取れないだけで他の量の式まで落とさないため

### D83. 子の表の軸(M 軸)の掃引は、今回は当てはめない(D72 の委任による戻せる判断)

- 内容:`fits.json` の `axis` は 1 つなので、M 軸(子の表の 3/30/300)の試行は読み飛ばす。必要なら別に起こす
- 理由:今回の範囲は N 軸の外挿試験(A)であり、M 軸の式は A の合否に使わない
- 付記:後の外挿の文書(`docs/research/extrapolation-test.md`)にも書く

### D84. `contradicts_static` の行には式の `a`・`b`・`k` を置かず、`rejected_fit` に退ける(D72 の委任による戻せる判断)

- 内容:退けた式は `rejected_fit`(と `reason`)に移す。指示書の出力の形への追加である。`bin/predict` は `fit_status` が `ok` でない行を採らないので、退けた式が誤って予測に使われない
- 理由:静的解析と矛盾した式を、予測の入力に見える場所に置かないため。式そのものは検証のために残す
- 付記:後の外挿の文書にも書く

### D85. 記録の項目名は `rows_examined`(snake_case)で読む。`rowsExamined` も読む(D72 の委任による戻せる判断)

- 内容:`attempts.jsonl` の項目名は `rows_examined`。D73 のとおり。当てはめの入力側は、`rowsExamined` も受ける
- 理由:既存の `peak_mem`・`rows_read` と同じ形に揃える。名前が違っても読み取りで落とさない

### D86. ルート名は `METHOD uri`、表は静的解析の `n_table` から取る(D72 の委任による戻せる判断)

- 内容:`fits.json` のルート名は、`attempts`/`routes` の `method` と `route` を空白でつないだ形にする。`table` は `tasks.json` の `spec.static.n_table` から取る(無ければ null)
- 理由:同じ URI でメソッドが違うルート(GET と POST)を取り違えないため

### D87. 当てはめの数値は、有効数字 12 桁で丸めて書く(D72 の委任による戻せる判断)

- 内容:`a`・`b`・二乗誤差などを有効数字 12 桁で丸めて書く
- 理由:浮動小数の揺れを書き出さず、`b` が小さく `k` が高い式でも精度を保つ

## 外挿試験(A)の測定器の直し(2026-11-04)

100,000 件の測定の前に、測定器(`poc/runtime/bin/measure` とその部品)を固めた。測定の途中で測定器を変えると「何で測ったか」が揺れるため、予測を固める前に直して commit する。合格基準(§7.4)の数値・分母・閾値、安全の条件(`poc/runtime/README.md` の 1〜6)は変えない。

### D90. 測定する規模は 1 つだけでも受け付ける(D72 の委任による戻せる判断)

- 内容:`bin/measure` の `--scales` と `MeasureConfig` の下限を「3 つ以上」から「1 つ以上」に直す(直す所は `bin/measure` の検査と `MeasureConfig` の 2 か所)。規模 1 つでは、規模の間の傾き(log-log)が取れず、増え方の判定は `insufficient_points` になる。外挿試験(A)が使うのは cold の値だけで、害は無い
- 理由:予測の規模 100,000 件だけを一度きり測る。規模を 3 つ並べて回避すると、時間が 3 倍になる

### D91. リクエストの上限を 600 秒まで許す。1 回の測定の上限は、それから導く(D72 の委任による戻せる判断)

- 内容:`--request-timeout` と `Requester` の上限を 60 秒から 600 秒に上げる(既定の 20 秒は変えない)。1 つの測定(アプリの起動と 3 回のリクエスト)の上限は、定数 150 秒をやめ、「リクエストの上限 × 3 + 起動 120 秒」として引数から導く(既定の 20 秒なら 180 秒)。上げても測れないルートは、今までどおり「測れなかった」として数える。測定用 DB の作成の上限 900 秒は変えない
- 理由:時間の上限は、暴走を止める実務の上限であって、隔離を担うものではない。安全の条件 1〜6(内部ネットワーク・測定用 DB のみ・合成データ・アプリ無改変・副作用の偽物・巻き戻し)にも、#01 の守ること 1〜10 にも、時間の上限は無い。緩めても隔離は変わらない。合格基準の「測れなかったルートが 20% を超えれば判定不能」の数値と分母の定義も変わらない(測れるルートが増えるだけ)。上げなければ、100,000 件で 1 リクエストが 1 分を超える型(1 件ごとに 1 回問い合わせる型)が測れず、判定不能に近づく

### D92. 100,000 件などで、warm(3 回目)のリクエストを省く選択肢を付ける(D72 の委任による戻せる判断)

- 内容:`bin/measure --warm=off` を付けたときだけ、各測定をウォームアップと cold の 2 回にする(`on` が既定で、今までどおり 3 回)。規模 0 が既に 2 回で測っているのと同じ扱い。合否を決める cold の値は変わらない。warm の試行は記録に残らない
- 理由:規模が大きいと 1 リクエストが数分かかる。合否は cold の値だけで決まるので、3 回目を省けば時間が約 3 分の 1 減る(約 3 分の 2 になる)。引数で明示したときだけ効くので、既定の測定は変わらない

### D93. BookStack の 3 本(`GET /my-account`・`POST /saml2/acs`・`GET /settings/{category}`)は、外挿試験(A)の `--only` から外す。コードは変えない(D72 の委任による戻せる判断)

- 内容:この 3 本は、全表を N 件に伸ばす計画で動く。この計画は設計上、空のシステム(規模 0)の点を作らないので、どの量も `insufficient_scales` になり、もとより式が作れず合否の分母に入らない。外しても分母の本数は 1 本も変わらない。外した 3 本は、`docs/research/extrapolation-test.md` の「測れなかったルート」の一覧に、理由つきで載せる(黙って落とさない)
- 理由:全表を伸ばす計画では、プロファイルの補正(`joint_permissions` を全エンティティ × 全ロールで作る)が規模の 2 乗で行を増やす。1,000 件で約 100 万行、10,000 件で約 1 億行になり、DB の作成の上限 900 秒を超えて測定そのものが止まる。プロファイルに項目を足す案(参照表を 9 件に固定する)は、項目が増え、煙試験も要る。足しても規模 0 の点が無く式は作れないので、得るものが無い

### D94. 予測を固める置き場は `docs/research/extrapolation-data/<対象>/`(`fits.json`・`predictions.json`)(D72 の委任による戻せる判断)

- 内容:外挿試験(A)の対象(検証用アプリ・BookStack)ごとに、当てはめの結果 `fits.json` と予測 `predictions.json` を `docs/research/extrapolation-data/<対象>/` に置き、100,000 件を測る前に commit する。測定の記録そのもの(`--out`)はリポジトリの外に置く
- 理由:予測を測定より前に固定したと、commit の時刻で示せる。置き場を決めておけば、後から見比べる側が探さずに済む
