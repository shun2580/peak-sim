### 版 0.2 の中での改め(2回目、2026-11-09 08:05)

## 0. 版 1.0 の完成の条件(2026-11-09 メンテナー裁定)

版 1.0 は「現時点でこれ以上はない」水準とする。それを確かめられる形にしたものが、次の 5 つの条件である。すべてを満たすまで版 1.0 としない。条件を緩めるときは、メンテナーが決め、判断記録に理由を残す。

1. **精度(目標の水準で合格する)**
   - 外挿試験(§7.1):まだ見ていない規模で、印の無いルートの 80% 以上が目標(クエリの本数 ±2%・読んだ行数 ±10%)に入る。かつ、全ルートの 80% 以上が最低基準(±5%・±20%)に入る
   - ラボのバックテスト(§7.2):目標(使用率の差の平均 5 ポイント以内、限界の rps が ±10% に入るシナリオ 80% 以上。後者は 2026-11-09 18:32 メンテナー裁定で足した)で合格し、素朴な見積もり(§7.3)に勝つ(2026-11-09 17:05 メンテナー裁定で 10 から 5 に引き締めた。ラボの予測を出す前に決めた。根拠は §7.4)
2. **汎用性**:まだ見ていない 3 本目のアプリ(Bagisto)で、1 と同じ水準で合格する
3. **残った外れは、すべて原因が分かり、事前に印で知らせられる**:1 と 2 を満たした上で残った外れについて、1 本ずつ原因を特定し、ツールが予測の時点で「当たらない恐れがある」と出せる。原因の分からない外れが 1 本でも残れば版 1.0 としない
4. **品質**:公式のツール(`src/`、phar)への移し、試験、README、使い方の文書がそろう。予測の出力に、そのアプリでの精度が必ず付く
5. **記事**:Zenn の記事を 1 本書く(メンテナーが書き、Claude が添削する)

道のり:① ラボのバックテスト → ② 印のあるルートの改善(改善のたびにまだ見ていない規模で確かめる)→ ③ Bagisto での確かめ → ④ 残った外れの原因の特定と印の強化 → ⑤ 公式のツールへの移し・文書 → ⑥ 記事。各段の報告で、条件 1〜3 にあといくつ足りないかを数字で示す

## 1. 目的と、正確さの物差し

目的(D62):自分のアプリの、繁忙期に効く上位のルートについて、コードに基づいて「繁忙期にどこが先に限界に来るか」を予測し、その予測の精度を数字で示す。

正確さは、次の2段で確かめる(D68)。

| | A. 外挿試験 | B. ラボのバックテスト |
| --- | --- | --- |
| 確かめること | 1リクエストのコストの見積もりが、大きなデータ量でも当たるか | 繁忙期の DB の使用率が当たるか |
| 方法 | 小さな規模の情報から大きな規模の値を見積もり、見積もりを記録してから実測する | 平常時のシナリオで較正し、繁忙期のシナリオを予測してから、実際に負荷をかけて測る |
| 対象 | 検証用アプリと BookStack。改善の効果は、まだ見ていない Bagisto で確かめる(§7.5) | BookStack(§7.2) |
| 公開 | できる | できる |

A と B の確かめ方は、利用者が自分のアプリで回せるツールの機能にもする(§8)。

業務のアプリは使わない(D69)。

先行事例との関係(prior-art §3.1・§4):調べた 63 件の中に、軸 D(繁忙期の限界の予測)と軸 E(過去の実績と比べた精度)で `yes` のものは無かった。ただし学術データベースは直接検索しておらず、日本語の情報源も見ていない(§6)。Verriet et al.(ICPE 2018、静的解析によるプロファイル+回帰)は全文を読んでいない。公開の文書で新しさを書く前に、この論文の全文を読み、補足の検索をする。

ラボのバックテストは本番の実績ではないので、軸 E の `yes`(過去の実際の結果との比較)には当たらない。公開の文書では「ラボで再現した繁忙期での照合」と書き、本番での精度とは書かない。

## 2. 全体の流れ

```
1. 静的解析(コード)
     ルートごとに、どの表が N か、どの文がどのループの中で何回呼ばれるか
        │
2. 文の捕捉(小さな規模で1回だけ実行)
     実際に発行された SQL・束縛値・文ごとの読んだ行数を、文の型ごとに記録
        │
3. 実行計画の見積もり(目標の規模の DB で EXPLAIN だけ。リクエストは実行しない)
     文ごとの実行計画と読む行数の見積もり。統計の状態を変えて揺れを調べる
        │
4. コストの式
     クエリの本数 = 静的解析の回数(足りなければ当てはめ)
     読んだ行数   = Σ 文ごと(EXPLAIN の見積もり × 本数)(EXPLAIN が使えない文は当てはめ)
        │
5. 較正(平常時の観測点) ──→ 本数・行数から DB の CPU への換算
        │
6. 予測(繁忙期のシナリオ) ──→ 限界に来る資源・倍率・主因ルート(幅つき)
        │
7. 確かめ(selfcheck:見積もりと実測の差 / backtest:予測と実績の差)
```

- コードが主である。予測の根拠は、静的解析が出す構造と、DB の実行計画に置く
- 実際の実行は、2 の文の捕捉(小さな規模で1回)と、7 の確かめと、EXPLAIN が使えない文の穴埋めに限る
- ローカルで測った時間は本番の機材に持ち込めない。扱うのは機材に左右されない量(クエリの本数・読んだ行数・メモリ)に限り、時間や使用率への換算は較正だけで行う

## 3. 入力

### 3.1 構造(静的解析の出力)

既存の解析器(`peak-sim analyze`)の出力を使う。ルートごとに次を取る。

- 増え方の軸と、N(M)となる表
- 増える箇所(file:line)と、その箇所の文がどのループの中にあるか
- 測るのに要るもの:ルートの引数、認証の要否、書き込みかどうか

静的解析で形(どの表で、どの次数で増えるか)が決まったルートの割合を、出力に必ず出す(§6.4)。この割合を上げることが、「コードが主」の度合いを上げることになる。

### 3.2 実測するルートの選び方

- 利用者がシナリオファイルに rps を書いたルートを、対象とする。ツールが勝手に足したり減らしたりしない
- コストを見積もれなかったルート(§4)は「コスト不明」として、rps の割合とともに列挙する
- **コスト不明のルートの rps が、そのシナリオの rps の合計の 20% を超えたら、そのシナリオの予測に `low_coverage` を付け、CLI の表示の先頭に警告を出す**。予測は出すが、黙って通さない
- 補助として、静的解析の重さ(下限の次数)でルートを並べた候補の一覧を出すコマンドを用意する。シナリオの雛形を作るためのもので、選ぶのは利用者

### 3.3 プロファイル

D64 のとおり、対象のルートについて利用者が書く。形式は `poc/runtime/profiles/` の形(`values`・`skip`・`rows`)を引き継ぐ。項目数は記録に必ず載せる(D57 と同じ)。

### 3.4 シナリオファイル(YAML、`schema_version: "0.1"`)

時間帯ごとの状態を書く。較正用(`calibration`)と予測用(`target`)を分ける。

```yaml
schema_version: "0.1"
resources:
  db_cpu:
    cores: 2              # DB に割り当てた CPU の数(必須)
    threshold: 0.8        # 使用率の閾値(既定 0.8)
  php_memory_limit: 128M  # 既定は対象アプリの php.ini の値。読めなければ必須

scenarios:
  - id: normal-1
    kind: calibration
    tables: { pages: 10000, books: 500 }
    rps: { "GET /books/{slug}": 5.0, "GET /search": 1.0 }
    observed: { db_cpu_utilization: 0.21 }   # 較正用は必須
  - id: peak-1
    kind: target
    tables: { pages: 100000, books: 3000 }
    rps: { "GET /books/{slug}": 15.0, "GET /search": 6.0 }
    observed: { db_cpu_utilization: 0.74 }   # 任意。backtest のときだけ書く
```

- ルートは「メソッド + URI」で書く。静的解析の出力に無いルートが書かれていたら、エラーで止める(終了コードは実装で決める)
- `target` の `observed` は、予測を出し終えて記録するまでツールが読まない。読み込みの順序を試験で縛る
- シナリオに書かれていないルートの rps は 0 とし、その旨を出力に書く
- 件数が書かれていない表は「件数不明」として列挙し、勝手に小さいと仮定しない(spec.md フェーズ2と同じ)

## 4. コストの見積もり

### 4.1 扱う量

| 量 | 主な求め方 | 補助 | 用途 |
| --- | --- | --- | --- |
| クエリの本数 | 静的解析が出す回数(ループの倍数) | 当てはめ(§4.5) | DB の負荷 |
| 読んだ行数 | 文ごとの実測(3 規模)からの当てはめ × その文の本数(H1)。印の付いた文は、EXPLAIN の比による値を幅の上側として併記する(§4.3) | — | DB の負荷 |
| ピークメモリ | 当てはめ(§4.5) | — | メモリの限界 |

読んだ行数は **rows examined**(DB が実際に読んだ行数)を指す。返った行数ではない。インデックスが効かない絞り込みでは、2つが桁で違う。

### 4.2 文の捕捉(小さな規模で各1回)

- ルートごとに、小さな規模の DB で cold のリクエストを1回ずつ実行する。規模は当てはめと同じ 100 / 1,000 / 10,000(not_found の 12 ルートは 10 から。D105)
- 文ごとの記録の仕組み(tap。`variance-run` の文ごとの記録)で、次を残す:SQL の型(リテラルを抜いた形)、束縛値、発行された回数、文ごとのハンドラーの数
- 同じ型の文はまとめ、型ごとに1件の代表(SQL と束縛値)を持つ。代表は最大の規模のものを使う
- 文の型ごとの本数が規模でどう増えるかは、この3規模から当てはめる(§4.5)。静的解析で回数が決まる文は静的解析の回数を優先し、当てはめと食い違えば印を付けて出す
- 実測の読んだ行数(ハンドラーの数)の測り方と照合の試験は、これまでの決めごと(D73・D96・D101・D102)を引き継ぐ

### 4.3 実行計画の見積もり(目標の規模の DB で EXPLAIN)

- 目標の規模の DB を生成器で作り、捕まえた型ごとの代表の SQL を、束縛値つきで `EXPLAIN FORMAT=JSON` にかける。リクエストは実行しない。捕捉の最大の規模(10,000 件)でも同じ文を EXPLAIN する
- EXPLAIN は点の見積もりに使わない(版 0.2 の中での改め、2回目)。印の付いた文についてだけ、「10,000 件での実測 × 目標の規模の見積もり ÷ 10,000 件の見積もり」を幅の上側として出す。比を使う式(H2・H3)は、開発中の確かめで H1 より当たらなかった(`docs/research/explain-estimate.md` §10)
- EXPLAIN の見積もりの絶対値を主にする式(C1〜C3)の結果は `docs/research/explain-estimate.md` に残す。主の求め方には使わない
- 束縛値が目標の規模の DB に存在しない、または EXPLAIN にかけられない文は「EXPLAIN 不可」とし、理由を記録して §4.5 の当てはめで補う
- 小さな規模と目標の規模とで、実行計画(使う索引、`type`)が変わった文には `plan_changes_at_scale` の印を付ける

### 4.3.1 offset の塊読みの印 `offset_chunk_fit`(2026-11-24 メンテナー裁定。Bagisto の見積もり・予測を出す前に決めた)

- 実行計画の印(`plan_changes_at_scale`・`plan_unstable`)とは別の印。`limit … offset …` で表を塊ごとに読む文を持つルートについて、見積もりの式がその文の読む行を、捕捉した件数の範囲の中で追えているかを見る。捕捉と見積もりだけから作り、データベースにも EXPLAIN にも、捕捉の最大より大きい件数の測りにも触れない
- 規則(ルートごと):(1) 文の本文(型の pattern、または代表の SQL)に `offset` を含む文を拾う。(2) その文ごとに、捕捉の最後の1点を外し、手前の点だけで回数と1回の行を見積もりと同じ式(`CostFit`)で当て直し、外した件数に置いた値の積(回数 × 1回の行)を、捕捉の実の積と比べる。相対誤差を取り置き誤差 e とする。4 つより少ない件数でしか捕捉していない文は e を持たず、印に数えない。(3) 目標の件数で2回以上走る文だけを数える(1回だけの `limit 20 offset 0` は頁寄せで、塊読みではない)。(4) ルートの値 S = 数える文ごとの「その文の読む行 ÷ ルートの読む行」×|e| の和。(5) S が 0.10 以上のルートに印を付ける。0.10 は行数の目標(±10%)で、この規則のために選んだ数ではない
- 見積もりが完結しないルート(見積もりの数が出ない型 `unavailable` を一つでも持つ、または offset の文の型が見積もりに載っていないルート)は、割合の分母が決まらないので、その文をすべて数えず(`not_counted_because: route_incomplete`)、S は出さず(0 のまま)、印も付けない。このとき印が無いことは安全を意味しない
- 出し方:`bin/estimate --candidate=H1_RANGE` の出力の各ルートの `offset_chunk_fit`(`marked`・`score`・文ごとの `share`・`held_out_error`・`counted`)と、`bin/marked-routes --estimate` の一覧。`offset` を含む文の無いルートには項目を付けず、見積もりの数と他の印は変えない。シミュレーターの出力(§6.4)・限界の値・使用率はこの版では変えない
- 印の形は外れを知った後に選んだものであり、「回数 2 以上」の限定も結果を見た後に足したものであり、240,000 件の BookStack に当てた「印 2・当たり 2・空振り 0」は既に見た記録への当てはめで試験ではなく、効き目はまだ見ていないアプリ(Bagisto)でしか確かめられない。限り:取り置きの外挿は 3 倍(10,000→30,000)だが 240,000 件の見積もりは 8 倍の外挿ゆえ、e は実の外れより小さく出て S は低めに出る。印が無いことは安全を意味しない。式の折れが捕捉の最大より上にあるアプリの外れは見えない
- 印は取り置きの当てはめの係数を丸めずに使うが、見積もりは係数を有効数字 12 桁に丸めて(`CostFit::sig`)から件数に置く。`offset` の文を持つ BookStack の 9 ルートで e の差は最大 1.2e-12 で、S も印も変わらなかった。印が変わり得るのは、S が 0.10 の約 1e-11 以内にあるときだけである

### 4.4 統計による実行計画の揺れ(D107)

- 目標の規模の DB で、統計の状態を変えて、同じ文を複数回 EXPLAIN する。状態の作り方の既定:`ANALYZE TABLE` を既定の標本数・少ない標本数・多い標本数の3通りで行い、それぞれの後に EXPLAIN する。状態の作り方の細部は実装で決め、判断記録に残す
- 状態によって実行計画が変わった文には `plan_unstable` の印を付け、状態ごとの見積もりをすべて記録する
- 限界の予測には、`plan_unstable` の文について重い方(読む行数が多い方)の見積もりを使う。両方の値と印は、出力に必ず出す
- 根拠:統計を固めると揺れが消え、統計が取り直されると実行計画が切り替わった(`docs/research/variance-investigation.md` §4.7。1つの DB・固まった試行 15 本という限定つき)

### 4.5 当てはめ(補助)

これまでの当てはめ(D73〜D89、D105)を、補助として残す。

- 使う場面:クエリの本数を静的解析で決められないルート、EXPLAIN 不可の文、ピークメモリ
- 規模:N 軸は 100 / 1,000 / 10,000。not_found の 12 ルートは 10 / 100 / 1,000 / 10,000(D105)。子の表の軸は 3 / 30 / 300
- `y = a + b·N^k` を当てはめ、a・b・k と残差を出す
- 静的解析の下限と食い違ったら(例:静的解析は O(N) 以上なのに、実測の k ≤ 0.2)、その式は採らずに「食い違い」として出す。偽の O(1) を採らないため(D21)
- 測れなかったルートは、理由つきで列挙する。シミュレーションでは「コスト不明」とし、0 として足さない

### 4.6 見積もりの出どころ

値ごとに、どこから来たかを出力に付ける:`static`(静的解析)/ `explain`(EXPLAIN の見積もり)/ `fit`(当てはめ)/ `unknown`(コスト不明)。

## 5. 較正

ある時間帯の DB の負荷を、次の式で表す。

```
L = Σ_r λ_r · ( c_q · 本数_r(N) + c_row · 行数_r(N) )
    λ_r : ルート r の rps(シナリオの値)
    N   : そのシナリオの表の件数
DB の使用率 = L / cores
```

- 較正用シナリオが2本以上あるとき:観測値に合わせて c_q と c_row を、負にならない最小二乗で決める(2係数)
- 較正用シナリオが1本のとき:2つの係数は決められない。本数だけの1係数(`L = c · Σλ·本数`)と行数だけの1係数(`L = c · Σλ·行数`)の両方で予測し、2つを予測の幅に含める。重みを勝手に仮定しない。2係数の較正ができるときは、1係数の較正を使わない(2026-11-09 改め)
- 係数が負に張り付いた(0 に切り詰めた)ときは、その係数に印と警告を付けて使う。黙って 0 のまま使わない(2026-11-09 改め。当初は「エラーで止める」としていた)
- 較正の残差を出力に書く

## 6. 予測と限界の判定

### 6.1 DB の CPU

- 予測用シナリオごとに使用率を出す
- そのシナリオの rps を全ルート同じ倍率で上げていき(0.1 刻み、上限 10 倍)、使用率が閾値を超える最初の倍率を「限界の倍率」として出す。10 倍で超えなければ「10 倍まで超えない」と出す
- 限界の倍率は、点の見積もりでの値と、印のあるルートを幅の上側に置き換えた値(安全側の値)の2つを出す。主に示すのは点の値で、安全側の値を並べる
- 主因ルート:そのシナリオでの L のルートごとの割合の上位5本。影響度 = rps × コスト(prior-art 5.2 の Scout の方式)。主因ルートには、負荷の大きい文と、その文の印(`plan_unstable`・`plan_changes_at_scale`)を添える

### 6.2 PHP のメモリ

- ルートごとに、ピークメモリが `php_memory_limit × 0.8` を超える件数 N を出す(トラフィックには依らない)
- §7.1 の外挿試験で、メモリの誤差が最低基準(±30%)に入ったルートだけを出す。入らなかったルートは「精度不足のため出さない」と書く
- 上の2行は、件数 N を出すかどうかの規則である。印 `app_limit_risk` のメモリ側(§6.4・D196)は、この規則に従わない。印は見逃してはならぬ警告なので、ピークメモリの式が ±30% に入らなかったルートや、どの試験でも測れなかったルートも、同じ係数で判定する(係数は ±30% の内外のルートを合わせた最大の比から決めた)

### 6.3 予測の幅

乱数を使わず、同じ入力から同じ幅が出る方法で作る(spec.md の再現性の要件)。

- 見積もりの幅:`plan_unstable` の文は、統計の状態ごとの見積もりの最小〜最大。当てはめで補った値は、3 規模すべての式と、2 規模ずつの 3 通りの式(計 4 本)の最小〜最大
- 較正の幅(2026-11-09 改め):較正用シナリオが3本以上なら、1本ずつ抜いた2係数の較正の範囲。2本なら「較正の幅は出せない」と明示し、較正の幅は置かない。1本なら §5 の 1 係数の 2 通り。当初の「2係数に 1 係数の 2 通りを混ぜる」形は、幅を不当に広げたため改めた
- 出力に、幅の倍率(上端 ÷ 点、点 ÷ 下端)と、幅の内訳(見積もりの幅だけ・較正の幅だけでそれぞれどれだけ広がるか)を出す
- 予測値:点の見積もり(H1)× 2 係数の較正(1本のときは、2 通りの中央)。印のあるルートは、幅の上側(H2)でも同じ計算をし、「上側での予測」として並べて出す(2026-11-09「版 0.2 の中での改め、2回目」に合わせた。20 万件の試験で上側は 19 本中 17 本で実測の最大を上回った)
- 幅:見積もりと較正のすべての組み合わせで出した値の最小〜最大
- 合格基準(§7.4)の判定には、予測値を使う。幅は使わない

### 6.4 出力に必ず含めるもの

- 予測値と幅
- 値ごとの出どころ(§4.6)と、印:`measured`(測った規模の中)/ `interpolated`(測った規模の間)/ `extrapolated`(測った規模の外)。prior-art 5.2 の Oracle の方式
- 文ごとの印:`plan_unstable`・`plan_changes_at_scale`・EXPLAIN 不可
- 静的解析で形が決まったルートの割合・EXPLAIN で見積もった割合・当てはめで補った割合・コスト不明の割合(ルート数と rps の割合の両方)
- 結果を最も左右した入力:各入力(表の件数、ルートごとの rps)を +10% 動かしたときの、限界の倍率の変化の大きい順に上位5つ
- コスト不明のルート、件数不明の表、rps が 0 とされたルート、`low_coverage` の有無
- 較正の方式(2 係数 / 1 係数)と残差
- そのアプリでの精度(§8.1 の selfcheck の最新の結果。無ければ「未確認」と出す)
- アプリの上限の印 `app_limit_risk`(2026-11-11 メンテナー裁定で足した):目標の件数で、あるルートが DB より先にアプリの上限(PHP の実行時間など)で落ちる恐れがあるときに付ける。上限の値は予測の入力として受け、ツールの定数にしない。限界の rps を出す行には、印の付いたルートを必ず並べ、「この限界の rps は印のルートが最後まで終わるものとして数えた値」と書く(R1a)。使用率と限界の rps の値そのものは変えない
- アプリの上限の印のメモリ側(2026-11-16 メンテナー裁定で足した・D196):PHP の `memory_limit` に届く恐れがあるルートに付ける。上限は予測の入力 `resources.app_memory_limit` で受け、既定値を埋めない(無ければメモリ側は作らず、出力は 1 バイトも変わらない)。規則は「予測ピークメモリ(§6.2 の当てはめの値)× 1.51 ≥ 上限」(1.51 は第 2 外挿試験の「実測ピーク ÷ 予測」の最大の比。根拠は `docs/research/lab-data/diagnosis/app-memory-risk/`)。ピークメモリの見積もりが無いルートは判定せず、別に並べる(危険なしとは数えない)。CPU 時間の側(`app_limit_risk`)とは別のブロック(`app_limit_risk_memory`)で出し、どちらの上限で付いたかをブロックで示す。式は起動済みアプリのメモリを含まぬ(実測のピークが、リクエスト開始前の使用量を引いた値のため)

## 7. 正確さの確かめ方

### 7.1 A. 外挿試験

- 小さな規模の情報(文の捕捉と当てはめ)と、目標の規模の DB の EXPLAIN から、1リクエストのクエリの本数・読んだ行数・ピークメモリを見積もり、見積もりを commit してから、その規模で実測して比べる
- 版 0.2 の最初の外挿試験は、D104 のとおり、まだ測っていない 200,000 件で行う。合格線(D71・D95)は変えない
- 対象:検証用アプリと BookStack のうち、コストを見積もれたルート。not_found の 12 ルートも分母に入れる(D105)
- 1回目の外挿試験(版 0.1・100,000 件)の結果は動かさない(D103)。100,000 件の既存の記録は、開発中の確かめに使ってよいが、合否には使わない(既に結果を見ているため)

**200,000 件の測り方(2026-11-09 08:05 に固定。200,000 件のデータを見る前に決めた)**

- 印のあるルート:200,000 件の EXPLAIN で、`plan_changes_at_scale` または `plan_unstable` の付いた文を 1 つでも含むルート。一覧は見積もりと一緒に commit する
- すべてのルートを、1回目の外挿試験と同じ測り方(cold を 1 回)で測る。印のあるルートは、さらに同じ 200,000 件の DB で cold を 3 回測る
- **合否を決める規則(規則 B)**:印の無いルートは cold 1 回の値と比べる。印のあるルートは、200,000 件で測った cold の値すべて(1 回 + 3 回)の最大値と比べる。理由:限界の予測は重い方の実行計画を出す決まり(D107)であり、比べる相手も重い方にそろえるため。許す誤差・分母・合格線(D71・D95)は変えない
- **並べて出す規則(規則 A)**:すべてのルートを cold 1 回の値と比べる(1回目の外挿試験と同じ規則)。合否には使わないが、必ず並べて出す
- 割合は、全体・印の無いルート・印のあるルートの 3 つに分け、最低基準と目標の両方で出す
- 統計の自動の取り直しは既定(有効)のままにする

- t-2・t-3・t-5 はデータ量を伸ばす。素朴な見積もりが見落とす条件

測り方:

- 較正用シナリオは 10 分間の一定の到着率で負荷をかけ、最初の 2 分は捨てる。予測用シナリオは上の段で測る
- 予測は、予測用シナリオを測る前に出し、ファイルにして commit する。その後で測る。予測には、すべての予測用シナリオのすべての段の使用率(点と、印のあるルートを上側に置いた安全側の値)と、限界の rps(点と安全側)を入れる
- 限界の rps:そのシナリオの件数と混ざり方で、DB の使用率が閾値(80%)に届く rps の合計。件数と混ざり方を決めると負荷は rps に比例するので(§5 の式)、0.1 刻みの倍率ではなく、比例の式から直接解く
- 決めた rps が実際に出たか(±5% 以内)を段ごとに確かめる。出なかった段は「無効」として記録し、黙って使わない
- 実測の限界の rps:使用率が 80% をまたぐ、有効な 2 つの段の間を直線で補って求める。80% 以上の段が無効だったときは、有効な段のうち rps の大きい 2 つから直線で延ばして求め、延ばしたことを記録する。有効な段が 2 つ未満のシナリオは、限界の rps を「測れず」とする
- 判定不能:使用率の差に使える段(下の §7.4 B)が 10 段未満、または限界の rps を測れたシナリオが 4 本未満なら、B は「判定不能」とする。合格とは扱わない

ラボで言えないこと:本番に特有の効果(キャッシュの効き方、DB のメモリに収まらないデータの読み込み、他の処理との取り合い、書き込みの負荷)。これらは報告に必ず書く。

### 7.3 素朴な見積もり(比べる相手)

```
繁忙期の使用率(素朴) = 較正用シナリオの使用率 × (予測用シナリオの rps の合計 ÷ 較正用シナリオの rps の合計)
```

較正用シナリオが2本あるときは、rps の合計が大きい方を使う。同じなら、使用率の観測値が大きい方を使う。ラボ(§7.2)では、件数が N_0 の較正用シナリオ(cal-1〜3)だけから選ぶ(cal-4 は件数が違うので使わない。2026-11-10 08:35 メンテナー裁定)。データ量の伸びとルートの混ざり方を無視した見積もりで、peak-sim がこれに勝てなければ、コードを読む意味が示せない。

### 7.4 精度の基準(D71・D108。データを見る前に固定する)

基準は2段に置く。**最低基準**は合否の線で、これを下回ったら直す。**目標**は「精度の高いツール」と名乗る線で、届くまで改善を続ける(§7.5)。

**A(外挿試験)**:対象のルートの 80% 以上で、見積もりが次の誤差に収まること。合否はクエリの本数と読んだ行数で決める(D95)。ピークメモリは §6.2 で使うルートを選ぶためにだけ使う。

| 量 | 最低基準 | 目標 |
| --- | --- | --- |
| クエリの本数 | ±5% | ±2% |
| 読んだ行数 | ±20% | ±10% |
| ピークメモリ | ±30% | ±30% |

**B(ラボのバックテスト)**:予測用シナリオの有効な段のうち、実測の使用率が 10% 以上 90% 以下の段(使用率の差に使える段)と、限界の rps を測れたシナリオについて、次をすべて満たすこと(2026-11-09 18:32 メンテナー裁定で段の測り方に合わせて改め、項目 4 を足した。ラボの予測を出す前に決めた)。

| 項目 | 最低基準 | 目標 |
| --- | --- | --- |

- **DB の上限で動かぬルートの扱い(B)**:B の件数で、B の設定のもとで印が付くルート(プレースホルダの側、メモリ 4G の側)は「動かない」と印で報告し、B のシナリオの配分から外す。外したルートの割合は、同じシナリオの同じ組(80% の組・20% の組、または均等)の残りのルートに、元の割合に比例して配り直す。素朴な見積もりも同じ配分で出す。外すルートと配り直した配分は、予測だけから決め、予測のファイルに理由とともに書く。組が空になるシナリオが出たら、測らずに止まって知らせる
- **B の要求の時間切れ**:B の設定の要求の時間切れ(k6 の要求の時間切れ・nginx の fastcgi_read_timeout・段の終わりの待ち)を 1,800 秒にする。CPU 時間の印が予測する 1 要求の時間が 1,800 秒の半分(900 秒)を超えるルートがあれば、測らずに止まって知らせる
- **件数**:B = **160,000 件**(捕捉の最大 30,000 の 5.33 倍。5 倍以上で、10,000 刻みのうち、まだ見ていない最小の件数。150,000 は印の試験で使い切り)。外挿試験 A = **240,000 件**(8 倍)。どちらも、これまでの記録(構築・見積もり・測定のいずれか)に現れた件数なら、測らずに止まって知らせる
- **構築の手順に references の作り直しを入れる**:BookStack のラボの DB は、構築 → `regenerate-references` 相当の作り直し(アプリの保守の処理)→ ANALYZE の順で作る。捕捉の DB(100・1,000・10,000・30,000 件)と、予測・測定の DB の両方に同じ手順を使う。手順を変えるので、BookStack の捕捉は取り直す(開発用のデータであり、試験の件数を使わない)。測定中に、他のルートが読む表の状態を変えるルートは、他のルートの後に測るか、測りの後に元の状態へ戻してから次を測る。どちらにしたかを記録に書く
- **前提として利用者に示すこと**:捕捉した DB と予測の対象の DB は、同じ保守の状態(作り直し・集計の処理を終えた状態)であること。README と出力の注記に書く
- **見積もりの規則の直し**:外挿試験 3 の原因(`docs/research/extrapolation-test-3-causes.md` の P1・P2、および P4 の調べで原因が確定したもの)に基づいて直す。規則は既に見た件数の記録だけから決める。既に見た件数に当てた結果は「当てはめの確かめ」であり、試験ではない。試験は 240,000 件の A で行う
- 較正(cal-1〜7)・合格線・許す誤差・段・窓・判定の規則は変えない
- **改め(2026-11-19 12:10 メンテナー裁定。160,000・170,000・240,000 の見積もり・予測を出す前に決めた)**:
  - B の件数を **170,000 件**(捕捉の最大の 5.67 倍)に改める。160,000 は、作り話の入力で見積もり・予測を流した試運転の出力に件数として現れており、上の「止まって知らせる」の字面に当たるため。170,000 は規模としての出現 0 を確かめた。A の 240,000 は変えない
  - 「構築の手順に references の作り直しを入れる」は取り消す。作り直しを流すと、生成したデータの本文に互いのリンクが無いため `references` が全件数で 0 件になり、既に見たすべての記録とデータの形が変わり、references を読むルートが件数に依らなくなって試験が易しくなるため。代わりに、捕捉・予測・測定のどの DB も作り直しを流していない同じ状態で揃える。他のルートが読む表の状態を変えるルート(作り直しのルートを含む)は、他のルートの後に測る。捕捉の DB のうち、そのルートの後に取ったものがあれば取り直す
  - 利用者に示す前提(同じ保守の状態であること)は残す。ラボの生成データは本文に互いのリンクを持たないことを、ラボの限界として結果の文書に書く

### 7.4.5 6回目の B に向けた決め(2026-11-21 メンテナー裁定。新しい件数の予測を出す前に決めた)

5回目の B(170,000 件)の項目 4 の外れの原因を記録から割り振った結果(`docs/research/lab-backtest-5-causes.md`)を受けて、次を決める。

- **原因の読み**:1 要求の見積もりは約 5% 以内で当たっており、外れの多くは窓の縁(捨てる最初の 60 秒より長い要求のこぼれと待ち)にある。予測は定常の負荷での使用率を出しており、本番の負荷は切れ目なく続く。ラボの窓の縁はラボの作りによるもので、予測に入れるべきものではない
- **採る直し(案 B-準備)**:使用率の定義(窓の中の DB の CPU 時間)と合格線・判定の規則は変えない。各段の「捨てる最初の時間(準備)」を、その段の配分に入るルートのうち、CPU 時間の印が予測する 1 要求の時間の上界が最大のもの以上にする(60 秒を下回らない)。準備の長さは予測のファイルだけから決め、予測の commit に書く。測りの結果で変えない
- **定常に達したことの記録**:各段の記録に、窓の始まりの時点で走っていた要求の数と、窓の終わりの時点で走っていた要求の数をルートごとに残す。合否には使わない(読みの資料)
- **これまでの合否との関係**:準備の長さが違うため、1〜5 回目の B の合否とは並べて比べない。これまでの合否は変えない。条件 1b は §7.4.4 の数え方(捕捉の最大の 5 倍以上・まだ見ていない件数・目標で合格)のまま
- **件数**:B は、捕捉の最大(30,000)の 5 倍以上で、10,000 刻みのうち、これまでの記録(構築・見積もり・測定・試運転の出力)に規模として現れていない最小の件数とする。確かめ方は D223 と同じ型(二人が別々に)
- **予行**:本番の前に、既に見た件数で、新しい準備の長さの測りと判定の台本が最後まで通ることを確かめる(§7.4.4 の予行と同じ扱い)
- 案 A(予測に窓の縁を入れる)は採らない。案 C(限界の定義の見直し)は版 1.0 の後に検討する。準備を伸ばしても残る外れが、DB のコアを重い要求どうしで分け合うこと(案 A-4 の読み)で説明できるなら、それは本番にもある現象なので、次の段で予測の式への取り込みを検討する

### 7.5 目標へ近づける改善の進め方

- 最低基準に通った後も、目標に届くまで改善を続けてよい。回数の上限は置かない
- 改善の効果は、改善するときに見ていないデータで確かめる。同じデータで直して確かめると、そのデータに合わせただけになるため
- 確かめに使うデータは、まだ見ていないルート → まだ見ていない規模 → まだ見ていないアプリ(Bagisto)の順に足していく
- Bagisto を使うときは、測定用の PHP のイメージ(PHP 8.4 以上)を別に作る(`poc/runtime/README.md` の手順)。対象に足すことは、始める前に判断記録に残す
- 改善の候補(分かっている範囲):DB のメモリに収まらなくなる規模での急な悪化の扱い、全件の走査と索引での引きとで1行あたりの重さが違うことの較正、静的解析で形が決まるルートの割合を上げること

## 8. 精度を確かめる機能(D109)

### 8.1 `selfcheck`

- 利用者のアプリで、§7.1 と同じ手順を回す:小さな規模の情報と目標の規模の DB の EXPLAIN から見積もりを出し、見積もりを記録してから、その規模で実測して比べる
- 出すもの:量ごとの誤差の分布、最低基準・目標に入ったルートの割合、`plan_unstable` の文の数、EXPLAIN 不可の文の数
- 結果は保存し、§6.4 の「そのアプリでの精度」として予測の出力に添える
- 実測は重い(1リクエストに数分かかることがある)ので、対象のルートと規模は利用者が選べるようにする

### 8.2 `backtest`

- 利用者がシナリオファイルの `target` に `observed`(過去の繁忙期の実績)を書いたときに使う
- 予測を出して記録した後で実績を読み、差と、素朴な見積もり(§7.3)との比較を出す
- 予測と実績の読み込みの順序は、試験で縛る(§3.4)
- 私たちが行う B(ラボのバックテスト)は、この機能をラボのデータで回したものとする

## 9. MVP で扱わないもの

- PHP のワーカー数、DB のコネクション数、キューの滞留(応答時間が要り、ローカルで測った時間は本番に持ち込めない)。spec.md フェーズ3のジョブとコマンドの試算も、MVP では扱わない
- 書き込みのルートの負荷(§7.2)
- 同時実行数と処理量の曲線(USL、prior-art 5.8)。本番相当の環境で負荷を測る必要があるため
- 大きな DB を統計値の拡大で模擬する方式(prior-art 5.9)。有効な特許として載っているため採らない。データは生成する。EXPLAIN をかける目標の規模の DB も、生成器で実際に作る

## 10. 実装の順序

各段の終わりに、動いた結果を記録してから次に進む。

1. 文の捕捉(§4.2)を `poc/runtime/` の正規の段にする。既存の tap を土台にし、型ごとの代表の SQL と束縛値を出力に残す
2. 目標の規模の DB での EXPLAIN と、統計の状態を変えた EXPLAIN(§4.3・§4.4)。`plan_unstable`・`plan_changes_at_scale` の印
3. 開発中の確かめ:100,000 件の既存の記録(外挿試験の1回目と、続く揺れの調べ2回の記録)と比べて、EXPLAIN の見積もりがどこまで合うかを見る。合否には使わない(§7.1)。ここで EXPLAIN からの求め方(§4.3)を決め、判断記録に残す
4. D105(not_found の 12 ルートの当てはめ)の実装
5. 版 0.2 の外挿試験 A を 200,000 件で行う(D104)。見積もりを commit してから測る
6. シナリオファイルの読み込み、較正、予測、幅、出力(§3.4・§5・§6)
7. `selfcheck`・`backtest` のコマンド(§8)
8. ラボの環境(§7.2)。ルートの一覧の commit → R_0 の決定 → 予測の commit → 予測用シナリオの測定 → B の合否
9. 目標へ近づける改善(§7.5)

A が最低基準に届かなければ、8 に進む前に止まって報告する(1リクエストのコストが当たらない状態で負荷をかけても、B の結果の意味が読めないため)。

## 11. 戻せる判断として決めたこと(D72)

メンテナーの委任により、次は推奨の形で決めた。結果を見て変えるときは、判断記録に理由を書き、見ていないデータで確かめ直す。

- 実測するルートは、利用者がシナリオに書いたもの。コスト不明の割合が 20% を超えたら警告(§3.2)
- 較正用シナリオが1本のときは、重みを仮定せず、本数だけ・行数だけの両方を幅に含める(§5)
- 予測の幅は、乱数を使わない組み合わせの最小〜最大(§6.3)
- 読んだ行数の実測は `Handler_read_*` の差分で測り、`performance_schema` で照合する(§4.2)
- シナリオファイルは §3.4 の形を `schema_version: "0.1"` とする
- ラボのシナリオの中身と、ルートの選び方(§7.2)
- 文の捕捉は当てはめと同じ3規模で各1回とし、文の型ごとの本数はその3規模から当てはめる(§4.2。2026-11-09、1つの規模だけでは本数の増え方が分からないため改めた)。統計の状態の作り方の既定は、ANALYZE の標本数を3通りに変えること(§4.4)
- ラボでは統計の自動の取り直しを既定のまま有効にする(§7.2)
