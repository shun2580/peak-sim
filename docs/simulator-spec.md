# 繁忙期シミュレーター 仕様

2026-11-04 · @shun

状態:確定(版 0.1)。大きな方向は殿が決め(判断記録 D68〜D71)、細部は殿の委任により推奨の形で決めた(D72)。細部は戻せる判断として置く。変えるときは判断記録に理由を残す。

前提:判断記録 D62(目的の作り直し)、D64(実測ではプロファイルを書く前提)、D65(`poc/runtime/` を係数の測定の土台にする)。先行事例は `docs/research/prior-art.md`(2026-11-04 調査)。この文書は `spec.md` のフェーズ3(繁忙期シミュレーター)を置き換える。

## 1. 目的と、正確さの物差し

目的(D62):自分のアプリの、繁忙期に効く上位のルートについて、コードに基づいて「繁忙期にどこが先に限界に来るか」を予測する。

正確さは、次の2段で確かめる(D68)。

| | A. 外挿試験 | B. ラボのバックテスト |
| --- | --- | --- |
| 確かめること | コストの式が、大きなデータ量でも当たるか | 繁忙期の DB の使用率が当たるか |
| 方法 | 小さな規模で当てはめ、より大きな規模の値を予測してから実測する | 平常時のシナリオで較正し、繁忙期のシナリオを予測してから、実際に負荷をかけて測る |
| 対象 | 検証用アプリと BookStack | BookStack(§7.2) |
| 公開 | できる | できる |

業務のアプリは使わない(D69)。

先行事例との関係(prior-art §3.1・§4):調べた 63 件の中に、軸 D(繁忙期の限界の予測)と軸 E(過去の実績と比べた精度)で `yes` のものは無かった。ただし学術データベースは直接検索しておらず、日本語の情報源も見ていない(§6)。Verriet et al.(ICPE 2018、静的解析によるプロファイル+回帰)は全文を読んでいない。公開の文書で新しさを書く前に、この論文の全文を読み、補足の検索をする。

ラボのバックテストは本番の実績ではないので、軸 E の `yes`(過去の実際の結果との比較)には当たらない。公開の文書では「ラボで再現した繁忙期での照合」と書き、本番での精度とは書かない。

## 2. 全体の流れ

```
静的解析 ──→ ルートごとの構造(どの表が N か・どこで増えるか・測るのに要る引数と認証)
    │
実測(シナリオに載ったルートだけ・プロファイルつき) ──→ コストの式(本数・読んだ行数・メモリ の係数)
    │
較正(平常時の観測点) ──→ 本数・行数から DB の CPU への換算係数
    │
予測(繁忙期のシナリオ) ──→ 限界に来る資源・倍率・主因ルート(幅つき)
    │
確かめ(A 外挿試験 / B ラボのバックテスト)
```

ローカルで測った時間は本番の機材に持ち込めない。測るのは機材に左右されない量(クエリの本数・読んだ行数・メモリ)に限り、時間や使用率への換算は較正だけで行う。

## 3. 入力

### 3.1 構造(静的解析の出力)

既存の解析器(`peak-sim analyze`)の出力を使う。ルートごとに次を取る。

- 増え方の軸と、N(M)となる表
- 増える箇所(file:line)
- 測るのに要るもの:ルートの引数、認証の要否、書き込みかどうか

静的解析の判定(O(1)/O(N)/unknown)は、「どの表を動かして測るか」を決めるために使う。増え方の指数そのものは実測で決める(§4)。

### 3.2 実測するルートの選び方

- 利用者がシナリオファイルに rps を書いたルートを、実測の対象とする。ツールが勝手に足したり減らしたりしない
- 式が作れなかったルート(§4)は「コスト不明」として、rps の割合とともに列挙する
- **コスト不明のルートの rps が、そのシナリオの rps の合計の 20% を超えたら、そのシナリオの予測に `low_coverage` を付け、CLI の表示の先頭に警告を出す**。予測は出すが、黙って通さない
- 補助として、静的解析の重さ(下限の次数)でルートを並べた候補の一覧を出すコマンドを用意する。シナリオの雛形を作るためのもので、選ぶのは利用者

### 3.3 プロファイル

D64 のとおり、実測するルートについて利用者が書く。形式は `poc/runtime/profiles/` の形(`values`・`skip`・`rows`)を引き継ぐ。項目数は実測の記録に必ず載せる(D57 と同じ)。

### 3.4 シナリオファイル(YAML、`schema_version: "0.1"`)

時間帯ごとの状態を書く。較正用(`calibration`)と予測用(`target`)を分ける。

```yaml
schema_version: "0.1"
resources:
  db_cpu:
    cores: 2              # DB に割り当てた CPU の数(必須)
    threshold: 0.8        # 使用率の閾値(既定 0.8)
  php_memory_limit: 128M  # 既定は対象アプリの php.ini の値。読めなければ必須

scenarios:
  - id: normal-1
    kind: calibration
    tables: { pages: 10000, books: 500 }
    rps: { "GET /books/{slug}": 5.0, "GET /search": 1.0 }
    observed: { db_cpu_utilization: 0.21 }   # 較正用は必須
  - id: peak-1
    kind: target
    tables: { pages: 100000, books: 3000 }
    rps: { "GET /books/{slug}": 15.0, "GET /search": 6.0 }
    observed: { db_cpu_utilization: 0.74 }   # 任意。バックテストのときだけ書く
```

- ルートは「メソッド + URI」で書く。静的解析の出力に無いルートが書かれていたら、エラーで止める(終了コードは実装で決める)
- `target` の `observed` は、予測を出し終えて記録するまでツールが読まない。読み込みの順序を試験で縛る
- シナリオに書かれていないルートの rps は 0 とし、その旨を出力に書く
- 件数が書かれていない表は「件数不明」として列挙し、勝手に小さいと仮定しない(spec.md フェーズ2と同じ)

## 4. 係数の測定(コストの式)

`poc/runtime/` を土台にする(D65)。ルートごとに、N となる表の件数を動かして次の3つを測る。

| 量 | 測り方 | 用途 |
| --- | --- | --- |
| クエリの本数 | 既存のとおり(1リクエストで発行された文の数) | DB の負荷 |
| 読んだ行数 | **rows examined**(DB が実際に読んだ行数)。返った行数ではない | DB の負荷 |
| ピークメモリ | `memory_get_peak_usage(true)` | メモリの限界 |

読んだ行数の測り方:

- 主:リクエストの前後で `SHOW SESSION STATUS LIKE 'Handler_read%'` を取り、`Handler_read_first`・`_key`・`_last`・`_next`・`_prev`・`_rnd`・`_rnd_next` の差分の合計とする。1ルート1プロセス・1接続で測る既存の仕組み(`bin/measure-one`)にそのまま載る
- 空のリクエスト(何もしない2回の取得)の差分を同じ方法で測り、引く
- 照合:検証用アプリでは、`performance_schema` の文ごとの `ROWS_EXAMINED` の合計と比べる試験を置く。差が 10% を超えるルートがあれば、試験を失敗させる

返った行数ではなく読んだ行数を測る理由:インデックスが効かない絞り込みでは、2つが桁で違う。Panorama(prior-art 6.5)は、DB の最適化で実際の計算量が変わることを、自分の推定の誤差の原因として挙げている。

当てはめ:

- 規模:N 軸は 100 / 1,000 / 10,000(既存と同じ)。子の表の軸は 3 / 30 / 300
- 各量について `y = a + b·N^k` を当てはめ、a・b・k と残差を出す。指数の判定の規則は log-log の傾き(D26)を引き継ぐ
- 静的解析の下限と食い違ったら(例:静的解析は O(N) 以上なのに、実測の k ≤ 0.2)、その式は採らずに「食い違い」として出す。偽の O(1) を採らないため(D21)
- 測れなかったルート(データが届かない、ロールバックできない、など)は、式を作らずに理由つきで列挙する。シミュレーションでは「コスト不明」とし、0 として足さない

## 5. 較正

ある時間帯の DB の負荷を、次の式で表す。

```
L = Σ_r λ_r · ( c_q · 本数_r(N) + c_row · 行数_r(N) )
    λ_r : ルート r の rps(シナリオの値)
    N   : そのシナリオの表の件数
DB の使用率 = L / cores
```

- 較正用シナリオが2本以上あるとき:観測値に合わせて c_q と c_row を最小二乗で決める(2係数)
- 較正用シナリオが1本のとき:2つの係数は決められない。本数だけの1係数(`L = c · Σλ·本数`)と行数だけの1係数(`L = c · Σλ·行数`)の両方で予測し、2つを予測の幅に含める。重みを勝手に仮定しない
- 係数が負になったら、その較正は採らずにエラーとして報告する(負の CPU は物理的にありえないため)
- 較正の残差を出力に書く

## 6. 予測と限界の判定

### 6.1 DB の CPU

- 予測用シナリオごとに使用率を出す
- そのシナリオの rps を全ルート同じ倍率で上げていき(0.1 刻み、上限 10 倍)、使用率が閾値を超える最初の倍率を「限界の倍率」として出す。10 倍で超えなければ「10 倍まで超えない」と出す
- 主因ルート:そのシナリオでの L のルートごとの割合の上位5本。影響度 = rps × コスト(prior-art 5.2 の Scout の方式)

### 6.2 PHP のメモリ

- ルートごとに、ピークメモリが `php_memory_limit × 0.8` を超える件数 N を出す(トラフィックには依らない)
- §7.1 の外挿試験で、メモリの誤差が基準(±30%)に入ったルートだけを出す。入らなかったルートは「精度不足のため出さない」と書く

### 6.3 予測の幅

乱数を使わず、同じ入力から同じ幅が出る方法で作る(spec.md の再現性の要件)。

- 式の幅:3 規模すべてで当てはめた式に加えて、3 規模から 2 規模ずつ選んだ 3 通りで式を作る(計 4 本)
- 較正の幅:2 係数の較正に加えて、本数だけ・行数だけの 1 係数の較正を作る(計 3 通り。1本のときは §5 の 2 通り)
- 予測値:3 規模の式 × 2 係数の較正(1本のときは、2 通りの中央)
- 幅:式と較正のすべての組み合わせで出した値の最小〜最大
- 合格基準(§7.4)の判定には、予測値を使う。幅は使わない

### 6.4 出力に必ず含めるもの

- 予測値と幅
- 値ごとの印:`measured`(測った規模の中)/ `interpolated`(測った規模の間)/ `extrapolated`(測った規模の外)。prior-art 5.2 の Oracle の方式
- 結果を最も左右した入力:各入力(表の件数、ルートごとの rps)を +10% 動かしたときの、限界の倍率の変化の大きい順に上位5つ
- コスト不明のルート、件数不明の表、rps が 0 とされたルート、`low_coverage` の有無
- 較正の方式(2 係数 / 1 係数)と残差

## 7. 正確さの確かめ方

### 7.1 A. 外挿試験

- 100 / 1,000 / 10,000 件で当てはめた式で 100,000 件の値を予測し、予測を記録してから 100,000 件で測る
- 対象:検証用アプリと BookStack のうち、§4 で式が作れたルート

### 7.2 B. ラボのバックテスト(D69)

手元の閉じたネットワーク内に再現した環境で、本当に負荷をかけて測る。

環境:

- BookStack + MySQL 8 + 負荷をかける道具(k6)。実測モードの安全の条件(内部ネットワーク、公開ポートなし。`poc/runtime/README.md` の 1〜5)を引き継ぐ。負荷をかける道具も同じ内部ネットワークの中に置く
- アプリは php-fpm で動かす(`artisan serve` は1本の処理しか同時に受けないため)
- DB のコンテナに割り当てる CPU は 2 に固定する。アプリ側には 6 を割り当て、DB より先にアプリが詰まらないようにする
- DB の CPU は、コンテナの cgroup の CPU 時間(`cpu.stat` の `usage_usec`)の差分で測る。瞬間の使用率は使わない
- 負荷をかけるのは GET のルートだけとする(書き込みで表の件数が変わるのを避けるため)

ルートの選び方(結果を見る前に、機械的に決める):

- BookStack の GET のルートのうち、§4 で式が作れたものを、静的解析の下限の次数が大きい順、同じなら「メソッド + URI」の文字列順に並べ、上位 8 本を取る
- この一覧はスクリプトで作り、ラボで1回も負荷をかける前に commit する。その commit の hash を記録に残す

シナリオ(N はそのルートの N となる表の件数。N_0 = 10,000):

| id | 種類 | 件数 | rps の合計 | ルートの混ざり方 |
| --- | --- | --- | --- | --- |
| cal-1 | 較正 | N_0 | R_0 | 8 本に均等 |
| cal-2 | 較正 | N_0 | R_0 | 並べた順の前半4本に 80%、後半4本に 20% |
| t-1 | 予測 | 3 × N_0 | 2 × R_0 | 均等 |
| t-2 | 予測 | 10 × N_0 | 2 × R_0 | 均等 |
| t-3 | 予測 | 10 × N_0 | 3 × R_0 | 前半に 80% |
| t-4 | 予測 | N_0 | 4 × R_0 | 均等 |
| t-5 | 予測 | 10 × N_0 | 4 × R_0 | 後半に 80% |

- R_0 は、cal-1 で DB の使用率が 20〜30% になる rps とする。cal-1 の条件だけで rps を 1 から倍々に上げて探す。予測用シナリオの測定は、R_0 を決める前に一切しない
- N となる表以外の表の件数は、生成器の既定に従う
- t-4 はデータ量を伸ばさず、トラフィックだけを伸ばす。素朴な見積もり(§7.3)が得意な条件で、peak-sim が負けないかを見るために入れる
- t-2・t-3・t-5 はデータ量を伸ばす。素朴な見積もりが見落とす条件

測り方:

- 1 シナリオは 10 分間の一定の到着率で負荷をかけ、最初の 2 分は捨てる
- 予測は、予測用シナリオを測る前に出し、ファイルにして commit する。その後で測る
- 決めた rps が実際に出たか(±5% 以内)をシナリオごとに確かめる。出なかったシナリオは「無効」として記録し、黙って使わない
- 有効な予測用シナリオが 4 本未満なら、B は「判定不能」とする。合格とは扱わない

ラボで言えないこと:本番に特有の効果(キャッシュの効き方、DB のメモリに収まらないデータの読み込み、他の処理との取り合い、書き込みの負荷)。これらは報告に必ず書く。

### 7.3 素朴な見積もり(比べる相手)

```
繁忙期の使用率(素朴) = 較正用シナリオの使用率 × (予測用シナリオの rps の合計 ÷ 較正用シナリオの rps の合計)
```

較正用シナリオが2本あるときは、rps の合計が大きい方を使う。同じなら、使用率の観測値が大きい方を使う。データ量の伸びとルートの混ざり方を無視した見積もりで、peak-sim がこれに勝てなければ、コードを読む意味が示せない。

### 7.4 合格基準(D71。データを見る前に固定する)

**A(外挿試験)**:対象のルートの 80% 以上で、100,000 件の予測が次の誤差に収まること。

| 量 | 許す誤差 |
| --- | --- |
| クエリの本数 | ±5% |
| 読んだ行数 | ±20% |
| ピークメモリ | ±30% |

**B(ラボのバックテスト)**:有効な予測用シナリオについて、次をすべて満たすこと。

1. 予測と実測の使用率の差の絶対値の平均が、素朴な見積もりより小さい
2. その平均が 15 ポイント以内
3. 「閾値を超えたか」の判定が、有効なシナリオの 80% 以上で実測と一致する(実測で閾値を超えたシナリオが無いときは、この条件を使わない)

**不合格のとき**:基準は動かさない。どの項がずれたかを記録し、式のどこを直すかを決める。直した後は、まだ見ていないシナリオやルートで確かめ直す(D51 と同じ)。B を確かめ直すときは、件数の倍率を 5 × N_0 と 20 × N_0 に変えた新しい予測用シナリオを使う。

数値(80%、±5 / 20 / 30%、15 ポイント)は、届きそうで緩すぎない値として置いた初期値で、先行事例の根拠は無い。

## 8. MVP で扱わないもの

- PHP のワーカー数、DB のコネクション数、キューの滞留(応答時間が要り、ローカルで測った時間は本番に持ち込めない)。spec.md フェーズ3のジョブとコマンドの試算も、MVP では扱わない
- 書き込みのルートの負荷(§7.2)
- 同時実行数と処理量の曲線(USL、prior-art 5.8)。本番相当の環境で負荷を測る必要があるため
- 大きな DB を統計値の拡大で模擬する方式(prior-art 5.9)。有効な特許として載っているため採らない。データは生成する

## 9. 実装の順序

各段の終わりに、動いた結果を記録してから次に進む。

1. 読んだ行数の測定(§4)を `poc/runtime/` に足し、検証用アプリで `performance_schema` との照合の試験を通す
2. 当てはめ(`a + b·N^k`)と、静的解析の下限との照合(§4)
3. A の外挿試験(§7.1)。ここで A の合否を出す
4. シナリオファイルの読み込み、較正、予測、幅、出力(§3.4・§5・§6)
5. ラボの環境(§7.2)。ルートの一覧の commit → R_0 の決定 → 予測の commit → 予測用シナリオの測定
6. B の合否を出す

A が不合格なら、5 に進む前に止まって報告する(式が当たらない状態で負荷をかけても、B の結果の意味が読めないため)。

## 10. 戻せる判断として決めたこと(D72)

殿の委任により、次は推奨の形で決めた。結果を見て変えるときは、判断記録に理由を書き、見ていないデータで確かめ直す。

- 実測するルートは、利用者がシナリオに書いたもの。コスト不明の割合が 20% を超えたら警告(§3.2)
- 較正用シナリオが1本のときは、重みを仮定せず、本数だけ・行数だけの両方を幅に含める(§5)
- 予測の幅は、乱数を使わない組み合わせの最小〜最大(§6.3)
- 読んだ行数は `Handler_read_*` の差分で測り、`performance_schema` で照合する(§4)
- シナリオファイルは §3.4 の形を `schema_version: "0.1"` とする
- ラボのシナリオの中身と、ルートの選び方(§7.2)
