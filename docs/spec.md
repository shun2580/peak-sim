# Laravel 繁忙期シミュレーター 仕様書(仮)

Oct 28, 2026 · @shun

## 概要と目的

Laravelアプリのソースコードを静的に解析し、「トラフィックやデータ量が増えたとき、どのルートから限界が来るか」を推定するCLIツールを作る。主な用途は、繁忙期前のスペックアップや改修の優先順位を、数字の根拠をつけて判断できるようにすること。

- ルートごとに、1リクエストあたりのクエリ数がデータ件数に対してどう増えるか(O(1) / O(N) / O(N×M))を判定する
- テーブル規模のヒントで危険度を重み付けする
- トラフィック倍率を与えると、どのルート・どのリソースが先に限界に達するかを推定する
- 本番環境には接続しない。対象リポジトリのローカルクローンとローカルDBだけで動く

## 背景と先行事例

部品ごとの先行例はあるが、「Laravel向けに、テストを書かず静的にクエリの増え方を出し、繁忙期の限界まで推定する」組み合わせは見当たらない(2026-10時点の調査)。

| ツール | 方式 | 本ツールとの違い |
| --- | --- | --- |
| [Enlightn](https://packagist.org/packages/enlightn/enlightn) | ルールベースの性能・セキュリティ監査(本家はメンテナンス終了) | 増え方や繁忙期の観点がない |
| [PowerStation](https://par.nsf.gov//servlets/purl/10067548) | Rails向け研究プロトタイプ。アクション単位のDBを意識した静的解析 | Rails専用、実務ツールとしては普及していない。アンチパターン分類は設計の参考にする |
| [phpunit-query-scaling](https://github.com/ralder/phpunit-query-scaling) | Laravelのテストでデータ規模を変えてクエリ数の増え方を実測 | 動的方式で、ルートごとにテストが必要 |
| [laravel-nplusone-scanner](https://packagist.org/packages/amrachraf6699/laravel-nplusone-scanner) | ASTベースのN+1静的検出 | N+1のみ。ルート単位の集計や規模の考慮がない |
| [Laravel Surveyor](https://github.com/laravel/surveyor) | 公式のメタデータ抽出ツール(ベータ) | 競合ではなく、土台候補 |

## スコープとフェーズ

MVPは繁忙期シミュレーターまで含める。ただし内部で3フェーズに切り、各フェーズの終わりで動くものを確認してから次に進む。

1. **フェーズ1 増え方の判定**:ルートごとのクエリ増加パターンを一覧化する
2. **フェーズ2 規模ヒントによる重み付け**:テーブル規模を掛けて危険度を出す
3. **フェーズ3 繁忙期シミュレーター**:トラフィック倍率から限界点を推定する

前提条件:

- 対象:Laravel 11以降(ツールの動作要件はPHP 8.2以上)。Laravel 11 はフレームワーク自体のサポートが終わっているため、ベストエフォート対応(動作は確認済み)
- OSSとして公開する(GitHub / Packagist、Zenn記事化を想定)
- 実装は将軍が担当し、仕様と要件はこのドキュメントで管理する

## アーキテクチャ

ツール本体は対象アプリの外で動く単体CLIとし、Laravelの構造情報は対象アプリのartisanコマンドのJSON出力から集める。対象アプリに何もインストールしないので依存衝突が起きず、Laravelのバージョン差は公開コマンドの出力形式に閉じる。

&#91;embedded content: 構成 · 入力3つ、解析CLI、出力\]

構造はローカルから自動で集め、規模とトラフィックだけ人がYAMLで与える。使い勝手が必要になったら、このCLIを呼ぶだけの薄いComposerパッケージを後から足す。

配布形態はphar(単一ファイル)を主とする。依存が中に閉じるので他ツールと衝突せず、ファイル1つで配布できる。

- **artisanの呼び方を設定可能にする**:対象アプリがDocker内で動く構成に対応するため。例:`artisan_command: "docker compose exec app php artisan"`
- **事前書き出しモード**:artisanのJSON出力を事前にディレクトリへ書き出し、そのディレクトリを渡して解析できるようにする。artisanを直接呼べない環境での逃げ道
- **Composerグローバル**:pharを包むだけの形で後から追加してよい
- **Dockerイメージ**:対象アプリのコンテナ内のartisanを呼ぶのが煩雑なため、MVPでは提供しない

## フェーズ1 解析仕様:増え方の判定

各ルートについて、クエリ数とロード件数がデータ件数にどう比例するかを判定し、根拠となるコード位置を添えて出す。

処理の流れ:

1. ルート一覧からコントローラーのメソッドを特定する
2. そのメソッドから、`app/` 配下のメソッド呼び出しを、vendorに出るか再帰を検出するまでたどる(安全上限20段)
3. クエリを発行する箇所と、それを囲むループを検出する
4. ループの入れ子と対象テーブルから、ルートの増え方を決める

検出対象:

| 分類 | 例 | 判定への影響 |
| --- | --- | --- |
| クエリ発行 | `Model::where()->get()`、`find()`、`DB::table()`、`count()` | 1回ごとにクエリ1本 |
| 遅延ロード | ループ内での `$order->items` などのリレーション参照 | N+1の主因 |
| ループ | `foreach`、`for`、`while`、Collectionの `each` / `map` / `filter` | 内側のクエリをN倍にする |
| 先読み | `with()`、`load()`、`withCount()` | 該当リレーションのN+1を打ち消す |
| 無制限ロード | `all()`、件数制限なしの `get()` | クエリ数はO(1)でもメモリがO(N) |
| 制限ありロード | `paginate()`、`limit()`、`chunk()`、`lazy()`、`cursor()` | メモリを一定に保つ(ただし cursor() はクエリ1本だが、PDOが結果を全件バッファするためメモリはO(N)) |

判定結果は「クエリ数の増え方」と「メモリの増え方」の2軸で持つ。各判定には、Nがどのテーブルの件数かを紐づける。

静的に追えないもの(動的なメソッド名、コンテナ経由の解決など)は「不明」として明示し、推測で埋めない。各判定には確度(high / medium)を付ける。

### 確度と「不明」の定義

根幹の原則:**「分からない」を「安全」にしない。** 追えない呼び出しが経路に1つでもあれば、その軸を O(1) とは出さない。危ないルートを安全と出す見逃しは、「不明」と出すより害が大きい。

| 確度 | 意味 |
| --- | --- |
| high | 経路上の呼び出しが、すべて解決できた |
| medium | すべて解決できたが、推定を含む(実装が複数ある束縛で最悪ケースを採った、リレーション名を推論で当てた、など) |
| (low は使わない) | 追えない部分があれば、その軸は `unknown` とする |

- `unknown` のときも、追えた範囲で分かった**下限**(「少なくとも O(N)」など)があれば、別の項目として添える。確度と「下限であること」は別の情報として出す
- gap がある軸は、既知の下限が O(N) であっても `unknown` と出し、下限を括弧で添える(例:`unknown (≥O(N))`)。O(N) と出して gap を添えることはしない。gap の先に、下限より重い増え方が隠れうるため(判断記録 D27)
- **追えなかった箇所(gap)** は、ファイル・行・理由つきで記録し、出力に含める
- 「何も見つからなかった」と「見つけようとして追えなかった」を必ず区別する。前者は判定の根拠になるが、後者は根拠にならない

出力には、各軸の判定と確度に加えて、下限と gap の一覧を含める。

#### 例外表の基準

解決できなかった呼び出しは gap にする。ただし、例外表(`resources/known-calls.php`)に載せた呼び出しは、gap にしない(判断記録 D28)。

- 例外表に載せるのは、「DB に触れず、アプリのコードを呼び返さない」ことを、根拠(basis・why)つきで確かめた呼び出しだけ。足すときは、根拠と試験を添える
- 載せないもの(Gate / Policy、Validator、`event()` / `dispatch()`、`Auth::user()`、Mail、`Http::`、`DB::raw`、`Cache::store()` など)を使うルートは、`unknown` になる
- `unknown` を緩める設定は、実アプリで試した結果を見てから決める
- DB に触れるが1リクエストあたりの本数が一定の呼び出し(`Auth::user()` など)は、例外表に足さず、将来「定数コストの呼び出し」として数える方針とする。未着手(判断記録 D29。未決事項参照)

解析対象には、コントローラーの外で発生するクエリも含める:Bladeテンプレート、`JsonResource`、`$appends` のアクセサ、モデルの `$with` プロパティ。

`Cache::remember` で包まれたクエリは、キャッシュミス時の増え方とヒット時のO(1)を両方記録し、キャッシュ付きであることを明示する。危険度とシミュレーターの既定はミス時(最悪ケース)で計算し、YAMLでヒット率が指定されていれば反映する。繁忙期の頭にキャッシュが一斉に切れるケースに備えるため。

変数の型は自前の簡易推論で解決する。`model:show --json` で取れるリレーション名の一覧を使い、モデルの静的呼び出しやクエリビルダーの戻り値をループする、といった典型的な流れだけを追う。追えないものは「不明」にする。PHPStan + Larastan は、対象アプリのオートロードや起動が必要になり重くなるため使わない。検証用アプリで精度が足りなければ見直す。

呼び出しの追跡について:

- **深さ**:DDDやレイヤード構成(Controller → UseCase → DomainService → Repository → Eloquent実装)では5〜6段になるため、深さは実質無制限とする。安全上限(既定20段、設定で変更可)に達したら「上限で打ち切り」と明示する
- **メソッドごとの要約**:各メソッドの解析結果(1回呼ぶとクエリが何本、Nにどう比例するか)を1度だけ計算して使い回す。深くしても計算量が爆発しないようにする
- **インターフェースの解決**:ServiceProviderの `bind` / `singleton` や `$bindings` プロパティを静的に読み、インターフェースと実装の対応表を作る。プロパティの型はコンストラクタの型宣言(依存性注入)から決める
- **実装が複数ある場合**:条件付きの束縛や複数の実装は全候補を解析し、最悪ケースを採用してその旨を明示する

## フェーズ2 規模ヒントによる危険度

フェーズ1の増え方に、規模ヒントから得た件数Nを代入して、1リクエストあたりの推定クエリ数と推定ロード件数を出し、ルートを危険度順に並べる。

- タグは代表件数に変換する。初期値の案は small = 100、medium = 10,000、large = 1,000,000(設定で上書き可)
- 概算件数が数値で書かれていればそれを優先する
- ヒントのないテーブルは「規模不明」として別枚で列挙し、勝手に小さいと仮定しない
- インデックスのないカラムでの絞り込みは、クエリ1本あたりのコストがNに比例するものとして重みを上げる

スコアの計算式はフェーズ2着手時に確定する(未決事項参照)。

## フェーズ3 繁忙期シミュレーター

トラフィック倍率を与えると、どのリソースが何倍で限界に達するかと、その主因になるルートを出す。

考え方:

- ルートiの秒間クエリ数 = 平常時rps × 倍率 × フェーズ2の推定クエリ数
- 全ルートの合計を、利用者が入力したリソース上限(DBの処理能力、コネクション数、PHPワーカー数など)と比べて使用率を出す
- 同時実行数はリトルの法則(同時実行数 = 到着率 × 処理時間)で見積もる
- 倍率を1倍から上げていき、最初に使用率が閾値を超えるリソースとその倍率を報告する

精度についての扱い:

- クエリ1本の処理時間やリソース上限を入力しなければ、結果は「ルート間の相対的な負荷の内訳」に留め、絶対値は出さない
- 実測値(平常時のDB CPU使用率や平均クエリ時間)を入力すると、それを基準に絶対値に換算する
- 推定であることと、どの入力が結果を最も左右したかをレポートに必ず書く

過去の繁忙期データで予測精度を検証するバックテスト機能はMVP後の拡張とする。

ジョブとコマンドは、起動のされ方で分けて試算する。

| 種類 | 頻度の求め方 | シミュレーションでの扱い |
| --- | --- | --- |
| リクエストから `dispatch` されるジョブ | ルートのrps × 1リクエストあたりのdispatch数(自動)。倍率と一緒に増える | DBへのバックグラウンド負荷と、キュー滞留 |
| スケジュール実行のコマンド・ジョブ | スケジュール定義から静的に取得。取れないものはYAMLで手入力・上書き | DBへのバックグラウンド負荷。繁忙時間帯と重なるかをYAMLで指定 |

ジョブは非同期なのでレスポンス時間には直接効かない。代わりに、ジョブの発生ペースがワーカーの処理能力を上回る倍率(キューが滞留し始める点)を別に報告する。

## 将来拡張:MCPモード

MVP後に、解析結果をMCPツールとして公開し、Claude CodeやCopilotなどのAIエージェントから呼べるようにする。別プロジェクトにはせず、同じCLIに起動モードとして追加する。

位置づけ:DBの事実を返すMCPは既にある([Laravel Boost](https://laravel.com/docs/master/boost)、[laravel-agent-mcp](https://github.com/anilcancakir/laravel-agent-mcp)、[Postgres MCP Pro](https://mcpservers.org/servers/crystaldba/postgres-mcp)など)。本ツールはそれらと競合せず、次の2点を補う。

- コードの側の判定:ルートごとのクエリとメモリの増え方
- 本番規模での危険度:既存MCPをローカルDBにつなぐと開発データの件数しか返らない。本ツールは規模ヒントを前提に評価する

公開するツールの案:

| ツール | 返すもの |
| --- | --- |
| `list_routes_by_risk` | 危険度順のルート一覧と増え方 |
| `explain_route` | 1ルートの判定、根拠のファイル:行、確度 |
| `simulate_peak` | 倍率を受け取り、限界に達するリソースと主因ルート |

制約:

- 中身はフェーズ1〜3のJSON出力と同一。MCP用の別ロジックは持たない
- 非機能要件(本番非接続、データの中身を読まない、再現性)をそのまま引き継ぐ
- 読み取り専用。対象アプリや設定ファイルを書き換えるツールは公開しない

## 出力形式

同じ解析結果を、人向け・CI向け・共有向けの3形式で出す。

| 形式 | 用途 | 内容 |
| --- | --- | --- |
| CLI表示 | 手元での確認 | 危険度順のルート一覧、各ルートの増え方と根拠のファイル:行 |
| JSON | CI、他ツールやAIエージェントからの利用 | 全判定と入力の前提、確度 |
| Markdownレポート | 稟議やレビューへの添付 | シミュレーション結果、前提条件、改善候補のルート |

CLIの終了コードで、閾値を超えたルートがある場合にCIを失敗させられるようにする。

## 非機能要件

- **本番非接続**:本番のDB・ログ・クラウドには一切接続しない。接続先はローカルDBのみ
- **外部通信なし**:解析中にネットワークへ出ない。テレメトリも持たない(開発環境の準備でパッケージやイメージを取得するのは対象外)
- **対象アプリを汚さない**:対象プロジェクトにパッケージを追加せず、ファイルも書き換えない(設定ファイルの雛形生成を除く)
- **データの中身を読まない**:ローカルDBからも取得するのはスキーマとインデックスのみ
- **依存衝突を起こさない**:ツール本体は対象アプリの外で動く単体CLIとして配布する
- **再現性**:同じ入力には常に同じ結果を返す(LLMを解析の中核に使わない)
- **性能**:数百ルート規模のアプリを実用的な時間で解析できること(目標値は未決)

## 検証用テストアプリ

判定の正しさは、答えの分かっているパターンを仕込んだ自作のLaravelアプリで確かめる。各ルートの「期待する判定」がそのまま正解データになる。業務特有の書き方ではなく、Laravelで一般的に問題になる書き方を網羅する。

- `/ok/`:誤検知が出ないことの確認
- `/ng/`:検出できることの確認
- `/hidden/`:コントローラーの外で発生するクエリを追えることの確認
- `/unknown/`:静的に追えないものを「不明」と出せることの確認

一覧系のルートは、特に断りがない限り `Order::get()` などで件数制限なしに全件を取る。期待値は人が決め、実装側で推測して埋めない。DBはMySQL 8を前提とする(cursor()のメモリなど、ドライバの挙動に依存する期待値があるため)。

| ルート | 仕込む内容 | 期待するクエリ | 期待するメモリ | N(M)のテーブル |
| --- | --- | --- | --- | --- |
| `/ok/eager` | `with()` で先読みした一覧 | O(1) | O(N) | orders |
| `/ok/paginate` | `paginate()` 付きの一覧 | O(1) | O(1) | orders |
| `/ok/chunk` | `chunk()` | O(N)(係数は1/チャンクサイズ) | O(1) | orders |
| `/ok/lazy` | `lazy()` | O(N)(係数は1/チャンクサイズ) | O(1) | orders |
| `/ok/with-count` | `withCount()` / `withSum()` | O(1) | O(N) | orders |
| `POST /ok/bulk` | 全顧客分のレコードを `insert()` / `upsert()` で一括作成 | O(1) | O(N) | customers |
| `/ng/n-plus-one` | ループ内で `$order->customer` | O(N) | O(N) | orders |
| `/ng/nested` | 二重ループで `$order->items` → `$item->product` | O(N×M) | O(N×M) | N=orders、M=1注文あたりのitems |
| `/ng/count-in-loop` | ループ内で `->items()->count()` | O(N) | O(N) | orders |
| `/ng/unbounded` | `Order::all()` | O(1) | O(N) | orders |
| `/ng/get-then-count` | `->get()->count()` | O(1) | O(N) | orders |
| `/ng/collection-filter` | `get()` の後にCollectionの `where` / `filter` で絞り込む | O(1) | O(N) | orders |
| `/ng/save-in-loop` | 全顧客をループして `save()` | O(N) | O(N) | customers |
| `/ng/first-or-create-in-loop` | 全商品をループして `firstOrCreate` / `updateOrCreate` | O(N)(1件あたり2本。条件つき、下の注記参照) | O(N) | products |
| `/ng/service` | N+1をサービスクラスの奥(2〜3段)に隠す | O(N) | O(N) | orders |
| `/ng/layered` | Controller → UseCase → DomainService → Repositoryインターフェース → Eloquent実装の5段で、最奥にN+1 | O(N) | O(N) | orders |
| `/hidden/blade` | Blade内でリレーション参照 | O(N) | O(N) | orders |
| `/hidden/resource` | `JsonResource` 内でリレーション参照 | O(N) | O(N) | orders |
| `/hidden/cache` | N+1を `Cache::remember` で包む | ミス時 O(N)、ヒット時 O(1)。キャッシュ付きと明示 | O(N)(シリアライズするキャッシュドライバ(Redis、Memcached、database、file など本番で一般的なもの)では、ヒット時も全件を復元するためメモリ O(N)。シリアライズしない array ドライバは対象外) | orders |
| `/hidden/appends` | `$appends` のアクセサ内でリレーション参照 | O(N) | O(N) | orders |
| `/hidden/model-with` | モデルの `$with` プロパティ | O(1)(毎回1本追加。`$with` の先読み1つにつき1本、下の注記参照) | O(N) | orders |
| `/hidden/cursor` | `cursor()` | O(1) | O(N)(PDOが結果を全件バッファする) | orders |
| `/hidden/conditional-binding` | 環境によって実装が切り替わる束縛(先読みありの実装とN+1の実装) | O(N)(全候補のうち最悪ケースを採用したと明示) | O(N) | orders |
| `/unknown/dynamic` | `$this->{$method}()` のような動的呼び出し | 不明 | 不明 | — |

表の注記(2026-11-01、将軍裁定 S-32):

- メソッドの記載がないルートは GET。`POST /ok/bulk` だけ POST
- `/ok/bulk` の O(1) は、MySQL のプレースホルダ上限(このルートでは 13,107 顧客)の内に限る。ツールはこの上限を判定に使わない
- `/ng/first-or-create-in-loop` の「1件あたり2本」は条件つき:`firstOrCreate` は行が無いとき(SELECT + INSERT)、`updateOrCreate` は値が変わるとき(SELECT + UPDATE)。検証用アプリは `?via=update` で `updateOrCreate` 側を認める
- `/hidden/model-with` の「毎回1本追加」は、`$with` の先読み1つにつき1本と読む(実測で 2 / 2 / 2 本と合う)
- 期待値との一致は、**クエリ・メモリ・N(M)のテーブル**の3軸で判定する。次は出力に必須だが、一致の判定の軸には入れない:キャッシュのミス時 / ヒット時とキャッシュ付きの明示、最悪ケース採用の明示。係数の補足(chunk の 1/チャンクサイズ、1件あたり2本、毎回1本追加)は、出せれば出す。一致の判定には入れず、出せなければ報告する

インデックスが効かない書き方(`LIKE '%...'`、`inRandomOrder()`、インデックスのない列での `orderBy` / `whereHas`)は、1本あたりのコストの問題なのでフェーズ2の検証用として別枚で用意する。

期待値そのものが正しいかは実測で確かめる。

- クエリ数:[phpunit-query-scaling](https://github.com/ralder/phpunit-query-scaling)(PHP 8.3以上、Laravel 12/13)で、件数を変えたときの増え方を測る。使えない場合は `DB::listen` による自前の計測でよい。そのため検証用アプリはLaravel 12か13で作る
- メモリ:`memory_get_peak_usage` を件数ごとに測り、O(1)かO(N)かを大まかに確かめる。誤差が大きいので参考値とする。増加分が小さいルート(`/hidden/cursor`)は、バイト / 行も併記する
- `/hidden/cache` のメモリは、シリアライズを有効にして測る(シリアライズするドライバでは、ヒット時も全件を復元するため)。この測り方は正しい
- 増え方の判定規則:件数を動かして測った結果を、log-log グラフの傾きに一本化して判定する(2026-11-01、将軍裁定 S-32)
  - O(1):傾き ≤ 0.2
  - O(N):傾き ≥ 0.5
  - 0.2 と 0.5 の間:判定不能。どちらかに合わせず、そのまま報告する
  - O(N×M):N を動かした傾きと M を動かした傾きが、両方 ≥ 0.5
  - クエリ数の区間ごとの傾きのばらつきは ±10% 以内
  - メモリは参考値のまま
- `/hidden/conditional-binding` は、テスト内で束縛を差し替えて両方の実装を測る。`/unknown/dynamic` は実測の対象外
- 実測と期待値が食い違った場合は、無理に合わせず報告する(期待値の側が間違っている可能性があるため)

公開リポジトリのテストやサンプルには、業務のコードやテーブル名を使わない。
